## 指摘

### 1. 直すべき｜コード（C8・C3）｜snippets/bitwise-independence/pair-xor-sum.cpp 3 行目のコメントと range_xor_sum（39 行目）

- 問題：冒頭のコメントは区間の和を「a[i] < 2^30・n <= 2×10^5 程度なら long long に収まる範囲で使う」とするが、この範囲で `res += odd << k` があふれる（符号付き整数のあふれで未定義動作）
- 根拠：n = 2×10^5、a[i] を 2^30 未満の乱数にして動かすと、サニタイザが `pair-xor-sum.cpp:39:13: runtime error: signed integer overflow: 5368762800648749056 + 5368747814968358608` を出し、2 行目の出力は −7709340841453593519 になった。Python で計算した正しい値は 10737403232255958097（> 2^63 − 1 = 9223372036854775807）。理論上も、各 bit で s の 0・1 が半々なら和は約 (N+1)^2/4 × (2^30 − 1) ≈ 1.07×10^19 になる
- 直し方：コメントの範囲を実際に収まるものに直す（例：「a[i] < 2^27（10^8 程度）・n ≤ 2×10^5 なら収まる」。(2×10^5+1)^2/4 × 2^27 ≈ 1.3×10^18）。または ループの上限を値の範囲に合わせ、本文の落とし穴の段落（個数 × 個数 × 2^k のあふれ）で区間版にも触れる。cases に n が大きい場合は入れにくいので、コメントの数字を正すのが最小の直し

### 2. 直すとよい｜コード（C8）｜pair-xor-sum.cpp 54〜62 行目（main の素朴な照合）

- 問題：`naive_range` を値の大きさにかかわらず計算するので、値が 2^30 以上の入力（cases の 5 件目のような 60 bit の値）では素朴な区間の和があふれる（未定義動作。結果は使わないが、UB が残る）
- 根拠：60 bit 近い値の乱数入力で、サニタイザが `pair-xor-sum.cpp:61:29: runtime error: signed integer overflow` を出した
- 直し方：素朴な区間の和の計算を `small` が真のときだけ行う（`small` の判定を照合の前に 1 回だけ作り、重複している 2 つの `small` の計算もまとめる）

### 3. 直すとよい｜分かりやすさ（U2・U3）｜節 top-down の「上限 X ≤ K があると bit どうしがつながる」の段落

- 問題：場合分けの説明が 1 段落に詰まっていて、レート 1000 前後の読者には「bit d を（K が 1 のところで）0 にすると、d より下は自由」がなぜ X ≤ K を保つのか（上が同じで bit d が K より小さいので、下をどうしても K 未満）と、各候補で下の bit をどう決めるか（上限なしと同じ多数決）が追いにくい。確認問題で反例はあるが、正しい手順の小さな例がない
- 根拠：本文だけで擬似コードを書こうとすると、「候補ごとに上の bit を K と同じに、bit d を 0 に、下を多数決で決め、f を計算して最大を取る」を自分で組み立てる必要がある
- 直し方：「上が K と同じで bit d が K より小さいので、下の bit をどう選んでも X < K」の一言を足し、確認問題の a = (4, 0, 0)・K = 4 で候補（d = 2 で X = 3、X = K = 4）を比べる 1〜2 文を本文に置く。または 4〜5 行の擬似コード（```text）にする

### 4. 直すとよい｜分かりやすさ（U3・U9）｜節 addition の 3 つめの箇条「和そのものは線形性で足す」

- 問題：「$\sum_i (X \oplus a_i)$ も、XOR を先に計算してから足しているので、bit ごとの寄与の和に分けてよい」が、見出し「和そのものは線形性で足す（bit に分ける必要はない）」と逆向きのことを述べていて、箇条の主張がぶれる
- 根拠：同じ箇条の前半は「bit に分ける必要はない」、後半は「bit に分けてよい」
- 直し方：後半を箇条の外（箇条の前の「XOR は繰り上がりを無視した足し算…」の段落の後など）に移し、「XOR してから足すのは分けてよい、足してから bit を見るのは分けられない」の対比として 1 文で書く

### 5. 直すとよい｜図（G5）｜bit-count-table.svg の行ラベル「1 × 0 × 2^k」

- 問題：「1 × 0 × 2^k」は数として読むと 0 になり、「1 の個数 × 0 の個数 × 2^k」の意味だと分かりにくい
- 根拠：SVG の 272 行目付近のテキスト。前の 2 行が「1 の個数」「0 の個数」なので推測はできるが、図だけを見ると誤読しうる
- 直し方：ラベルを「寄与」にし、セルの式はそのまま（2×1×4 = 8）にする。または「(1 の個数)×(0 の個数)×2^k」と書く（x=30 から 170 の手前まで収まる長さにする。15px で全角 7 字程度が上限なので、2 行に分けるか「寄与」が無難）
- 図のほかの点：値・ラベル・合計（8 + 4 + 2 = 14 = 6 + 5 + 3）は本文と一致。背景は白で塗られ、viewBox があり、文字はテキストのまま、相対パスで参照されている。最下行の文は全角 3 字・半角約 60 字で、15px の太字でも x = 30 から 620 前後に収まる見込み（描画しての確認はしていない。メインが描画できる環境で一度見るとよい）。格子が左の 480px にあり右に余白が残るが、問題はない

### 6. 直すとよい｜記法とリンク（F7）｜節 addition の「（[XOR の性質](../basics/bit-operations.md)）」

- 問題：$a + b = (a \oplus b) + 2(a \text{ AND } b)$ の出どころとしてページ全体へリンクしている。bit-operations は draft 以降で、該当の節 `#xor-properties`（「XOR の性質（打ち消し・a + b との関係・0〜n の XOR）」）がある
- 根拠：手引き §7「節は #anchor を足す。draft 以降のページの節へはリンクしてよい」。なお bit-operations へは要点の前提でもリンクしており、本文での初出は導入ではなくこの節なので、1 回目のリンクとして置くのは妥当
- 直し方：`../basics/bit-operations.md#xor-properties` にする

### 7. 直すとよい｜事実（F2）｜節 range-xor の最終段落と落とし穴「区間の AND・OR を累積で引こうとする」

- 問題：「累積で打ち消せるのは XOR だけである」「累積で引けるのは XOR（と和）だけである」は言い過ぎ（逆元のある演算なら一般に引ける。例：素数の法での積）
- 根拠：累積で区間を求められる条件は「逆の操作があること」で、本文もその理由を述べている
- 直し方：「AND・OR は累積で引けない（逆の操作がない）」と、AND・OR についての否定に絞る。または「この話題の演算（XOR・AND・OR）のうちで」と範囲を付ける

### 8. 直すとよい｜読みやすさ（U9）｜節 addition の 1 つめの箇条（153 字）と節 range-xor の最終段落の 1 文（133 字）

- 問題：1 文に条件と括弧書きが重なり、目安の 120 字を超える
- 直し方：addition の箇条は「この条件の下では…3 通りになり、bit ごとに独立に数えられる。」で切り、上限 L の括弧書きを次の文にする。range-xor は「（AND なら…、OR なら…）」の括弧を別の文にする
