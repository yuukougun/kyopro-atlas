## 指摘

### 1｜直すべき｜事実（F2）｜#pitfalls「付け替え先が区間の中にある」

- **問題**：「区間の中の要素 c の直後へ移すと閉路ができ、先頭からたどると無限ループになる」は誤りである。区間を切り取った時点で外側の p と n が直接つながるので、先頭からのたどりは区間に入らずに TAIL へ着く。実際に起きるのは、区間（の一部）が列から外れて閉路になり、出力から黙って消えることである。無限ループになるのは区間の中の要素から nxt をたどったときだけ。また山の場合の条件「p が c より上にない」は、p が一番上である前提では「p が c と同じ山にない」と同じで、言い方がずれている（同じ山なら一番上の p は必ず c 以上にある）
- **根拠**：一時置き場の splice.py。区間 2〜4 を 2・3・4 の直後へ移すと、どれも先頭からのたどりは `[1, 5]` で止まる。山（土台・1〜4）で c = 2 を p = 4 の上へ移すと、土台からの枚数は 1 で止まり、2〜4 は 2→3→4→2 の閉路になる
- **直し方**：「区間 a〜b を区間の中の要素 c の直後へ移すと、区間が列から外れて閉路になる。先頭からたどっても止まるが、区間の要素が黙って出力から消える（区間の中からたどると止まらない）。山の付け替えなら、p が c と同じ山にない（c の上に乗っていない）ことが制約で保証されているかを確かめる」とする

### 2｜直すとよい｜事実（F2）・分かりやすさ（U9）｜#choosing の表の最後の行

- **問題**：「値の大小の順で前後や $k$ 番目を問う → set」とあるが、set で $k$ 番目を引けるのは $k$ が小さいときだけである（リンク先の ordered-set #near-kth もそう書いている）。読者が「set で k 番目が速い」と読み違える
- **根拠**：docs/ds/ordered-set.md 87〜93 行（イテレータは 1 歩ずつしか動けず、$K$ が大きいと $O(N)$）
- **直し方**：「値の大小の順で前後を問う → set」とし、$k$ 番目は「BIT（K 番目の値を求めるデータ構造）か pb_ds の tree」と分けて書く

### 3｜直すとよい｜図（G3）｜insert-erase.svg

- **問題**：viewBox の幅 720 のうち節点は x = 590 までで、右の約 130 は凡例の行以外は空いている。幅 358px に縮むと縮尺が約 0.5 になり、14px の文字が約 7px、凡例の 12px が約 6px になって読みにくい。行の間（約 120）も広い
- **根拠**：幅 358px の枠で画像にして確認（節点の数字は読めるが、見出しと凡例の文字は小さい）
- **直し方**：凡例を 2 行に分けて viewBox の幅を 620 程度に詰め、行の間を詰める（例：viewBox="0 0 620 360"）。あるいは文字を 16px・凡例を 14px に上げる

### 4｜直すとよい｜事実（F1）｜#output の「map なら $O(L \log L)$」

- **問題**：map の 1 回の参照は map の大きさの対数である。削除で行を消すコード片なら大きさは $L + 2$ だが、本文の落とし穴が勧める「在否の印を別に持つ」書き方では削除した値の行が残り、大きさは $N + Q$ までになる。要点の「map なら $O(\log N)$」も $N$ が初期の長さか全要素数かが書かれていない
- **根拠**：std::map の検索は大きさ $M$ に対して $O(\log M)$。例題の解法の詳細は正しく $O(\log(N + Q))$ と書いている
- **直し方**：#output を「map なら $O(L \log M)$（$M$ は map に入っている行の数）」に、要点・complexity の $O(\log N)$ を「$N$ は登場する要素の総数」と一言添える
