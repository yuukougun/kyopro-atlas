- **問題**：viewBox が 850 × 470 の横長で、スマホの表示幅（約 358px）では縮尺が 0.42 になる。本文の文字（font-size 14）が約 5.9px、深さのラベル・表の見出し・下の補足（12）が約 5.1px になり読めない

- **直し方**：木と表を横に並べず縦に積む（上に木、下に①②③の文と表）。幅は 460 前後に収まる（木は x = 20〜420、表は 5 列で幅 350 ほど）。font-size を 16（補足は 14）にすれば 358 / 460 × 16 ≈ 12.5px。表の見出し「u の 2^k 上」は「u の 2ᵏ 上」か「up[k][u]」にすると幅も詰まる

### 5｜直すとよい｜分かりやすさ（U3）・事実（F2）｜#kth-ancestor の最後の段落「最も遠い頂点は直径の端点にとれるので、端点を根にした木で u の K 個上を求めればよい」

- **問題**：「端点を根にした木」が単数で、1 つの端点を根にすれば足りるように読める。実際は 2 つの端点 $x, y$ のどちらが遠いかは $u$ によるので、両方の根で試す必要がある（例題の解法の詳細では正しく 2 つ作っている）
- **直し方**：「直径の両端それぞれを根にした 2 つの木で、深さが $K$ 以上のほうから $u$ の K 個上を求めればよい」とする

### 6｜直すとよい｜事実（F2）｜#kth-ancestor の「パス $u$–$v$ 上で $u$ から $K$ 番目の頂点」

- **問題**：$K \le d(u, v)$ の条件が書かれていない。$K > d(u, v)$ のとき「$v$ の $d(u, v) - K$ 個上」は負の個数になる
- **直し方**：「$0 \le K \le d(u, v)$ とする」と前置きする

### 7｜直すとよい｜事実（F2）｜#pitfalls の 1 項目目「$2^{17} = 131072$ より深い頂点」

- **問題**：17 段で届く最大は $2^{17} - 1 = 131071$ 個なので、届かないのは深さの差が 131072 **以上**のとき。「より深い」だと 131072 ちょうどが漏れる
- **直し方**：「深さの差が $2^{17} = 131072$ 以上になると（パス状の木で起きる）届かず」とする

## 確かめて問題がなかった点

- 要点・front matter の complexity・本文の計算量（前処理 $O(N \log N)$・1 回 $O(\log N)$・表 $O(N \log N)$）が一致し、根拠が「なぜ速いか」にある（F1・F10）
- 「なぜ正しいか」の単調性の議論（同じ深さの 2 頂点を $d$ 個上げて一致するのは $d \ge D$ のとき、根で止まっても一致は保たれる）は正しく、2 段目がこの最大の $d = D - 1$ を上の桁から決める説明になっている
- 比較の表（オイラーツアーと Sparse Table：$O(N \log N)$・$O(1)$・列の長さ $2N - 1$、HL 分解：$O(N)$・$O(\log N)$）は cp-algorithms と一致
- 確認問題 1・2・4 の答えは正しく、理由まで書かれている
- 本文中のリンク先の anchor（doubling の table・binary-search-on-doubling・aggregates、tree-traversal の recursion-depth、euler-tour の root-path・meanings、tree-diameter の root-at-end、hld の when-to-use、minimum-spanning-tree の why-correct・query-edges、glossary の identity-element）はすべて存在する
