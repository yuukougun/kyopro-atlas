## 指摘

### 1（直すべき）コード｜例題 abc157_e の「解法の詳細」（L265）

- **問題**：`popcount(prod(l - 1, r))` と書いているが、値の型が `int` のセグメント木（本文の char-set.cpp と同じ形）では、`std::popcount` は符号なしの整数しか受け付けないのでコンパイルエラーになる。コード片の方は `popcount((unsigned)seg.prod(l, r))` とキャストしており、本文とコード片が食い違う
- **根拠**：`int x = 5; cout << popcount(x);` を `g++-15 -std=gnu++23` でコンパイルすると `error: no matching function for call to 'popcount(int&)'`
- **直し方**：`popcount((unsigned)prod(l - 1, r))` にそろえる。あわせて文字列へのクエリの節（L206 の「`popcount`」）で、`std::popcount` は C++20 から・符号なしの型だけを受け付ける、と一言添え、[ビット演算](../basics/bit-operations.md#popcount) へリンクするとよい（C5・C6）

### 2（直すとよい）事実（F2）｜§complexity の証明の折りたたみ（L103）

- **問題**：「同じ段で 3 個以上のノードを使ったとすると、それらは区間の中で隣り合って並ぶ」の理由がない。使うノードは一般には隣り合わない（[1, 7) では葉の段で使うのはノード 9 と 14 で、間が空く）ので、読者はこの一文でつまずく
- **根拠**：反例の図そのもの（prod-nodes.svg の葉の段）
- **直し方**：「同じ段で 3 個以上使ったとすると、両端でない 1 個 v を取る。v の兄弟（2k と 2k+1 の相方）は v の左右どちらかの隣で、左右の使ったノードの間にあるので区間にすっぽり入る。よって v の親もすっぽり入り、極大であることに反する」と、真ん中の 1 個で論じる形に直す

### 3（直すとよい）分かりやすさ（U2）｜§operations の prod の説明（L148〜L150）

- **問題**：1 段ごとの操作の理由は書かれているが、ループを抜けたときに答えになる理由（保たれる性質）が書かれていない。自分で書く読者は「l が偶数のときに何もせず上がってよい理由」「l = r で止めてよい理由」を本文から組み立てられない
- **直し方**：「各段の始めに、$s_L \cdot (\text{今の段の } [l, r) \text{ のノードの積}) \cdot s_R$ が求める総積に等しい」という性質を 1 文で書き、偶数の l・奇数でない r はそのまま親に引き継げること、l = r で残りが空になることを添える

### 4（直すとよい）分かりやすさ（U6）｜§operations の追跡（L152）

- **問題**：「図の $[1, 7)$ で追うと」の図は §complexity の prod-nodes.svg で、この節にある図は set-path.svg（set の図）である。節だけを読むと、どの図・どの列の話か分からない
- **直し方**：「列 $(5, 3, 7, 2, 6, 4, 8, 1)$（[なぜ O(log N) か](#complexity) の図）の $[1, 7)$ で追うと」のように、列を書き直して節の中で閉じる

### 5（直すとよい）コード（C3）｜own.cpp の prod（L26〜L31）と本文の記号

- **問題**：本文と擬似コードは $s_L$・$s_R$（`sL`・`sR`）、取り込んだ C++ は `sml`・`smr`（ACL の名前）で、対応が書かれていない
- **直し方**：コード片の変数名を `sL`・`sR` にそろえるか、コメントで「`sml` = $s_L$」と示す

### 6（直すとよい）分かりやすさ（U4）｜§operations の擬似コードの set（L136）

- **問題**：「k ← k / 2 として、k ≥ 1 の間 d[k] ← op(d[2k], d[2k+1]) をくり返す」は、くり返しのたびに k を半分にするのかが読み取りにくい（1 回だけ半分にして同じ k を作り直し続けるとも読める）
- **直し方**：`k ← k / 2` を `while k ≥ 1:` の中に入れる形（`d[k] ← op(...)` → `k ← k / 2`）で書く

### 7（直すとよい）事実（F2）｜§recursive-vs-iterative の表と最後の段落（L196・L198）

- **問題**：「遅延セグメント木…に広げやすい」は再帰型の欄だけにあり、続く文で「遅延伝搬が要るときに再帰型を覚えるとよい」とある。ACL の `lazy_segtree` 自体は非再帰で書かれているので、「遅延セグメント木には再帰型が要る」と読まれるおそれがある
- **根拠**：~/lib/ac-library-master/atcoder/lazysegtree.hpp（`prod`・`apply` は葉側からのループと `push`・`update` で、再帰しない）
- **直し方**：「非再帰でも書ける（ACL の lazy_segtree は非再帰）が、自作するなら再帰型の方が遅延の伝わり方を追いやすい」のように、好みの問題であることが分かる書き方にする

### 8（直すとよい）記法（F7）｜例題 abc157_e の「解法の詳細」2 段落目（L267）

- **問題**：「区間 $[l, r]$ に $c$ があるか」の閉区間に「閉区間」の断りがない（手引き §6）。前の段落では 0-indexed の半開区間に直す話をしているので混ざる
- **直し方**：「閉区間 $[l, r]$（1-indexed）に $c$ があるか」とする

### 9（直すとよい）問題（F5・U7）｜練習 abc461_e の要約（L276）

- **問題**：「白いマス目の行を黒く塗る操作と…」は「白いマス目」が初期状態を言っていると読み取りにくい（「白いマスからなる行」と読める）
- **直し方**：台帳への提案の summary を「最初はすべて白い N×N のマス目で、行を黒く塗る操作と列を白く塗る操作のたびに、黒いマスの数を答える。」のように直す（本文の行は fix_problems が作るので、提案として扱う）

### 10（直すとよい）図（G3）｜prod-nodes.svg・set-path.svg

- **問題**：幅 390px に縮めると、ノードの区間（font-size 11）・ノード番号（10）・説明の 2・3 行目（12）がおよそ 6〜7px になり、読みにくい。値（14・太字）は読める
- **確かめた環境**：chrome-headless-shell 146、ライト（SVG の背景は白なのでダークでも同じ）、幅 640px と 390px
- **直し方**：区間とノード番号を 13〜14 に上げる（ノードの幅 60〜64 に「[0, 8)」は収まる）か、説明の行を代替テキストと本文に任せて図の中の文字を減らす

### 11（直すとよい）構成（手引き §13.1）｜`## 使い分け {#choosing}`（L302）

- **問題**：定型の「使い分け」の anchor は §13.1 で `comparison` だが、このページは骨格の sections の `choosing` を使い、sections にも載っている。執筆者も報告で挙げている
