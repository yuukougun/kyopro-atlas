b2（青 46）・b3（黄 35）の提案のまとめ（`summary/style.md`）への判断。手引きには §15 として足す（§13・§14 と食い違えば §15 を優先）。

## 食い違いの決定（summary/style.md §1）

| 件 | 決定 |
| --- | --- |
| 用語集へのリンク | 用語集にまだない語はリンクせず、本文で短く定義して提案に書く。メインが用語集に足した後でリンクを張る（§13-5 を改める。check_pages の検査はそのまま） |
| 箇条書きの句点 | 文の箇条書きは句点で終える。名詞句だけの列挙（要点の囲みの見出し語、参考・出典の一覧、使い分けの表の代わりの短い列挙）は句点なしでよい。既存のページはそろえ直さない |
| ACL の節 | 骨格の sections に `{#acl}` の中身の節があるページは、その節の中に囲みを置いてよい（§14-4 の例外） |
| 使い分けに近い中身の節 | `which-tool`・`when-to-use` など sections にある中身の節は残す（anchor を変えない）。定型の `{#comparison}` と併存させない |
| Library Checker の練習 | `## 練習問題 {#practice}` の中に「Library Checker」の小見出しを立て、judge.yosupo.jp へのふつうのリンクの箇条書きで置いてよい（問題の囲みは atcoder.jp 専用のまま） |
| ikatakos だけの裏付け | evidence は2つ以上を目標にする。ikatakos.com が落ちているときは web.archive.org の写しを読んでよい（問題文の節は読まない）。GitHub の個人の解説リポジトリも同じ扱い |
| 指示文 | 執筆の指示は level ごとに分ける（基礎の「短く」は基礎だけ）。メインの工程の手順 |

## そのほか

- §2・§5・§9 の事実の注意は、担当が正しさを確かめたものだけを1行ずつ足す。持ち主のページを決めるもの（ゼータ変換を戻せない、オートマトンの終端の継承、mulmod）は、提案どおりの持ち主（zeta-mobius-subset・aho-corasick#inherit-terminal・mod-pow）にする
- §8 図：1枚の SVG の幅は 400 程度までにし、横に並べたいものは2枚に分ける。SVG には viewBox と同じ比の width・height を付ける。値の一覧は数式の1行で書いてよい
- §9：`using namespace std;` の下で std の名前と同じ関数名を作らない。数論のコード片に限り `using u64 = unsigned long long;`・`using u128 = unsigned __int128;` を許す。短い補助の関数のラムダは「など」に入る
- §10：台帳の表示名は変えない（大文字の contest id のまま）。手元の列挙で数えた値は「手元の列挙で数えた値」と添える
- 付録 A・B・prh は提案どおり（付録 B は noai を確かめ直してから）
- checklists：検証で繰り返し出た型（360px での図の文字、確認問題が本文の文をそのまま問う、練習の答えが本文で見える、summary と要点の不一致）を観点に足す
- 既存のページの図の 360px の問題などは、工程10の全体の検証でまとめて見る
