## 指摘

### 1. 直すべき｜事実（F1）｜front matter の complexity、要点の「計算量」、#abc285_g の解法の詳細の最後の箇条

- **問題**：「容量がすべて 1 なら $O((N + M)\sqrt{M})$」と書いているが、この帰着で最大流を流すグラフは、容量がすべて 1 にはならない。$s$-$t$ 流では $t \to s$ に容量の大きい辺を必ず足し、$S \to v$・$v \to T$ の容量は $d(v)$ である。例題の「容量がすべて 1 なので最大流は速い」も同じ誤り。ABC285 G の作り方では、$s$ の $d$ は $-(\text{2 の黒マスの数})$、$t$ の $d$ は $+(\text{2 の白マスの数})$ になり、$s \to T$・$S \to t$ の辺の容量は 1 より大きい。$t \to s$ も大きな容量である
- **根拠**：ACL の document_ja/maxflow.md の $O((n + m)\sqrt{m})$ は「辺の容量がすべて 1 の時」の条件つき。本文の作り方（l.60・l.63）では $t \to s$ の容量が大きいので、この条件は満たされない
- **直し方**：complexity と要点は「最大流を 2 回（Dinic 法で $O(N^2 M)$。返り値の流量を $F$ として $O(F(N + M))$ も上限）」のように、容量 1 の条件の行を外す。代わりに「元の辺の容量が 1 なら、流す量は辺の数ほどで抑えられる」と書くなら、その根拠も書く。例題の最後の箇条は「元の辺の容量はすべて 1 で、判定で流す量 $D$ は 2 のマスの数以下」のように事実だけにし、「速い」の根拠に容量 1 の計算量を使わない（実際に速いことを言うなら $O(F(N + M))$ と $D \le HW$ の見積もりを使う）

### 2. 直すべき｜事実（F2・F5）｜#super-vertex の最小費用流の段落（l.83）、#practice の Minimum Cost b-flow の行（l.110）

- **問題**：「ACL の `mcf_graph` は負のコストを扱えないので、負のコストを含む問題では別の実装が要る」は言い過ぎで、偽である。コストが負の辺は、先に上限 $R$ まで流したことにして、逆向きにコスト $-c$（正）・容量 $R$ の辺を置けば、コストが非負のグラフに直せる。これはこのページの「先に流したことにする」とまったく同じ置き換えで、過不足は $S$・$T$ で調整して `mcf_graph` の `flow(S, T, D)` で求まる。練習の行の「負のコストも入るので ACL の `mcf_graph` だけでは通らない」も、通らない理由の取り違えになっている。Minimum Cost b-flow が `mcf_graph` だけで通らない主な理由は、各辺の流量に加えて双対変数 $p$（ポテンシャル）を出力させること（`mcf_graph` はポテンシャルを返さない）と、答えが $2^{64}$ を超えうることである
- **根拠**：library-checker-problems の min_cost_b_flow/task.md の出力（$z$・$p$・$f$）と注記「the result value may exceed $2^{64}$」。ACL の mincostflow.md の制約 $0 \le \mathrm{cost}$
- **直し方**：l.83 は「`mcf_graph` のコストは非負に限られるので、負のコストの辺は先に上限まで流したことにして逆向きの辺に置き換えてから使う」のように直す（このページの置き換えの応用として 1 文で足りる）。l.110 は理由を「最小コストだけでなく、各辺の流量と双対変数（ポテンシャル）も出力させ、答えが 64 bit に収まらないので、ACL の `mcf_graph` だけでは通らない」に直す。要約は問いの内容だけにし、解き方のヒント（「下限の扱いはこのページの帰着と同じ」）は外してもよい（U7。指摘 4 も参照）

### 3. 直すとよい｜図（G5）・分かりやすさ（U3）｜transform.svg の注記の 1 行目と代替テキスト

- **問題**：「u は L だけ多く出した（不足は T へ）」の「不足は T へ」は、何が不足していて、なぜそれを T へ送るのかが読み取りにくい。本文 l.52 では、送りすぎの頂点は「$-d(v)$ だけ多く受け取らなければならない」とあり、$u \to T$ の辺は「多く受け取る分を $T$ へ流し出す」ためのものである。「不足」を $T$ へ送ると読むと向きが逆に感じられる
- **根拠**：図の 2 行の注記と本文 l.52 の言い方が対応していない（v の側は「S から補う」で本文と合っている）
- **直し方**：注記を「u は L だけ多く出した（その分 L を多く受け取り、T へ流す）」のように、本文の「受け取らなければならない」と同じ向きの言い方にする。代替テキストも同じに直す

### 4. 直すとよい｜分かりやすさ（U6）｜#super-vertex の 1 段落目

- **問題**：節の冒頭で $d(v)$ を説明なしに使う。$d(v)$ の定義は #pre-flow にあり、#super-vertex だけを取り出して読むと「$d(v) > 0$ の頂点」が何か分からない。また #pre-flow の最後の段落（l.56）と図には、次の節で導入する $S$・$T$ が先に出てくる
- **根拠**：clarity.md U6（節の中で定義のない記号）
- **直し方**：#super-vertex の 1 文目に「下限を先に流したことで生じた食い違い $d(v)$（$v$ に入る下限の合計 − 出る下限の合計）を」のように定義を短く添える。l.56 は「後で超頂点からの辺を足すとき」のように、まだ $S$・$T$ が出ていないことに合わせた言い方にするとよい

### 5. 直すとよい｜事実（F2）｜#super-vertex の最後の段落（l.85）

- **問題**：最小の流量の求め方（$t \to s$ の辺の残りの容量をなくし、$t$ から $s$ へ流して打ち消す）は正しいが、結果が負になりうることが書かれていない。直前の自作の要点（l.77）では「求まるのは流量が 0 以上の流れだけ」と書いているので、最小の流量も 0 以上だと読める。実際には、判定が通る（0 以上の流れがある）入力でも、最小の流量は負になりうる。また「打ち消せるだけ打ち消せば」から、答えが「すでに流れた量 − `flow(t, s)` の返り値」であることが読み取りにくい
- **根拠**：検証プログラムの 20 万通りで、この方法の値は全列挙の最小値と一致し、そのうち 6770 通りで負だった。Luzhiled's Library の min_flow の説明も「負になることがある」と明記している
- **直し方**：「判定で $t \to s$ に流れた量を $X$ とし、この辺の残りの容量を 0 にしてから $t$ から $s$ へ流す。返り値を $Y$ とすると、最小の流量は $X - Y$ で、負になることもある（Luzhiled's Library の方法）」のように式と注記を足す

### 6. 直すとよい｜分かりやすさ（U9）｜#super-vertex の自作の要点の 2 つ目（l.75）

- **問題**：「`long long` で $2^{60}$ などにし、`int` の最大値を使って足し算であふれさせない」は、「`int` の最大値を使え」と読める。言いたいのは「`int` の最大値などの小さな値を選ぶと、ほかの容量の合計より小さくなりうる／`int` のまま足すとあふれる」ことだと思われるが、どちらなのかが分からない
- **根拠**：文の構造（「〜にし、〜を使って〜させない」）で、`int` の最大値が推奨と禁止のどちらか定まらない
- **直し方**：「容量は `long long` にし、$t \to s$ の容量は $2^{60}$ などにする。`int` の最大値では、ほかの容量の合計に足りないことがある」のように、何を避けるかを明示する

### 7. 直すとよい｜コード（C2）｜snippets/flow-lower-bounds/usage.yaml

- **問題**：本文 l.77 が述べる「下限のせいで流量が負にしかなれない入力は流せないと判定される」境界の case がない（関数の中のランダムな照合では通っているが、cases として本文の主張と対応していない）
