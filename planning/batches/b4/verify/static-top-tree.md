- cases の期待出力を手で計算し直した：1 頂点（3・0）、星 0→{1,2}（A_1=0 で 1+0·3=1、A_0=5 で 5）、パス 0–1–2（A_2=4 で 2+4=6, 1+6=7。A_1=−1 で −1+4=3, 1+3=4）。すべて一致。軽い子のある形（星）も入っている
- 図の二分木の形：コード片の merge を手でたどった。重いパス 0–1–2–3 の部品の重みは 3（0 と 4・6）・2（1 と 5）・1・1、全体 7。最初の分割は u=7>3 で 0 が左、残りが右。右は u=4>2 で 1 が左、2・3 が右。圧縮(0, 圧縮(1, 圧縮(2, 3)))、0 の下は 4・6 の辺の併合、1 の下は 5 の辺だけ（併合なし）で、stt.svg と一致。tree.svg の重い子も部分木サイズ（1 の部分木 4 > 1）と合う
- merge の分け方の性質：u は単調に減り、一度 u ≤ s になると以後ずっと c に入る（u_{i+1} ≤ −s_i < s_{i+1}）ので b・c は連続で、2 要素以上なら両方とも空でない（無限再帰しない）
- 「重み w の部品は重み W の列の中で深さがおよそ log2(W/w)」：作業用の場所の Python（scratchpad/v-static-top-tree/seq.py）で、乱数・2 冪・1 つだけ巨大・昇順の重みの列 20000 個について merge と同じ分け方の深さを調べた。深さ − log2(W/w) の最大は 2.59 で、「およそ log2(W/w)＋定数」は成り立つ
- 打ち消し合い（本文 100 行目）：パスの列（重み W）→部品（w）→束の列（w−1）→辺（w'）→パスの列（w'）…で log2 の和は log2 N 以下。正しい
- 節点の数 O(N)：頂点の節点 N、圧縮は重い辺の数、辺を付けるは軽い辺の数、併合は軽い辺の数以下。blue_jam 氏の記事の数え方とも合う
- 構築 O(N log N)：各列の merge は分割の深さごとに列を走査するので、走査の総量は節点ごとの列の中の深さの和 ≤ 節点の深さの和 = O(N log N)。上界として正しい（ei1333 氏の Luzhiled's Library のページは構築を O(n) と書く）
- 更新 O(log N)：calc が O(1) で、根までの節点の数は高さ O(log N)。HL 分解の方法の O(log^2 N) も正しい
- 表の値：圧縮 (a1 a2, a1 b2 + b1)、頂点を付ける (束の積, A_v)、葉 (0, A_v)、辺を付けるは定数 b を束の値にする。コード片の calc の 5 つの case と一致
- HL 分解の向き：docs/dp/dynamic-dp.md#on-trees は f(v) = M_v ⊗ f(h) で浅い方が左の積。本文の「浅い方が左」と同じ向き

## 指摘

### 1. 直すべき｜分かりやすさ（U7）・事実（F5）｜#heavy-path-dp の最後の段落（71 行目）

- **根拠**：clarity.md U7 のよくある失敗「本文…が練習の問題を指して、その解き方を折りたたみの外で書いてしまう」
- **直し方**：本文から「（[練習問題](#practice)の ABC311 Ex）」を外す（手法の説明は残してよい。問題との結び付きは練習の方針の折りたたみにすでにある）。あわせて、執筆者の提案どおり abc311_h をこのページの練習から tree-dp-square などへ移すかをメインで決めると、この結び付き自体がなくなる

### 2. 直すとよい｜事実（F3）・分かりやすさ（U3）｜71 行目と練習の方針（174 行目）の食い違い

- **問題**：71 行目は「重い子へは親の DP の配列をそのまま渡し、軽い子では配列を作り直して再帰する」、練習の方針は「軽い子へは…2 通りで 2 回再帰」と書く。KK_lang 氏の記事では、軽い子にも親の配列を初期値として（色ごとに 2 通り）渡しており、「作り直す」のは各頂点の答えを求めるため 0 から始める呼び出しのほうである。71 行目の言い方では、なぜ 3T(n/2) になるかが読めない
- **根拠**：https://www.luogu.com.cn/article/1s1aiccu の解き方と計算量の節
- **直し方**：71 行目を「親の DP の配列を子の再帰へそのまま渡し、渡し方が 1 通りで済む重い子へは 1 回、軽い子へは必要な通り数だけ再帰する」のように、重い子と軽い子の違いを「再帰の回数」で書く

- **問題**：コード片の組み立て方の見積もりとしては正しいが、手法そのものの構築は O(N) にできる。読者が「Static Top Tree の構築は O(N log N) かかる」と受け取りうる
- **根拠**：Luzhiled's Library のページは構築を O(n) と書く。maspy 氏の記事も yosupo 氏の解説の線形時間の作り方に触れる。コード片の O(N log N) は上の「実行して確かめたこと」のとおり正しい
- **直し方**：本文の平衡の段落か自作の節に「このページのコード片の組み立ては O(N log N)。工夫すれば O(N) で組める（Luzhiled's Library）」と 1 文足す。complexity は「構築 O(N log N)（工夫すれば O(N)）」とするか、そのままにして本文で補う

### 7. 直すとよい｜事実（F2）｜#compress-rake の平衡の段落（100 行目）

- **問題**：「通る列の数は軽い辺の数と同じ」。実際は軽い辺 1 本ごとにパスの列と束の列を 1 つずつ通るので、列の数は軽い辺の数の 2 倍＋1 である（O(log N) の結論は変わらない）
- **根拠**：コード片の compress → add_vertex → rake → add_edge → compress の呼び出しの並び
- **直し方**：「通る列の数は軽い辺の数のおよそ 2 倍で O(log N) なので」とする

### 8. 直すとよい｜分かりやすさ（U3）｜#compress-rake のパスの部品の説明（79 行目）

- **問題**：「上端の頂点と、下端の頂点の重い子の位置に「穴」が 1 つある」は、上端にも穴があるように読める
- **直し方**：「上端の頂点で上につながり、下端の頂点の重い子の位置に「穴」が 1 つある」とする

### 9. 直すとよい｜分かりやすさ（U6）｜#compress-rake の「上の例」（79・80・84 行目）・「HL 分解の方法の手順 3」（102 行目）

### 10. 直すとよい｜コード（C4）｜自作の節の取り込み（build 63 行・dp 36 行）

- **問題**：取り込みが合わせて約 100 行で、実装のほぼ全体になっている。手引き §9「載せるのは要点の数行と処理の流れ」、発展の概要は「実装の流れは資料に任せる」（§4）。ただし dynamic-tree（54＋42 行）にも同程度の前例がある

### 11. 直すとよい｜コード（C5）｜stt.cpp の HashDP::set・StaticTopTree::merge

- **問題**：`using namespace std;` の下で std の名前（std::set・std::merge）と同じ名前のメンバ関数を作っている。メンバなので曖昧さのエラーにはならない（g++-15 で警告なし）が、手引き §9 の「std の名前と同じ関数名を作らない」の趣旨には触れる
- **直し方**：`set` を `update`、`merge` を `build_balanced` などにする（本文の「更新では…」の説明はそのままでよい）
