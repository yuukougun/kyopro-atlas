## 指摘

### 1｜直すべき｜C3・F2（コードと本文の一致）｜library の節「保つ性質」の 3 つ目（本文 119 行）と snippet 11 行のコメント

- **問題**：本文は反転の保留を「自分には反映済みで、子にはまだ配っていない」作用と説明し、snippet の `rev` のコメントも同じだが、snippet の `push` は `rev[x]` が立っているときに **x 自身の左右の子を入れ替える**（29 行 `swap(ch[x][0], ch[x][1])`）。つまりコードでは、印のある頂点は自分の子の並びもまだ入れ替えていない（「自分にもまだ反映していない」流儀）。説明とコードの流儀が逆になっている。
- **根拠**：snippet 28〜33 行と 80 行（evert は `rev[x] ^= 1` の直後に `push(x)` を呼んで、初めて x の子を入れ替える）。ei1333 の記事の toggle は印を立てるときに左右を入れ替える「反映済み」の流儀で、本文の説明はこちらに合っている。和は左右を入れ替えても変わらないので今の snippet は正しく動くが、本文が勧める Dynamic Tree Vertex Set Path Composite（1 次関数の合成）へ広げるとき、本文 137 行の「逆向きに合成した値を持ち、反転のときに入れ替える」を読んだ人が、合成値の入れ替えを push の `swap(ch…)` の隣に書くと、印のある子の合成値が向きの違うまま親の pull に使われて答えが壊れる。
- **直し方**：次のどちらか。(a) snippet を「反映済み」の流儀に直す：`toggle(x)` を作り、印を立てるときに `swap(ch[x][0], ch[x][1])`（非可換なら合成値の入れ替えも）を行い、push は子の toggle だけにする。evert は `toggle(x)` だけでよい。本文はそのまま。(b) コードはそのままにして、本文 119 行とコメントを「x の左右の入れ替えは push のときに行う。集約値は和なので入れ替えの影響を受けない」と正しく書き、137 行に「非可換な演算では、合成値の入れ替えは印を立てるとき（子へ印を渡すとき）に行う」と添える。読み手が拡張しやすいのは (a)。

### 2｜直すとよい｜U3・F6（前提）｜link-cut の節と library の節

- **問題**：splay 木を説明もリンクもなしに使っている。前提の balanced-bst は treap の split・merge が中心で、splay 木は「ならし O(log N) の仲間」として名前が出るだけ。取り込んだコードの `rotate`・`splay`（zig-zig・zig-zag）は、読者が初めて見る回転の操作になる。
- **根拠**：docs/ds/balanced-bst.md 100 行（splay の言及はこの 1 文だけ）。用語集にも splay はない。
- **直し方**：link-cut の節の最初の splay 木の出現に「splay 木は、触れた頂点を回転で根まで持ち上げる平衡二分探索木で、各操作がならし O(log N) になる」程度の 1 文を足す。library の節の取り込みの前に「rotate は親子を入れ替える回転、splay は x を根まで回転で上げる」の 1 文を足す。

### 4｜直すとよい｜F2（言い過ぎ）｜add-only の節の表の最後の行（本文 107 行）

- **問題**：「辺の削除もあり、パスや部分木の値を問う。または先読みできない → 動的木」。1 つ上の行（オフライン動的連結性）は一般のグラフの話なので、この行も一般のグラフと読める。一般のグラフで先読みできない動的連結性は、LCT や ETT だけでは解けない（ETT を部品にした Holm らの方法などが要る。本文 86 行も「部品として」と書いている）。
- **根拠**：森でない一般のグラフでは、辺を削除しても別の経路で連結のままでありうる。LCT・ETT は森しか持てない。
- **直し方**：「森で、辺の削除もあり、パスや部分木の値を問う。または森で先読みできない」のように「森で」を入れる。または一般のグラフのオンラインは範囲外と 1 文添える。

### 5｜直すとよい｜F2・U4（あいまいさ）｜ett-top-tree の節の cut（本文 84 行）

- **問題**：「u→v と v→u の位置で列を切り、その間（v の側の木）を取り出して」。列の中で v→u が u→v より前にある場合（u が v の子の側にあるとき）は、その間が u の側の木になる。
- **根拠**：列が根 r から始まるとき、間にあるのは r から遠い側の木。例：0-1-2 の木を 0 から回ると [0, 0→1, 1, 1→2, 2, 2→1, 1→0] で、cut(2, 1)（u = 2・v = 1）の「間」は 1→2 から 2→1 で、v = 1 の側ではなく u = 2 の側になる。
- **直し方**：「2 つの位置で列を 3 つに切り、真ん中（今の根から見て遠い側の木）を取り出して、残りの前後をつなぐ」とする。

### 6｜直すとよい｜F1（計算量の条件）｜link-cut の節の「なぜ速いか」（本文 74 行）

- **問題**：「ほかの平衡二分探索木を使うと…全体は $O(\log^2 N)$ になる」の「全体」に、ならしの条件がない。付け替えの回数がならしで O(log N) なので、ここもならしになる。
- **直し方**：「expose 1 回はならし $O(\log^2 N)$ になる」とする。

### 7｜直すとよい｜F7・U3（記号の定義）｜要点と library の節（本文 32・138 行）

## 執筆者の未解決の点について

- **abc350_g の LCT による解き方**（練習の方針）：正しい。森では、2 頂点に共通の隣接頂点があることと距離がちょうど 2 であることが同値で、あれば 1 つしかない（2 つあると閉路ができる）。evert(u)・expose(v) で取り出したパスの頂点数が 3 なら真ん中がそれで、同じ木にないか頂点数が 3 でなければ 0。頂点数の集約と、真ん中の頂点を splay 木から探す処理が要るが、方針として飛躍はない。マージテクの 3 通り（親が同じ・u の祖父が v・v の祖父が u）と $O(N \log N + Q)$ も drken の記事の解き方と一致した。台帳の approach の直しは執筆者の提案に賛成（第三者の解説での裏付けがないので「想定外の別解」と注記する案がよい）。
- **expose のならし O(log N) と、ほかの木での $O(\log^2 N)$**：Sleator–Tarjan の結果として知られており、ei1333 の記事もならし O(log N) と明記する。evert を挟んでも、反転するのは根から v のパスだけで、重い・軽いの状態が変わる辺の寄与は O(log N) に収まるので主張は保たれる。本文は証明を資料に任せていて、言い過ぎはない（条件の抜けは指摘 6）。
- **Top Tree で直径や最も遠い頂点を保てる**：Top Tree のクラスタに端点 2 つからの最遠距離などを持たせれば compress・rake で併合でき、よく知られた使い方である。問題なし。
- **動く図なし**：catalog（planning/catalog/tree.yaml 697 行）の visual は null。静的な図 2 枚で G7 は満たす。
