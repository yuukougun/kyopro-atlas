## 指摘

### 1. 直すべき｜事実（F2）｜導入の 2 段落目「ABC では difficulty 2400 を超える G に限られる。」

- **問題**：言い過ぎである。台帳には木の上の版の ABC368 D「Minimum Steiner Tree」（diff 816、steiner-subtree の例題）があり、題名に「Steiner Tree」とある ABC の問題が 2400 を超える G に限られるわけではない。一般のグラフで DP が要る問題に話を絞っても、「限られる」は台帳の 2 問から言える範囲を超える
- **根拠**：data/problems.yaml の abc368_d（title: Minimum Steiner Tree、difficulty 816）。本文の #on-tree も「問題文に「シュタイナー木」とあっても、グラフが木なら」と書いており、導入の断定と合わない
- **直し方**：「一般のグラフでこの DP が要る ABC の問題は、これまで difficulty 2400 を超える G だけである。」のように対象と範囲を限る。木なら易しい版が D にも出ることを #on-tree へのリンクで添えるとなおよい

### 2. 直すとよい｜分かりやすさ（U3）・事実（F2）｜#dijkstra-step の 1 文目「残りは S と u をつなぐ木になる」

- **問題**：$v$ が $S$ の指定頂点のとき、辺 $(v, u)$ を除いた残りは $v$ を含まないので $S$ をつながず、$S \setminus \{v\}$ と $u$ をつなぐ木になる。#merge の最後の文がこの場合を分ける遷移に回しているが、#dijkstra-step だけを読むと（U6）一般の主張に見える。遷移 $\mathrm{dp}[S][u] + w$ が上界として正しいこと（DP の値そのもの）は変わらない
- **根拠**：本文の場合分けと、根 $v = t_i$・次数 1 の木での数え上げ
- **直し方**：「$v$ が $S$ に含まれない場合、」と条件を付け、「$v$ が指定頂点なら[分ける遷移](#merge)で $T = \{v\}$ として扱う」と一言添える

### 3. 直すとよい｜分かりやすさ（U3）｜#library の「DP の表の大きさ」

- **問題**：「$4 \times 10^8$ 個で、`long long` では足りない」は、`long long` の値の範囲が足りない（あふれる）とも読める。言いたいのはメモリが足りないこと
- **根拠**：$4.1 \times 10^8 \times 8$ バイト ≈ 3.3 GB
- **直し方**：「`long long` で約 3.3 GB になり、メモリ制限（1024 MB など）に収まらない」と書く

### 4. 直すとよい｜図（G5）｜transitions.svg の左

- **問題**：T 側と S∖T 側の楕円が真ん中で重なっていて、2 つの木が頂点を共有しているように見える。本文は「$v$ だけを共有する 2 つの木」と言う。また $v$ がどちらの楕円の外にも描かれていて、$v$ が両方の木に含まれることが図から読みにくい
- **根拠**：render_svg.py の 360px・720px の PNG で、楕円の重なりが目立つ
- **直し方**：楕円を重ならないように離し（例：cx を 55 と 145、rx を 40）、各楕円の上端を $v$ まで伸ばすか、「v は両方に入る」と注記する

### 5. 直すとよい｜分かりやすさ（U2）｜#examples の解法の詳細と、#dijkstra-step の見積もり

- **問題**：#dijkstra-step の「$K = 10$、$N = 4000$、$M = 8000$ なら」は ABC364 G を念頭に置いた数に見えるが、例題では DP の指定頂点は $K - 1$ 個である。見積もりの $K$ が「指定頂点の数」なのか「問題の K」なのか、読者が例題と結び付けるときに迷う
- **根拠**：本文の解法の詳細「指定頂点は $K - 1$ 個なので、状態は $2^{K-1} \times N$ 個」
- **直し方**：見積もりは仮定の形のままで、「指定頂点が 10 個、…なら」と言い換える。問題の制約には触れない

### 6. 直すとよい｜事実（F9）｜#resources の 1 項目目「空集合の初期値を置いて実装を簡単にする工夫もある」

- **問題**：ikatakos 氏の解法の節の文章には空集合の初期値の説明はなく、載っているコードで全頂点の空集合の値を 0 にしているだけである
- **根拠**：ikatakos 氏 ABC364 の記録の G の解法の節（文章は DP[{t}][t] = 0 だけ）
- **直し方**：「載っているコードは空集合の値を 0 に置いて実装を簡単にしている」と、コードの工夫であることを書く

### 7. 直すとよい｜コード（C5）｜snippets/steiner-tree/steiner.cpp の restore と connects

- **問題**：(a) 取り込みの restore の `es[id].u ^ es[id].v ^ v`（辺のもう一方の端点）は、レート 1000 前後の読者には説明がないと分かりにくい。(b) 取り込みの外だが、connects のラムダの名前 `find` は `using namespace std;` の下で std::find と同じ名前（手引き §15-9。ラムダの変数なので衝突はしない）
- **根拠**：手引き §9・§15-9
- **直し方**：(a) 行の末尾に「// 辺のもう一方の端点」と注を付ける。(b) `root` などに改める

### 8. 直すとよい｜事実（F10）・分かりやすさ（U1）｜要点と summary（提案として）

- **問題**：summary の計算量 $O(3^K N + 2^K M \log N)$ と complexity の $O(3^K N + 2^K (N + M) \log N)$ が字面で違う（連結なら同じなので誤りではない）。また summary・要点の「端点の集合」は、本文の「指定頂点の集合」と語が違う
- **根拠**：front matter と本文 #state
- **直し方**：本文は直さなくてよい。メインへの提案として、summary の計算量を $(N + M)$ にそろえ、「端点の集合」を「指定頂点の集合」にすることを報告に書く
