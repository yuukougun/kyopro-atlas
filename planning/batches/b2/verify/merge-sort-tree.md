## 指摘

### 1. 直すべき｜図（G3）｜tree.svg のノードの区間のラベル

- 根拠：render_svg.py の tree-360.png を拡大して確かめた。[0, 2)・[2, 4) などがつぶれて判読できない（720px では読める）
- 直し方：区間のラベルを 14〜16 程度に、列の数字を 18〜20 程度に上げる。横幅は葉 8 個で決まるので、ノードの箱の間の余白を詰めるか、ラベルを箱の上辺の外（線の脇）に出して箱を低くし、viewBox の幅を 600 前後にすると縮みが小さくなる。説明の 2 行も 18 程度にする

### 2. 直すとよい｜分かりやすさ（U4）・事実（F2）｜各段に BIT を持たせる {#bit-per-level}

- 問題：(a) 枠を位置の順に葉に並べると、同じ位置 i に枠が何個もある（初めの値と更新で入る値）。そのため「区間をノードに分けるところまでは同じ」ではなく、位置の区間 [l, r) を、先に枠の区間（位置が l 以上の最初の枠から、r 以上の最初の枠の手前まで）に二分探索で直す手順が要る。本文にないので、読者はここで実装が止まる。(b) 「BIT を 1 本持つ。1（和を取るなら値）を立て」とあるが、この節のクエリは個数と和の両方で、力試しの方針も「個数と和を数える」。両方なら各段に 2 本要る（kmjp 氏の実装も num と sum の 2 本）。(c) 入れ替えた形（値の順を葉）で、ノードの中の「位置が [l, r) にある今いる要素」を数える方法（ノードの列は位置の順なので、l と r を二分探索して枠の範囲を出し、その段の BIT で範囲の和を取る）が書かれていない（執筆者の未解決 3）
- 根拠：本文の手順どおりに擬似コードを書こうとすると、(a) の変換と (c) の数え方で止まる。kmjp 氏の記事のコードは (c) を二分探索と BIT の区間和で行う
- 直し方：クエリの項に「枠は位置の順に並ぶので、位置の区間 [l, r) を二分探索で枠の区間に直してから、セグメント木と同じくノードに分ける」の 1 文を足す。BIT の項を「個数を数える BIT（今いる枠に 1）と、和を取る BIT（今いる枠に値）を各段に 1 本ずつ」とする。入れ替えの段落に「ノードの中では、位置の順の列で l と r を二分探索して枠の範囲を出し、その段の BIT で範囲の和を取る」の 1 文を足す

### 3. 直すとよい｜事実（F1・F3）｜クエリの手順の計算量の段落と、build の「計算量とメモリ」

- 問題：(a) 「1〜2 秒で終わる目安」は見積もりで、実測では 0.43 秒だった。(b) メモリの「合わせて約 61 MB」は値と累積和の中身だけで、このページのコード片（ノードごとの `vector` を 2 本）は実測で約 109 MB 使う。管理の領域の話は落とし穴にあるが、build の節だけを読むと 61 MB で済むと受け取れる
- 根拠：N = Q = 2×10^5、値 1〜10^9 の乱数で、core の範囲をそのまま使って計測（/usr/bin/time -v、-O2）：0.43 秒、Maximum resident set size 108708 kB。2 × 524288 本の vector の管理の領域（各 24 バイト）と確保ごとの余分で約 45 MB 増える
- 直し方：(a) 「手元の計測（N = Q = 2×10^5）では 0.4 秒ほどである」と実測に置き換える。(b) 「約 61 MB である。ノードごとに vector を持つと管理の領域が加わり、実測で 100 MB ほどになる（[落とし穴](#pitfalls)）」とする。制限 1024 MB の AtCoder では十分収まることも添えるとよい

### 4. 直すとよい｜分かりやすさ（U3）｜力試し {#challenge} と「各段に BIT を持たせる」の並び

- 問題：力試しの方針が、まだ読んでいない後ろの節（各段に BIT を持たせる）の形と言い回し（「値の順を葉にした木」「各段の BIT」「今いる要素」）に頼っている。上から読む読者は、力試しの時点で意味が分からない
- 根拠：本文の並びが 例題 → 力試し → 各段に BIT（発展）→ 確認問題。§4 の目安では処理の流れの節が例題より前
- 直し方：「各段に BIT を持たせる」の節を落とし穴の前か、例題の前に移す（sections の並びもそろえる。§14-11 で入れ替えてよい）。動かさないなら、力試しの方針の冒頭に「（下の[各段に BIT を持たせる](#bit-per-level)を先に読む）」と添える

### 5. 直すとよい｜事実（F1）｜確認問題「クエリを先に全部読めるなら…」

- 問題：「全体 $O((N + Q) \log (N + Q))$ でメモリも $O(N)$」とあるが、クエリを全部読んで並べ替えるので、メモリは $O(N + Q)$ である
- 根拠：オフラインの処理はクエリ $Q$ 個を保持してソートする
- 直し方：「メモリも $O(N + Q)$ で済む」とする（$O(N \log N)$ との対比は保てる）

### 6. 直すとよい｜コード（C3）｜応用の型の「区間の K 番目」と kth の範囲

- 問題：本文は「x 以下が K 個以上になる最小の x」（K は 1 始まり）、取り込むコードは k が 0-indexed で `>= k + 1` と比べる。コードの注釈に書いてあるので誤りではないが、本文の文だけを読むと K と k の対応が分からない
- 根拠：kth の範囲の 1 行目の注釈「k 番目（0-indexed）」と本文の「K 番目に小さい値」
- 直し方：本文に「コードでは k を 0 始まりにし、k + 1 個以上を条件にする」の 1 文を足す
