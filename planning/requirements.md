# AtCoder黄色到達教材 要件定義

> このファイルは、教材を制作するClaude CLIセッションへの指示書です。
> 最初に全体を読み、末尾の「制作セッションへの指示」に従って作業を始めてください。
> いきなりページを書き始めず、まず質問から始めること。

最終更新：2026-10-21

---

## 1. 目的と前提

緑上位〜水色手前の学習者が、AtCoderで黄色（レート2000以上）に到達するための、読んで学ぶ網羅的な教材を作る。

- 学習者：AtCoder ID `yuukougun`。2026年10月時点でレート961、直近のパフォーマンスは概ね1100〜1450
- ABCではD問題まで安定、E問題は時々解ける
- 使用言語はC++。基本文法は習得済みだが、解説コードに出る現代的な書き方には不慣れ
- 目標はABC中心。ARC的な考察系は重視しないが、少しは含めてよい
- 段階は「水色 → 青 → 黄色」で考える（黄色はパフォーマンスで安定して2000前後が必要）

## 2. 形式と技術構成

本文はMarkdownで章（ページ）ごとに書き、MkDocs Materialで静的サイトにする。制作はローカルのClaude CLIで、時間をかけて行う。

- リポジトリはGitHubで公開し、GitHub Pagesで公開する（スマホからも読める）
- MkDocs Materialを選ぶ理由：タグ機能による多軸分類、検索、折りたたみ、コードハイライト、数式（KaTeX等）
- ページにJavaScriptを埋め込み、動く図（ステップ送りの可視化など）を置けるようにする
- ページの長さに上限や目安は設けない。難しい分野の解説を長さの都合で削らない
- Claude用の索引ファイル（全ページのタイトル・タグ・扱う内容・ファイルパス・サイトURL）を、各ページのメタデータから自動生成する
- 進捗チェックなどの仕組みを入れる場合、データはブラウザ内（localStorage）だけに保存し、端末間の同期はしない
- 記録用フォルダ（例：`notes/`）は `.gitignore` に入れる
- リポジトリ内の具体的なフォルダ構成は制作セッションで決める

## 3. 扱う範囲と内容の決め方

範囲は細部まで網羅する。章構成と各章に何を書くかは、制作セッションで既存の記事・サイト・書籍の情報などを広く深く調査してから決める。

- アルゴリズムとデータ構造に加え、競技プログラミングに必要な数学の知識（整数論、組合せ、確率・期待値など）も含める
- C++の章を設ける：基本文法は省き、解説コードによく出る現代的・特殊な書き方を扱う（例：`for (const auto& [i, component] : scc.scc() | views::enumerate)` のような構造化束縛、ranges/views、ラムダ、標準ライブラリの便利機能など）
- 実装は原則載せない。意味と処理の理解を優先し、載せるのは要点となる数行や処理の流れ程度。実装力は実戦で積むものとして教材の範囲外とする
- 載せるコード片は、可能な限りコンパイル・実行して正しさを確認する
- 考察系（主客転倒、寄与、不変量、構築など）は少しだけ扱う

## 4. 分類と各ページの構成

分類は一つの軸に縛らず、各ページのメタデータ（タグ）から複数の入口を作る。ページの構成は固定テンプレートを使わず、短い編集方針だけを決めて分野ごとに判断する。

### 分類

- 必須の軸：レベル（水色／青／黄色の3段階）と分野
- 各ページに前提となるページを記載し、知識マップと「次に読むページ」の生成に使う
- それ以外の軸（手法の種類、問題のサインなど）は制作時に判断して追加してよい

### 編集方針（ページ共通の原則）

- 意味の理解を最優先にし、図で伝わるものは図にする（静的な図、Mermaid、SVG、必要に応じて動く図）
- 「なぜそうなるか」を必ず書き、手順の羅列で終わらせない
- 構成要素（導入、使いどころ、計算量、例題、練習問題、確認問題など）の有無と順序は分野ごとに決める
- 全ページ共通で必須なのはメタデータだけ
- 全体を不必要に縛らない。この方針自体も、制作中により良い形が見つかれば見直してよい

## 5. 横断コンテンツ

分野別のページとは別に、章をまたいで知識を引き出すためのページを作る。特に逆引き辞典・知識マップ・戦い方の3つを重視する。

| ページ | 内容 |
| --- | --- |
| 逆引き辞典 | 制約（N≤20、N≤2×10⁵、N≤10¹⁸など）や問題の言い回し（最小値の最大化、区間一括更新など）から、疑うべき手法と該当ページへ |
| 似た手法の使い分け | BFS／01-BFS／ダイクストラ、BIT／セグ木／Sparse Tableなど、混同しやすいものの比較と選び方 |
| 知識マップ | 全ページの前提関係をグラフで表示し、クリックで各ページへ。メタデータから自動生成 |
| 色別ロードマップ | 色段階ごとの推奨ルート |
| 早見表 | 計算量の目安、STL操作の計算量、modの性質、よく使う公式など。各ページへリンク |
| コンテストの戦い方 | 時間配分、詰まったときの手順、WA・TLEの原因チェックリスト、ストレステスト |
| 精進の仕方 | 解説の読み方、upsolveの方法、解説を読んでも分からないときの対処 |
| 用語集 | 用語の短い定義。本文から用語へリンク |

使い分けページと早見表は、本文を作りながら育てていけばよい。

## 6. 問題の扱い

例題・練習問題はAtCoderの過去問などから選び、問題文は転載せずリンクと自分の言葉での要約だけを載せる。

- 主な出典：ABC、ARC、典型90問、EDPCなど
- 難易度の目安としてAtCoder Problemsのdifficultyを参考にする
- 問題番号・リンク・難易度は記憶で書かず、作成時に実在を確認して載せる
- AtCoderのページはAIによる取得を制限する表示があるため、問題ページや公式解説を読み込めるかは制作時に確認する

## 7. 使い続けるための仕組み

教材は「読み通す本」ではなく、ABCで解けなかった問題をきっかけに「引く辞書」として使う。そのために、claude.aiでの解説とローカルのClaude CLIでの記録の2つを用意する。

### 解説（claude.ai＋GitHub連携）

- claude.aiのプロジェクトに教材リポジトリを接続し、教材を参照しながら分からなかった問題を解説してもらう
- 解説の手順はリポジトリ内のファイルとして置き（git追跡対象）、プロジェクトの指示から参照する。教材と一緒にバージョン管理され、同期で最新の手順が反映される
- Claudeはまず索引ファイルで関連ページを探し、必要なページだけを読む
- 想定する流れの例（具体は制作時に決める）：問題（URLかスクリーンショット）と考えた内容を受け取る → 「ヒントだけ」か「解説まで」を選ぶ → 教材の用語に合わせて解説し、該当ページ・節へリンク → 教材にない知識なら明示 → 解けなかった原因（知識不足／気づけなかった／実装ミス／時間不足）を一言
- 頼まれたときだけ、CLIに貼り付けられる「記録用まとめ」を出す
- 教材を更新したら、claude.ai側でGitHubの内容を同期し直す必要がある

### 記録（ローカルのClaude CLIのスキル）

- 記録が必要だと感じたときだけ使う。全問題を記録する必要はない
- 1問1ファイル。記録フォルダはgit追跡外（スキル自体は追跡対象）
- 記録する内容：日付、問題へのリンク、原因の分類、学んだことを一言、関連ページ、教材の改善案（あれば）。ファイル先頭にメタデータとして書く
- 集計機能は持たせない
- 記録はGitHubに上がらないため、claude.ai側の解説からは参照できない（意図どおり）

### その他

- 採用した仕組みは上の2つだけ。進捗の可視化や確認問題は必須ではなく、入れる場合もデータはブラウザ内のみ。AtCoder Problemsとの連携はしない
- 2つのスキルの具体的な中身は制作セッションで決める

## 8. 制作セッションへの指示

制作セッションは、このドキュメントで決めていない事項を自ら判断する。**教材の作成に着手する前に、必ず全体を深く思考すること。** 目的と学習者の現状、教材の使われ方（引く辞書としての使用、claude.aiでの解説との連携）、扱う分野の全体像と相互の関係、規模と作業の分割、品質を保つ方法、起こりうる失敗とその対策までを考え抜く。その結果を設計書として文書に残してから作り始め、いきなりページを書き始めてはいけない。

**ユーザーの認識とずれた判断を避けることを重視する。** 分からない点や解釈が分かれる点は推測で埋めず、選択肢付きの質問形式でユーザーに尋ねる。最初にまとめて質問し、作業の途中でも必要になればその都度質問する。最初の質問には、少なくとも次の点を含める。

- レベルの3段階（水色／青／黄色）に収まらない緑以下の基礎知識を、どう扱うか
- 進捗チェックや確認問題を入れるか
- このドキュメントを読んで、ほかに曖昧だと判断した点

### 制作セッションが判断すること

- 網羅すべき項目の一覧と全体の目次（数学、C++の章を含む）
- 各分野・各ページに適した構成と、図や動く図をどこでどう使うか
- レベル・分野以外の分類軸と、メタデータの具体的な形式
- 各項目のレベル（色段階）の割り当てと、ページ間の前提関係
- 練習問題の選び方と、ページごとの数
- リポジトリのフォルダ構成、MkDocsの設定・プラグイン、数式や図の描画手段
- 索引ファイルの形式と生成方法
- 解説用の手順ファイルと記録用スキルの中身
- 進捗チェックや確認問題など、教材の使い勝手に関わる仕組みの詳細

### 進め方

1. 質問：このドキュメントを読み込み、分からない点・曖昧な点を質問形式でユーザーに確認する
2. 調査：既存の記事・サイト・書籍の情報を分野ごとに広く深く調べ、調査レポートとしてリポジトリ内に残す
3. 設計：調査をもとに上の判断事項を考察し、目次・分類・編集方針・技術構成をまとめた設計書を作る。複数の案を比較し、なぜその案を選んだかを書く
4. 設計の見直し：作成者とは別のサブエージェントが設計書を批判的にレビューし、抜けや偏りを直す
5. 決定の提示：着手する前に、設計で決めた内容を簡潔な一覧にしてユーザーに出力し、確認を得てから先に進む
6. 土台作り：MkDocsの設定、メタデータの形式、索引ファイルの自動生成など
7. 試作：性質の違う分野から数ページを作り、設計を検証・修正する
8. 本制作：残りのページを作る。横断コンテンツは本文と並行して育てる
9. スキル作成：解説用の手順ファイルと記録用スキルを作る
10. 全体の検証：リンク切れ、前提関係の矛盾、用語・記法の不統一、事実の誤りを確認する

### サブエージェントの使い方

教材は非常に大きいため、サブエージェントの使用を必須とする。メインのセッションは全体の設計と一貫性の管理に専念し、調査・執筆・検証をサブエージェントに分担させる。

- 調査：分野ごとにサブエージェントを並列で動かし、結果をファイルにまとめさせる
- 執筆：ページまたは小さな分野の単位で割り当てる。設計書・編集方針・用語集・記法の約束を必ず渡し、ページ間で書き方がぶれないようにする
- 検証：書いたものとは別のサブエージェントが確認する（事実・計算量・問題リンクの実在、コード片のコンパイルと実行、分かりやすさ）。書いた本人に採点させない
- 長期作業の再開：進捗と残り作業をリポジトリ内のファイルに記録し、セッションが途切れても続きから再開できるようにする

### 注意点

- 教材の更新は、まとまった単位で意図を持ってコミットする（細かいコミットを乱立させない）
- 事実（問題番号、計算量、定理など）は確認してから書く
- 他者の記事は参考にしても文章を転載せず、自分の言葉で書く。参考にした資料は出典として残す
