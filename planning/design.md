## 1. 前提の整理

### 1.1 学習者と目標

- レート961、パフォーマンス1100〜1450。ABC は D まで安定、E は時々。目標は黄色（パフォーマンス2000前後を安定して出す）
- 直近81回の ABC（abc400〜abc480）の difficulty（research/00 §2.3）から、教材のレベルと問題位置はおおむね次のように対応する。**水 ≒ E（と易しい F）、青 ≒ F（と難しい E）、黄 ≒ 難しい F と易しい G**
- F の75%は difficulty 2000 未満。したがって黄色への主な条件は「青までの知識を速く確実に使うこと」で、黄の知識は難しい F と G で効く。教材は「水・青を厚く、正確に」を最優先にする
- 最近の傾向：E は数え上げ（二項係数・包除・寄与）と累積和・差分、F は「言い換えてからセグ木（特に遅延セグ木）に載せる」、G は専用の手法（FPS・フロー・行列累乗・Mo など）が多い（research/00 §2.3.8）。この傾向は、最近の ABC のデータ（§5.5）から、ロードマップの「位置ごとの頻出手法」として学習者に見せる（§7。D5）

### 1.2 教材の使われ方と、そこから来る設計の条件

| 使われ方 | 設計の条件 |
| --- | --- |
| ABC で解けなかった問題から引く（辞書） | どのページも冒頭だけで「何ができて、いつ使うか」が分かる。名前・別名・問題のサインのどれからでも引ける（検索・用語の索引・逆引き・索引）。最近の ABC の問題からも引ける。行き止まりを作らない（基礎と発展もページを持つ） |
| 色ごとに順に学ぶ | レベルと前提関係から、ロードマップと知識マップを自動で作る。下位のページにある上位の帯の節も、その色のロードマップに出す（D1）。「次に読む」がたどれる |
| 解説コードの1行が読めない | C++ 章を「書き方から引ける」形にする（C++ の逆引き） |
| claude.ai で解説してもらう | 索引ファイルから関連ページと節を探せる。1ページが単独で読める（断片だけ読まれても意味が通る）。用語と記法が教材全体でそろっている |
| 自作ライブラリを作る | 実装の全体は載せないが、自分で実装できる粒度の処理の流れ（保つ性質・各操作の手順・境界）を書く。ACL の対応と、Library Checker での確かめ方を示す |
| スマホで読む | 表を横に広げすぎない。動く図は指で操作できる。長い証明は折りたたむ |

### 1.3 成功の条件

1. 学習者が解けなかった ABC の E・F を持ってきたとき、関連するページに3クリック以内（または用語の索引・索引の1回の検索）でたどり着ける
2. 各ページが「なぜそうなるか」を説明しており、手順の羅列で終わっていない
3. 事実（計算量・定理・問題番号・difficulty・ACL の API）に誤りがない。問題番号はすべて機械的に実在を確かめ、問題の内容の裏付けは台帳（§5.4）で管理している
4. 用語・記法・文体が全ページでそろっている
5. 制作が途中で止まっても、どこまでできていて次に何をするかがファイルから分かる

## 2. 全体構成

### 2.1 分野（ナビゲーションの章）

ページは1つの分野（`field`）に属し、ナビゲーションの章になる。分野をまたぐ引き方は、手法の種類（`kind`）・レベル・題材・逆引き辞典・用語の索引が受け持つ。

| field | 表示名 | 中身 | おもな出典 |
| --- | --- | --- | --- |
| `start` | はじめに | この教材の使い方、記法と用語の約束、AtCoder の仕組み | 00 |
| `guide` | 横断ページ | 逆引き辞典、用語の索引、使い分け、知識マップ、ロードマップ、早見表、戦い方など（§7） | 00 |
| `basics` | 基本テクニック | 計算量の見積もり、全探索、二分探索、累積和・いもす、尺取り、ソート・座標圧縮、貪欲、半分全列挙、ダブリング、分割統治、周期性、bit 演算 | 01 |
| `thinking` | 考察 | 言い換え・主客転倒・寄与・余事象・偶奇・不変量・構築などの型（少しだけ扱う。入口は `guide` の「詰まったときの発想リスト」） | 01 |
| `dp` | 動的計画法 | DP の考え方、列・区間・集合・桁・木の DP、DP の高速化 | 02 |
| `graph` | グラフ | 探索、最短路、有向グラフ、連結性と全域木、探索木と次数の性質、フロー | 03 |
| `tree` | 木 | 木の性質、直径・LCA・オイラーツアー・マージテク・重心など | 04 |
| `ds` | データ構造 | STL の応用、スタック・キュー、Union-Find、BIT・セグ木、クエリ処理の工夫 | 05 |
| `math` | 整数論・代数 | mod、素数・約数、GCD と合同式、floor、行列・線形代数、畳み込み | 06 |
| `comb` | 数え上げ・確率・ゲーム | 数え方の考え方、二項係数・包除、確率・期待値（期待値 DP を含む）、ゲーム（ゲーム DP を含む） | 07 |
| `string` | 文字列 | ハッシュ、Z・KMP・Manacher、Trie、Suffix Array、Aho-Corasick | 08 |
| `geometry` | 幾何 | ベクトルと外積、誤差、凸包、偏角ソート、45度回転など | 08 |
| `misc` | その他の技法 | インタラクティブ、乱択、bitset による高速化、構文解析 | 08 |
| `patterns` | 題材別 | 括弧列・mex・順列・XOR・区間・グリッド・部分列と部分文字列・約数と倍数など、問題に現れる「対象」から引く案内ページ | 00 |
| `cpp` | C++ | 解説コードに出る書き方、AtCoder と手元の環境、落とし穴、ACL の読み方 | 09 |

並び順は上の表のとおり。`guide` を `start` の次に置くのは、辞書として引く入口（逆引き・地図）を最初に見せるため。

### 2.2 ページの種類（`type`）

| type | 内容 | 分量の性格（上限ではない） |
| --- | --- | --- |
| `technique` | 手法・データ構造・定理。教材の本体 | 制限なし（基礎は短め） |
| `thinking` | 考察の型 | 短い |
| `pattern` | 題材別の案内（よく出る問われ方 → 手法の表） | 短い〜中 |
| `hub` | 入口・比較・地図（写像12相、DP の高速化の入口など）。中身の説明は各ページに任せる（D6） | 表とリンクが本体 |
| `overview` | 発展（2400〜）の概要。何ができるか・どんな問題で使うか・ライブラリでの使い方 | 短い |
| `cpp` | C++ の書き方 | 短い〜中 |
| `guide` | 横断ページ・はじめに（手書き。生成部分を含むものがある） | ページによる |
| `generated` | スクリプトが作るページ（ホーム・分野の入口・レベル別と種類別の一覧） | — |

右の列は分量の性格を示すだけで、上限ではない。難しい内容を長さの都合で削らない（要件 §2。T23）。

### 2.3 規模の見込み

調査の項目は延べ598（重複30を含む）。§4 の規則でまとめた目次の初版（catalog の初版）は **367ページ**だった（technique 257、overview 55、thinking 10、pattern 8、cpp 19、guide・start 18。ほかに生成ページ）。レベル別は基礎93・水90・青58・黄44・発展55・なし27。

工程4の見直しで、同じ手法の重複と黄の薄いページの統合（§4.4）、入口・比較・地図のページの hub への変更（§4.1）、題材別の2ページの追加を行い、目次の第2版は **353ページ**になった（technique 240、overview 51、thinking 10、hub 4、pattern 10、cpp 19、guide・start 19。ほかに生成ページ）。レベル別は基礎100・水79・青52・黄37・発展51・なし34。出題頻度（technique・thinking・overview の301ページ）は A 76・B 153・C 72。問題は延べ1438（異なる問題は1178で、台帳ですべて裏付けを確認済み）、例題は461。動く図の priority 1 は24。発展の概要は1手法1ページのまま続けるが、ABC の問題がない概要が多いので、量を工程5でユーザーに示す。

規模を下げる案（分野ごとの大きなページにまとめて約150ページ）も比べたが、辞書として引くときに目的の節を探す手間が増え、レベルの違う内容が1ページに混ざるので採らない（§13 案の比較 A）。使用量が見込みを超えたときに規模を下げる手段は §10.4 に決めておく。

## 3. レベルと分類

### 3.1 レベル（`level`）

| level | difficulty | 扱い |
| --- | --- | --- |
| 基礎 | 〜1199 | 短いページ。初歩の説明は省き、応用の型・落とし穴・上位の手法とのつながりに絞る |
| 水 | 1200〜1599 | 本格的に扱う |
| 青 | 1600〜1999 | 本格的に扱う |
| 黄 | 2000〜2399 | 本格的に扱う |
| 発展 | 2400〜 | `overview` ページだけ |

割り当ての規則：

1. **その手法を知らないと解けない問題が、まとまって現れ始める帯**にする。易しい例が1問だけ下の帯にあっても下げない。根拠の問題と difficulty を catalog の `level_evidence` に残す
2. difficulty は AtCoder Problems の推定値（`tools/ap.py`。台帳 §5.4 に取得日付きで持つ）。**帯は abc319 以降（7問体制、2023-09 以降）の根拠を主に数え、古い問題は最近の根拠がないときだけ使う**（2019年以前の ABC は同じ手法でも高めに出る。D2）
3. **ACL を呼ぶだけで解ける問題も帯の根拠に数える**。ただし S・F の設計や縮約後の処理など、ACL の外の考察が本体なら数えない（D2）
4. 典型90問など difficulty のない問題は、作問者の★を目安にする（★4＝基礎、★5＝水、★6＝青、★7＝黄）。ABC の問題があればそちらを優先する
5. 1つの手法で易しい使い方と難しい使い方の帯が分かれるとき：中身が多ければページを分け（例：区間 DP と区間 DP の応用）、少なければ1ページの中の節に level を付ける（§3.3 の `sections`。D1）
6. **節の level はページの level 以上にする**。ページより低い内容の節は作らず、下位のページに置いて、上位のページには導線の1行（`related` か本文の参照）だけを残す。**基礎のページの節は青まで**にし、黄・発展の中身は上位のページへ置く（D1）
7. ページの前提に、そのページより高いレベルのページを置かない（検証スクリプトで警告する）。避けられないときは `related` にする
8. `start`・`guide`・`patterns`・`hub`・`generated` はレベルを持たない。`cpp` は「目に入り始める帯」を `level` に入れてよい（D6）

上位の帯の節は、その色のロードマップに「ページ#節」として出る（§7）。「理解した」もページ×レベルで記録する（§9.1）。

### 3.2 分類の軸

| 軸 | キー | 値 | 使い道 |
| --- | --- | --- | --- |
| 分野 | `field` | §2.1 の15個のどれか1つ | ナビゲーション |
| レベル | `level` | §3.1 | バッジ、レベル別一覧、ロードマップ、知識マップの色 |
| 手法の種類 | `kind` | 固定の語彙（catalog/README.md §4。第2版で「計算量」を足した。D15）から1〜3個 | 分野をまたぐ一覧（例：DP の種類に `comb` の期待値 DP も入る）。ページのバッジにも出す |
| 出題頻度 | `frequency` | A（最近の ABC で頻出）／B（時々）／C（まれ）。最近の ABC のデータから機械的に付ける（§5.5。D5） | ロードマップの「必修・準必修・余裕があれば」 |
| 問題のサイン | `signs` | 問題文の言い回し（phrase）・制約の形（constraint）・立てた式の形（shape。D9） | 逆引き辞典 |
| 前提 | `prerequisites`・`related` | ページ id（related は節なら `id#anchor`。D12） | 知識マップ、次に読む、ロードマップの順序 |

Material の tags プラグイン（階層タグ）も比べたが、1ページ1値の軸（レベル・分野）を単一値のキーで持つほうが二重管理がなく、検証もしやすい。一覧ページはスクリプトで生成する（research/10 §3.1.2 の案 K。§13 案の比較 B）。

### 3.3 メタデータ（front matter）

全ページ共通で必須なのはメタデータだけ（要件 §4）。ただし冒頭の要点も全ページに置く（§6.1 の2。工程5で確かめる）。形式は `schema/page.schema.json` で検証する。

```yaml
---
id: lazy-segment-tree          # 一意。ファイル名と同じ。英小文字・数字・ハイフン。8a 以降は変えない
title: 遅延セグメント木
nav_title:                     # 題名が長いときだけ、ナビゲーション用の短い名前（D11）
aliases: [遅延セグ木, Lazy Segment Tree, lazy segtree]
type: technique
field: ds
chapter: 区間クエリ            # 分野の中の章（ナビゲーションの小見出し。T14）
order: 120                     # 分野の中の並び順（10刻み。8a 以降の nav はこれと chapter から作る。D18）
level: 水
kind: [データ構造, 区間クエリ]
prerequisites: [segment-tree]                    # 直接の前提だけ（知識マップの辺）
related: [lazy-segment-tree-patterns, imos, range-set-management#merge-intervals]   # あると良い関連。節は id#anchor
summary: 区間への一括更新と区間の集約（和・最小など）を、どちらも O(log N) で行う。
complexity: 構築 O(N)、更新・取得 O(log N)
signs:
  - {type: phrase, text: 区間に一括で加算・代入し、区間の和や最小値を何度も答える}
  - {type: constraint, text: "N, Q ≤ 2×10^5 で区間の更新と区間の質問が交互に来る"}
acl: [lazy_segtree]
verify: [range_affine_range_sum]   # Library Checker の問題名（自作ライブラリ用。任意。D14）
frequency: A
sections:                          # 主な節（D1）。level を省くとページと同じ
  - {title: 区間の長さを S に持たせる, anchor: size-in-node}
  - {title: 保つ性質と push の手順（自作するとき）, anchor: invariants, level: 青}
stage: draft                       # stub / draft / reviewed / done（T1）
updated: 2026-10-21
---
```

- 制作の段階は `status` ではなく `stage` に持つ。`status` は Material の予約キーで、書くとナビゲーションに印が出る（T1）。`stage` が stub のページには、テンプレートで「準備中」の印を出す（T13）
- `cpp` のページは、`cpp_std`（17・20・23）、`gcc_min`（13・14・15）、`atcoder`（AtCoder で使えるか）を足す（research/09 §7.3）。`gcc_min` は g++-13 と g++-15 で確かめる（§8.6）
- `sections` は工程8a で catalog から写す。本文の見出しに `{#anchor}` を付けてリンクの行き先にし、分野ごとの詳細索引（§8.3）にも載せる。節の level の規則は §3.1 の5・6（D1）
- 例題・練習問題の ID は front matter に重ねて書かない。本文の一覧（§6.6）からスクリプトが拾い、台帳（§5.4）と照らす（二重管理を避ける）
- `summary`：1文目は何ができるか（いつ使うか）。2文・120字以内。「このページ」「ここ」「まとめる」「扱う」「紹介する」と、帯の名前（水・青など）を使わない。索引・一覧・知識マップのツールチップで単独で読まれるので、単独で意味が通るように書く（D10）
- `complexity` などの新しい事実は、骨格（8a）では入れず、8b の執筆と検証で入れる（T13）

## 4. ページの粒度と分野間の境界

### 4.1 粒度の規則

1. **1ページ＝名前で引かれ、独自の「なぜ」を持つ1つの単位**。その変種・応用は節にし、節には見出しのアンカーを付けて直接リンクできるようにする
2. **難度帯がはっきり分かれる型は、基本と応用を別ページにする**（研究の提案どおり）：セグ木は「基本（水）／遅延セグメント木（水）／モノイドの設計（青）／セグ木上の二分探索（水。§4.3）／載せ方の型（青）」の5ページ、区間 DP・桁 DP は基本と応用、bitDP は「bitDP（水）／3^N（青）／プロファイル DP（黄）」
3. **基礎の小さな項目は、引かれる名前が違えば別ページ、同じ考え方の変種なら節**（例：いもす法と2次元いもすは1ページ、bit 全探索と順列全探索は1ページ。差分は、基礎の部分をいもす法のページに置き、黄の「差分列への言い換え」を別ページにする）
4. **発展は1手法1ページの短い概要**（ユーザーの回答どおり）。ただし同じ系統で単独では薄すぎるもの（Monge の系統、文字列の発展手法など）は1枚にまとめ、節ごとにアンカーを付ける。発展の概要は話題の章に置く（§5.1）。ABC の問題がない概要が多いので、量は工程5でユーザーに示す
5. **C++ 章は約15〜20ページ**にし、4〜5章に分ける（D13）。書き方1つずつにアンカーを付け、「C++ の逆引き」（書き方 → ページ#節。手書きの表）を入口にする。研究の案 A（36ページ）は1ページが薄くなりすぎ、案 B（11ページ）は1ページが長くなりすぎるので中間を取る（§13 案の比較 F）
6. **幾何は ABC での出題が少ないので、統合を優先して8ページ前後**にする
7. **考察（`thinking`）は短いページと節で少しだけ扱う**（research/01 §7.3）。入口は横断の「詰まったときの発想リスト」（`guide`）1つにし、「問題の形 → 試す型」の表もそこに置く。observation-hub は入口をやめ、小さな型（対称性・鳩の巣原理・場合分け）のページにする（D7）。要件の「少しだけ」に合わせ、各ページは「その型が使える合図・最小の例・ABC の例題2〜4問」に絞り、証明の技法は体系的に教えない
8. **題材別（`patterns`）は10ページ前後**：括弧列、mex、順列（置換）、XOR、区間、グリッド、K 番目と中央値、操作列（クエリ・逆順処理）、部分列と部分文字列、約数と倍数（後の2つは D16 で足した）。各ページは「その題材でよく出る問われ方 → 使う手法」の表を中心にした案内で、手法の説明は各ページに任せる。問題は表の行の代表のリンクだけにする（§5.3）
9. **入口・比較・地図のページは type `hub`** にする（D6）。中身の説明は各ページに任せ、表とリンクを本体にする。level と frequency は持たず、問題は0〜3で例題なしでよい。候補は写像12相・DP の高速化の入口・グラフへの帰着・発展のデータ構造の一覧。最短路の使い分けは hub にせず、横断の「似た手法の使い分け」に吸収する

## 5. 目次（catalog）の作り方

### 5.1 形式と書き方の規則

- `planning/catalog/<field>.yaml` に、その分野の全ページを並べる。並び順がナビゲーションの順になる
- 1ページの項目：`id`・`chapter`（分野の中の章。ナビゲーションの小見出し）・`title`・`nav_title`・`aliases`・`type`・`level`・`level_evidence`・`kind`・`prerequisites`・`related`・`summary`・`signs`・`acl`・`verify`・`frequency`（付け直すときに `frequency_evidence`）・`sections`（`{title, anchor, level}` の列）・`merged_keys`（統合した調査の key）・`visual`（`{kind, priority, text}`）・`problems`（`{id, role, summary, approach, representative}` の列）・`problems_note`・`sources`（執筆時に読むべき調査レポートの節）。ファイルごとに `moved`・`dropped`・`open_issues`
- 詳しい形式・規則と `kind` の語彙は [catalog/README.md](catalog/README.md)（第2版）

書き方の規則の要点：

- **id**（D11）：英小文字・数字・ハイフン。原則は調査の key で、統合したページは主な key を id にする。統合した key・消えたページの id・変える前の id は `merged_keys` に入れる。`segtree-` は `segment-tree-` にそろえる。8a 以降は変えない（§10.3）
- **題名と別名**（D11）：正式名は「セグメント木」（本文と補足では「セグ木」も可）。数の K は大文字。人名の連結は ASCII のハイフン（Aho-Corasick・Sprague-Grundy）。半角英数字と全角文字の間に空白を入れる（「2 次元累積和」「K 番目」）。長いかっこの補足は付けず、別名・summary に回す（ナビゲーションで長いなら `nav_title`）。英語の定まった名前がある手法は英語名を別名に入れる。題名と同じ語や、ほかのページの名前と紛らわしい語は別名にしない
- **前提と関連**（D12）：`prerequisites` は直接の前提だけ（推移的に届くものは書かない。多くて4つ）。前提と `related` に同じページを置かない。どちらもページの id で書き、related は節なら `id#anchor` にする（調査の key は書かない）。同じ分野の前提は、ナビゲーションでそのページより前に置く。入ってくる道のないページを作らない
- **節**（D1）：`sections` の level は §3.1 の5・6 に従う。`anchor` は英小文字・数字・ハイフンで、ページの中で一意
- **summary**（D10）：§3.3
- **signs**（D9）：`phrase`（問題文の言い回し・求めるもの）、`constraint`（制約の形。数や不等号を含む。数のないものは phrase にする）、`shape`（立てた式・遷移の形）。手法名を入れない。候補を絞れないサインは書かない。技法の特徴が制約に出るページは constraint を1つ以上置く
- **章**（D13）：発展の概要は話題の章に置き、「発展」の章を作らない。1ページだけの章は隣と合わせる。`cpp` も4〜5章に分ける
- **kind**（D15）：語彙に「計算量」（計算量の見積もり・ならし計算量・調和級数・定数倍）を足した
- **verify**（D14）：Library Checker の問題名。ACL に対応のあるページと、Library Checker を節に書いていたページで埋める
- **visual**（D8）：`kind` は dynamic か static、`priority` は 1（必ず作る）・2（余力があれば）・3（静的な図で代えてよい）。§8.5
- **frequency**：§5.5。`cpp`・`hub`・`guide`・`patterns`・`start` は持たない
- **problems**：§5.3

### 5.2 作り方

1. 分野のまとまりごとにサブエージェントが、調査レポートと topics.yaml、この設計書の §3〜§5 に従って下書きを作る
2. メインのセッションが検証スクリプト（`tools/check_catalog.py`）で全体を確かめる：形式、id の重複、前提の解決・循環・レベルの逆転、`kind` の語彙、問題の実在、分野ごとの数とレベルの分布、調査の key の取りこぼし。第2版で、節の構造とレベル、推移的に冗長な前提、前提と related の重複、related の調査の key、同じ分野の前提がナビゲーションで後ろ、入ってくる道のないページ、例題の重複、同じ別名の重複、根拠の問題が帯に入らない、練習の不足、summary の長さと禁止語、visual の priority 1 の数を足す（catalog/README.md §7）
3. 工程4の見直しで、目次も含めて批判的に読んでもらう。指摘への対応を design-review.md に決め、分野ごとの担当が catalog を第2版の形式と規則に直す（design-review §4）。最後に、最近の ABC のデータから `frequency` を付け直す（§5.5）
4. 工程8a で catalog から各ページの front matter を作る。8a 以降は front matter と問題の台帳が正で、catalog は凍結し、執筆の指示（sections・visual・sources）としてだけ使う（T10）

### 5.3 例題・練習問題の選び方

| 役割 | 内容 | 数の目安 |
| --- | --- | --- |
| 例題 | 本文で方針まで説明する | 1〜3（基礎は1、発展・hub は0〜2、thinking は2〜4、patterns は0〜1） |
| 練習 | 要約と難易度だけ。「解いた」チェック付き | 2〜6（patterns は0〜3） |
| 力試し | そのページの手法を、言い換えや組み合わせで使う難しめの問題 | 0〜3 |

hub の問題は合わせて0〜3でよい（D6）。

- **例題は1問につき1ページ**（その手法の持ち主）だけにする。ほかのページでは練習か本文の参照にする（D4）
- **代表問題**は並び順と切り離し、帯の中の例題1問に `representative: true` を付ける。並びは易しい順のまま（D4）
- **水・青のページは abc319 以降の問題を1問以上入れる**。ないときは `problems_note` に理由を残す（D4）
- 練習が目安に足りないページは `problems_note` に理由を書き、工程8b の前に「問題の補充」を作業として行う（候補は research/00 §2.3.8 と各調査。裏付けを取って台帳に入れる。D4）
- 題材別の問題は「表の行の代表」のリンクだけで、ほかのページと重ならないものにする（D16）
- ABC を優先し、近年（7問体制の abc319 以降）の問題を重く見る。典型90問・EDPC は型の代表として使う。ARC は考察寄りなので少なめにする
- 例題の位置の目安：水は E、青は F（と難しい E）、黄は難しい F と易しい G
- 易しい順に並べ、そのページのレベルの帯をまたいで幅を持たせる
- 問題の `summary` は問いだけ（何を求めるか）を書き、手法名・解き方は `approach` に書く。手法名しか分からない問題は summary を「（執筆時に確かめる）」とし、approach に手法を書く
- 問題の内容（何を問い、どの手法で解けるか）は、第三者の解説で裏付けが取れたものだけ使う。裏付けは台帳に記録する。調査で「未確認」とした問題は、裏付けが取れるまで使わない

### 5.4 問題の台帳（D3）

- `data/problems.yaml`（git で追跡。サイトには出さない）に、使う問題を1問1項目で持つ
- 項目：ID・元のコンテストと記号・タイトル・difficulty（取得日付き）・問い（`summary`。手法名を書かない）・方針（`approach`。執筆者向けで、サイトでは折りたたみの中にだけ出す）・使う手法のページ・裏付けの URL（atcoder.jp・codeforces.com 以外）・確認の状態（確認済み／未確認／不採用）・使うページ
- 調査レポートと catalog から機械的に下書きを作る（工程6）
- **未確認の問題は本文に使えない**。執筆者は台帳の要約を使い、直すときは提案として報告する（§10.2）。事実の検証役は台帳の裏付けの URL で確かめ、確認済みの記録は2ページ目以降で使い回す
- CI と tools は AtCoder Problems の API ではなく、台帳のスナップショットを見る。difficulty の更新は `tools/ap.py` で意図して行い、差分を確かめて別の commit にする

### 5.5 最近の ABC のデータと出題頻度（D5）

- `data/recent-abc.yaml`：research/00 §2.3.8 の abc451〜480 の D〜G の120問を、使う手法のページ id に対応させる
- これから、ロードマップの「位置ごとの頻出手法（最近30回）」と「最近の ABC → ページ」の表を生成する（§7）
- `frequency` を機械的に付け直し、`frequency_evidence` に回数を残す。付け直しは工程4の終わりに行う。基準（catalog/README.md §5）：A＝最近の ABC で2回以上、または多くのページの前提。B＝最近の ABC で1回、または古い ABC で繰り返し使われた。C＝それ以外（発展の多く）
- `cpp`・`hub`・`guide`・`patterns`・`start` は frequency を持たない

## 6. 編集方針

### 6.1 共通の原則

1. **意味の理解を最優先にする。** 「何ができるか」の次に「なぜそれで正しいか」を書き、手順の羅列で終わらせない
2. **冒頭だけで引ける。** 各ページの最初に「要点」の囲み（何ができるか・いつ使うか・計算量・前提）を置く。辞書として引いたときは冒頭だけ読めば足り、学ぶときは続きを読む。**全ページで必ず置くのは front matter とこの要点だけ**にする。要点を必須にするのは要件の「全ページ共通で必須なのはメタデータだけ」を超えるので、工程5でユーザーに確かめる（T6）
3. **図で伝わるものは図にする。** 静的な図（Mermaid・SVG・表）を基本にし、状態が時間とともに変わるものだけ動く図にする（§8.5）
4. **自分で実装できる粒度の処理の流れを書く。** コードの全体は載せない。保つべき性質（不変条件）、各操作の手順、境界（半開区間・空区間・単位元）を言葉と短い擬似コード・数行のコード片（§6.5）で示す
5. **1ページで完結させる。** 前提の説明は繰り返さずリンクするが、断片だけ読まれても何のページか分かるように、冒頭の段落にタイトル・別名・要点を書く（claude.ai の検索で断片が読まれる前提。別名が冒頭にあるかを検査する。§8.6）
6. **用語と記法をそろえる。** 用語は用語集の正規形（`planning/style-guide.md` と `prh.yml` で検査。どちらも工程6で作る）、記法は「記法と用語の約束」のページに従う。各ページで用語の最初の出現だけを用語集のアンカーへリンクする。用語集と prh.yml はメインのセッションが更新し、更新したら全ページに textlint をかけ直す（T19）
7. **全体を不必要に縛らない。** 下の構成（§6.3）は目安で、固定のテンプレートではない。分野と内容に合わせて変えてよい。分野ごとに効く構成と書き方は、style-guide の分野ごとの節（research の各 §7 から作る）に書く（T6）

### 6.2 文体

- だ・である調。です・ます との混在を textlint で検出する
- 「〜である」「〜する」を基本にし、読者への呼びかけは控えめにする
- 1文を短く。1段落1つの主張
- 半角英数字と全角文字の間に空白を入れる（「2 次元」「K 番目」）。題名・別名の規則（§5.1。D11）と同じで、textlint で検査する（design-review §5）

### 6.3 ページの構成の目安（type ごと）

以下は目安である。目安を埋めるためだけの薄い節は作らない（分かりやすさの検証で確かめる。§10.2）。骨格（8a）では節の見出しを生成せず、構成は 8b の執筆で分野と内容に合わせて決める（T6）。

**technique（水・青・黄）**

1. 要点の囲み（一言・使いどころ・計算量・前提）
2. どんな問題で必要になるか（素朴な方法がなぜ間に合わないか）
3. アイデアと、なぜ正しいか（図）
4. 処理の流れ（保つ性質・各操作の手順・境界）
5. 計算量とその根拠
6. 応用の型（上位の帯の節は `sections` に level を持たせる。問題のサインを添える）
7. 落とし穴（よくある誤解・バグ）
8. ACL では（囲み。対応する名前・宣言・主なメソッド・要件だけ）
9. 例題（要約・方針。解法の詳細は折りたたみ）
10. 練習問題・力試し（チェック付き）
11. 確認問題（折りたたみ）
12. 使い分け・次に読む（前提と次に読むはテンプレートが出す。§8.4）
13. 参考（出典）

**technique（基礎）**：要点 → 応用の型 → 落とし穴 → 上位の手法とのつながり → 問題。初歩の説明は省く。節は青まで（§3.1）

**overview（発展）**：何ができるか → どんな問題で使うか（サイン）→ 計算量 → ライブラリでの使い方 → 学ぶための資料 → 例題0〜2

**hub**：表（何から引くか → 使う手法 → ページ）とリンクが本体。中身の説明は各ページに任せる。問題は0〜3（例題なしでよい）

**thinking**：その型が使える合図 → 最小の例 → ABC の例題2〜4（方針は折りたたみ）→ 関連する手法

**pattern**：題材の性質 → 「よく出る問われ方 → 使う手法 → ページ」の表（行の代表の問題へのリンク）

**cpp**：一言 → 素朴に書くとどうなるか（同じ意味のコード）→ 版（いつから・AtCoder と手元の g++-15 で使えるか）→ 落とし穴（確かめた実例）→ 確認問題 → 関連

### 6.4 記法の約束（要点）

- 計算量は $O(N \log N)$ のように KaTeX で書く。log の底は書かない
- 区間は**半開区間** $[l, r)$ を基本にする。閉区間を使うときは明記する
- 添字は、問題文の 1-indexed と実装の 0-indexed の変換を各ページで明示する
- 合同式は $a \equiv b \pmod{m}$、余りは $a \bmod m$、床関数は $\lfloor x \rfloor$
- 木の記法は research/04 §7.5（深さ `dep`、親 `par`、部分木サイズ `sz`、行きがけ番号 `in`・`out`）
- 詳細は工程6で `docs/start/notation.md`（記法と用語の約束）と `planning/style-guide.md` に書く

### 6.5 コード片

- 載せるのは要点の数行と処理の流れ。完全なプログラムは `snippets/<page-id>/` に置き、本文には `pymdownx.snippets` の範囲指定（`--8<--`）で必要な部分だけ取り込む
- **本文の ```` ```cpp ```` は取り込みだけにする**。本文に C++ を直接書かず、擬似コードは ```` ```text ```` で書く（どちらも検査する。§8.6。T11）
- snippets ごとに設定（使うコンパイラ・フラグ・期待：実行して出力が一致／コンパイルエラーになる／警告が出る、入力と期待出力）を置く。C++ 章の失敗例（コンパイルエラーになる書き方・誤った結果を出す書き方）もこの設定で確かめる（T11）
- 書き方は AtCoder の GCC 15.2（`-std=gnu++23`）で通る範囲で、読みやすさを優先する。`#include <bits/stdc++.h>` と `using namespace std;` を使ってよい。マクロ（`rep` など）と型の別名は使わない（`long long` と書く）
- 範囲 for・構造化束縛・ラムダ（比較関数と DFS）は使ってよい。views・`println`・deducing this などの新しい書き方は、使うときに C++ 章の該当ページへリンクする
- 入出力は最小限にし、手法の中心の関数を見せる

### 6.6 問題の載せ方

- 問題文は転載しない。リンクと、自分の言葉での1〜2文の要約だけを載せる。要約は台帳の `summary`（問いだけ。手法名を書かない）を使い、練習の一覧で解き方が見えないようにする。方針（`approach`）はサイトでは折りたたみの中にだけ出す
- リンクは `https://atcoder.jp/contests/<contest>/tasks/<id>` の形で、台帳の情報（元のコンテスト・記号・タイトル）と一致させる
- difficulty は「diff 1882」のように数値と色を添える。値は台帳から取る（更新の仕方は §5.4）
- **例題・練習問題・力試しの一覧は、目印の付いた囲みに入れる**（`<div class="kp-problems" data-role="practice" markdown>` 〜 `</div>`。`data-role` は役割）。1行の書式は工程6で style-guide に決める。JS（解いたチェック）とスクリプト（ロードマップの集計・問題 → ページの対応表・検証）は同じ目印を使う（D4）
- 検査：一覧の各行が書式に合うか、拾った ID が台帳にあり確認済みか、本文の参照（一覧の外の問題へのリンク）が一覧の漏れでないか（§8.6）。書式が崩れても黙って集計から抜けないようにする
- 例題の解法は「方針」までを本文に書き、詳細は折りたたみ（ネタバレ防止）

### 6.7 出典

- 他者の記事は参考にしても文章を転載しない。各ページの末尾に「参考」として URL を残す
- atcoder.jp と codeforces.com は noai 指定のため開かない。USACO Guide は無断複製を禁じる規約なので構成の参考にとどめる。ikatakos 氏の記録（CC BY 4.0）は問題文を引用した節を使わない（research/00 §7.5）
- 新しいドメインを資料にする前に `tools/check_noai.py <URL>`（robots の meta と X-Robots-Tag を読む）で確かめ、確かめたドメインを style-guide に記録する（T20）

`tools/gen_site.py` が全ページの front matter と本文の問題の一覧を読み、次を生成する。生成物はコミットし、CI で `--check`（再生成して差分がないこと）を確かめる（claude.ai と GitHub 上の閲覧で読むため）。

| 生成物 | 用途 |
| --- | --- |
| `docs/llms.txt` | Claude 用の索引（llms.txt の書式）。1ページ1行「[タイトル](URL)（id・レベル・分野・段階）：要約」に絞る（約8万字）。冒頭に版と詳細索引への案内を書く（T5） |
| `docs/index/<field>.md` | 分野ごとの詳細索引：別名・サイン・kind・節（アンカー付きの URL）（T5） |
| `nav.yml` | ナビゲーション。front matter の順と chapter から作り、mkdocs.yml が `INHERIT: nav.yml` で読む（T14） |
| `docs/index.md`・分野の入口ページ・`docs/lists/*.md` | ホーム、分野の入口、レベル別・種類別の一覧（T14） |
| `overrides/assets/` の graph.json | 知識マップ・ロードマップ・進捗の集計（サイトの JS 用）。重ければ配置の座標も入れる（T2） |
| 手書きのページの生成部分 | 逆引き辞典の表（constraint・phrase・shape）、ロードマップのページ列（上位の節を含む）と位置ごとの頻出手法、問題 → ページの対応表と最近の ABC → ページの表、Library Checker の対応表、用語の索引。目印（`<!-- gen:begin 名前 -->` 〜 `<!-- gen:end -->`）の間に直接書き、`--check` はその範囲を比べる。手書きは目印の外だけ（T17） |
| 制作状況の表 | `stage` の集計（§10.3） |

- 索引の版は、入力（全ページの front matter と問題の一覧）の内容のハッシュと、front matter の `updated` の最大値にする。どちらも決定的なので `--check` と両立する（生成日時とコミットは書かない。T5）
- 前提・次に読むは生成せず、テンプレートで出す（§8.4。T15）

### 8.4 表示

- **検索**：`lang: ja` に加え、文字種の境目で区切る `separator` と、`pipeline: [stemmer, stopWordFilter]` を設定する（research/10 の設定 C。T3）。試作の14ページでは30問中29問で正解のページが出たが（research/10 §2.4）、367ページの規模ではほぼ全ページがヒットして順位だけが頼りになる（review/02 指摘4）。そのため用語の索引（§7）を検索に頼らない入口にし、8a の後に検索の試験をやり直す（§8.6）
- **数式**：KaTeX 0.16.47 を同梱し、`pymdownx.arithmatex`（generic）で描画する
- **図**：Mermaid（Material の標準の統合）。Mermaid は CDN から読まれるので、欠けると困る図は SVG にする
- **バッジ**：ページ上部にテンプレートの上書きで、レベル（AtCoder の色）と分野のバッジを出し、kind も一覧へのリンク付きで出す（T23）。`stage` が stub のページには「準備中」の印を出す（T13）
- **前提・次に読む**：テンプレートの上書き（`nav.pages` の各ページの meta を読む）で出す。次に読む（このページを前提にするページ）は、同じレベルと1つ上のレベルを優先して8件までにし、続きは知識マップの焦点の表示へつなぐ（T15）
- **知識マップ**（T2）：
  - 既定は分野ごとの表示。ページから開くと、そのページの祖先（前提をすべて）と子孫（次に読む）だけを描く
  - 全体は、分野を頂点にした15頂点の図にする
  - related は配置に使わず、選んだページの周りに配置の後から薄く足す
  - 点はページで、上位の帯の節を持つページに印を付ける（D1）。理解したページを塗り、次の候補を強調する（§9.1）
  - 重ければビルド時に座標を計算して graph.json に入れる。同じ内容を表（レベル別一覧）でも出す
  - 理由：367ページを1枚に描くと外形が約27:1で読めず、related も辺にすると配置に約42秒かかった（review/02 指摘3）
- ライトとダークの切り替え、スマホ表示に対応する

### 8.5 動く図

- 素の JS ＋ SVG の小さな部品にする。「状態の列を先に全部作り、i 番目を描く」方式で、外部ライブラリを使わない（research/10 §3.3）
- 共通部品（ステップ送りの操作：最初・前・次・最後・自動再生・速度、キーボードとスワイプ）を1つ作り、図ごとに「状態の列を作る関数」と「状態を描く関数」だけを書く
- 埋め込みは `<div class="kp-viz" data-viz="<名前>" data-config="…">` の形。部品の class の接頭辞は `kp-` にそろえ、Material の class とぶつけない（T23）。instant navigation の下でも動くよう `document$` で初期化する
- JS が動かない環境（claude.ai での読み込みを含む）でも意味が通るように、図の前後に文章で要点を書く
- **数と優先度**（D8）：catalog の `visual` を `{kind, priority, text}` で持つ。priority 1（必ず作る）は全体で25前後にし、担当ごとの枠は design-review §4.2 に従う。ほかの dynamic は priority 2〜3（余力があれば）にするか、静的な図に直す
- priority 1 の候補（研究の提案から）：BFS の層とキュー、ダイクストラのヒープ、01-BFS の deque、ワーシャルフロイド、最大流の残余グラフ、Union-Find、セグ木の更新と取得、遅延伝播、二分探索の境界、尺取り、いもす法、ナップサックの表、オイラーツアーと列の対応、LCA のダブリング、直径の2回探索
- **試験**（D8）：図ごとに、状態の列を作る関数の単体試験（Node で実行）を置く。ヘッドレスのブラウザでの取り付けの検査を §8.6 に入れ、コードの検証役が図も確かめる（§10.2）

### 9.2 解説（claude.ai ＋ GitHub 連携）

- **方式**：従来のプロジェクトに GitHub 連携で `docs/`・`snippets/`・`claude/` を入れる（research/10 §3.6 の方式 A）。静的ファイルは `overrides/assets/` にあるので、docs/ は丸ごと選べる（T16）。教材が大きくなると claude.ai が自動で検索方式（RAG）に切り替わる前提で手順を書く。加えて、利用者がメッセージに `llms.txt` の URL を書いたときは、公開サイトから最新のページ（Markdown 版。§8.7）を読む方式 B も手順に書いておく。方式 C（新しい Projects）を試すときは、解説用の指示を制作用の CLAUDE.md と分ける（T8）
- **守るべき規則はプロジェクトの指示そのものに書く**（T8）：開催中のコンテストは断る・atcoder.jp と codeforces.com を開かない・最初にヒントか解説かを聞く・教材の用語と記法に合わせる・索引の版を回答に書く。短く書いて版の番号を付け、原文は `claude/project-instructions.md` に置く。RAG では手順ファイルも断片で検索され、規則が読まれない恐れがあるため
- **手順ファイル**：`claude/explain.md`（git で追跡。プロジェクトの指示から参照）。1つの断片に収まる長さにし、詳細は別ファイルに分ける（T8）。「記録用まとめ」の形式は `claude/record-format.md` に書き、explain.md と記録用スキルの両方から参照する（T18）
- **手順の骨子**：
  1. 開催中のコンテスト（ABC・ARC・AGC）の問題なら解説しない（AtCoder生成AI対策ルール）。開催中かは、終了したコンテストかを利用者に確かめる。ADT・AWC は判断がつくまで同じく断る（T8）
  2. 問題はスクリーンショットか利用者の要約で受け取る。atcoder.jp・codeforces.com のページを開かない
  3. 利用者が考えたことを聞き、「ヒントだけ」か「解説まで」を選んでもらう
  4. 索引（`docs/llms.txt`）で関連ページを探し、節は分野ごとの詳細索引（`docs/index/<field>.md`）で探す。検索方式のときは、手法名・別名・問題のサインで言い方を変えて複数回検索する。必要なページだけを読む。stub（準備中）のページは根拠にしない（T13）
  5. 教材の用語と記法で解説し、該当ページ・節の URL（詳細索引のアンカー付き）を示す。教材にない知識はそうと明示する。回答に索引の版を書く
  6. 解けなかった原因を一言で分類する（知識不足／気づけなかった／実装ミス／時間不足）
  7. 頼まれたときだけ、記録用スキルに貼り付ける「記録用まとめ」を決まった形（`claude/record-format.md`）で出す
- AtCoder生成AI対策ルールの版（今は20261014版）を、この教材の使い方のページとプロジェクトの指示に書き、改定されたら見直す（T8）
- **実機で確かめること**（9b。工程7と並行。T7）：GitHub 連携でのフォルダの選び方と同期、RAG での索引と本文の引かれ方、`llms.txt` の URL を渡したときに各ページを続けて取得できるか（web fetch）、教材のトークン数。試作のページと仮の索引で確かめ、索引と冒頭の形式を決めてから 8a に進む

### 9.3 記録（Claude Code のスキル）

- `.claude/skills/record-problem/SKILL.md`（git で追跡）。`disable-model-invocation: true` で、利用者が `/record-problem` と打ったときだけ動く。本文に依存しないので工程6の中で作る（9a。T7）

| 事実の検証 | 執筆とは別のエージェント | 書かれたページ、事実のチェックリスト、台帳 | 指摘の一覧（計算量・定理・ACL の API・問題の内容と difficulty・リンク）。問題は台帳の裏付けの URL で確かめる |
| コードと図の検証 | 同上 | snippets、動く図、チェックリスト | コンパイル・実行の結果、図の試験の結果と指摘（D8） |
| 分かりやすさの検証 | 同上。レート1000前後の読者の立場で読む | ページ、前提のページ、チェックリスト | 分かりにくい箇所・飛躍・「なぜ」の欠け・目安を埋めるためだけの薄い節（T6） |
| 修正 | 執筆者か別のエージェント | 指摘の一覧 | 直したページ |

- 書いた本人に採点させない
- **並列の執筆の規則**（T9）：執筆者が書くのは担当ページ（`docs/<field>/<id>.md`）と `snippets/<id>/` だけ。用語集・prh.yml・早見表・使い分け・catalog・台帳への追加は報告に「提案」として書き、メインがバッチの終わりにまとめて反映する。`gen_site.py` の実行と commit・push はメインだけが行う。この規則は CLAUDE.md と執筆の手引きに書く
- 並列の数と止める基準は、試作の実測と利用の上限から決めて progress.md に書く（T21）
- 1バッチ（例：ある分野の水のページ群）ごとに、執筆 → 検証 → 修正 → 提案の反映 → 機械的な検証 → commit・push。バッチの記録を残す（§10.3）

### 10.3 進捗の管理と再開

- 各ページの `stage`（stub → draft → reviewed → done）を front matter に持ち、`tools/gen_site.py` が制作状況の表を生成する
- バッチごとに `planning/batches/<番号>.md`（ページ・担当・各検証の結果と指摘・直したか・未解決・使用量）を書き、progress.md から参照する。工程10の「検証の記録」はこれを集めたものにする（T12）
- `planning/progress.md` に工程・バッチ・次にやること・並列の数と止める基準を書く。セッションが切れたら、これと制作状況の表とバッチの記録から再開する
- **8a 以降に正となるデータ**（T10）：各ページの front matter と問題の台帳。catalog は凍結し、執筆の指示（sections・visual・sources）としてだけ使う。id と URL は変えない（変えるときは転送と localStorage の鍵の読み替え表を用意する）。ページの追加・統合・削除は decisions.md に残し、ユーザーに知らせる
- 新しく決めたことは decisions.md に、設計の変更はこの文書の変更履歴に残す

### 10.4 使用量と期間（T21）

- 工程7の試作で、ページの種類（基礎・水〜黄の手法・発展・C++・横断）ごとに、入出力のトークン・道具の呼び出し回数・Web 取得の回数・所要時間を記録する。その実績から全体の使用量と期間の見込みを出し、工程7の確認でユーザーに示す
- 試作に黄の手法ページを1つ加える（§10.1）
- 執筆者には設計書の全文ではなく執筆の手引きを渡す（§10.2）
- バッチごとの使用量をバッチの記録に残し、見込みを更新する
- 規模を下げる手段を先に決めておく：発展の概要を短い型に固定する、動く図を priority 1 に絞る、問題の枠を減らす。使うときはユーザーに確かめる（§10.5）

### 10.5 ユーザーに確かめる場面（T22）

工程5（決定の提示）と工程7（試作）の確認のほか、次の場面ではユーザーに確かめてから進める（要件 §8「作業の途中でも必要になればその都度質問する」）。

- ページの追加・統合・削除
- レベルの変更
- 要件から外れる表示や機能
- 使用量が見込みを超えるとき
- 8b の最初のバッチの出来
- Zensical への移行

## 12. 決定の一覧（工程5でユーザーに示す要約の元）

1. 構成：15の分野（はじめに・横断・基本テクニック・考察・DP・グラフ・木・データ構造・整数論・代数・数え上げ・確率・ゲーム・文字列・幾何・その他・題材別・C++）。目次の第2版は353ページ（基礎100・水79・青52・黄37・発展51・レベルなし34）。入口・比較・地図のページは type hub
2. レベル：基礎〜1199／水／青／黄／発展2400〜。「まとまって現れ始める帯」で決め、abc319 以降の根拠を主に数える。ACL を呼ぶだけで解ける問題も数える。根拠の問題を残す。上位の内容は節に level を付け（節はページ以上、基礎のページは青まで）、その色のロードマップに出す
3. 分類：分野・レベル・手法の種類・出題頻度（最近の ABC のデータから機械的に付ける）・問題のサイン（言い回し・制約・立てた式の形）・前提。一覧はスクリプトで生成
4. 境界と統合：期待値 DP とゲーム DP は「数え上げ・確率・ゲーム」に置く、Union-Find の構造は「データ構造」、使い方は「グラフ」、括弧列・mex・順列・XOR などは「題材別」の案内ページ。重複していた DP の4ページを「整数論・代数」「数え上げ・確率・ゲーム」「基本テクニック」のページへ統合し、ABC の根拠が薄い黄のページを節にする（§4.4）
5. 粒度とレベルの主な決定：セグ木5ページ（遅延セグ木は水）、行列累乗は青、区間 DP・桁 DP・bitDP は基本と応用に分ける、C++ は約15〜20ページ（4〜5章）＋C++ の逆引き、考察は短いページで入口は横断の「詰まったときの発想リスト」1つ、幾何は8ページ前後、題材別は「部分列と部分文字列」「約数と倍数」を足して10ページ前後
6. ページの構成：全ページ必須は front matter と冒頭の要点。構成（なぜ正しいか、自分で実装できる粒度の処理の流れ、ACL の囲み、例題（解法は折りたたみ）、練習問題（チェック付き）、確認問題）は目安で、分野ごとの書き方は style-guide に決める
7. コード片：本文の C++ は snippets からの取り込みだけ。完全なプログラムは別ファイルで GCC 15.2・gnu++23 でコンパイル・実行して確かめる（失敗例はコンパイルエラー・警告を期待として確かめる）
8. 問題：ABC 優先、例題1〜3・練習2〜6・力試し0〜3。問題の台帳で裏付けを管理し、未確認の問題は使わない。例題は1問1ページ、水・青のページには abc319 以降の問題を1問以上入れる。本文の一覧は目印の囲みに入れて検査する
9. 技術：Material 9.7.7 固定、生成は独立スクリプト（nav も生成）、静的ファイルは `overrides/assets/`、日本語検索の調整と用語の索引、KaTeX 同梱、知識マップは Cytoscape.js で分野ごと・焦点の表示、動く図は自作の小さな部品（priority 1 を25前後）、索引は `docs/llms.txt`（1ページ1行）と分野ごとの詳細索引。Zensical の評価は工程6の終わりと 8b の前
10. 進捗：確認問題（折りたたみ）、練習問題の解いたチェック、ページ×レベルの理解したチェック（localStorage の1キー、書き出し・読み込みは手動の退避）
11. claude.ai：GitHub 連携で `docs/`・`snippets/`・`claude/` を入れる。守るべき規則はプロジェクトの指示に版付きで書き、手順は `claude/explain.md`。開催中のコンテストは断り（開催中かは利用者に確かめる。ADT・AWC も当面断る）、atcoder.jp・codeforces.com は開かない。問題はスクリーンショットか要約で受け取る
12. 記録：`/record-problem` スキルで `notes/<問題ID>.md` に1問1ファイル（同じ問題は追記）
13. 制作順：土台（記録用スキルを含む）→ 試作（claude.ai の実機確認と使用量の測定。ユーザーの確認）→ 骨格 → 解説手順の確定 → 問題の補充 → 本文（基礎・水 → 青 → 黄 → 発展）→ 全体の検証
14. 途中でユーザーに確かめる場面：ページの追加・統合・削除、レベルの変更、要件から外れる表示や機能、使用量が見込みを超えるとき、8b の最初のバッチの出来、Zensical への移行（§10.5）

工程5で特に確かめること（design-review §6）：

1. 冒頭の「要点」を全ページに置く（要件の「全ページ必須はメタデータだけ」を超える）（T6）
2. 解説と記録の仕組みの時期の変更（9a・9b・9c）（T7）
3. Zensical の評価の時期（T4）
4. 規模：353ページ（基礎100・発展51）。発展の概要は1手法1ページのまま
5. 公開中に stub のページがある（「準備中」の印）（T13）
6. 問題は利用者のスクリーンショットか要約で受け取る（claude.ai に atcoder.jp を開かせない）
7. 「理解した」「解いた」の書き出し・読み込みは手動の退避で、同期ではない
8. 使用量と期間は試作で測ってから示す（T21）
9. 執筆者には設計書の全文ではなく、設計書・編集方針・用語集・記法の約束から執筆に要る規則を集めた「執筆の手引き」を渡す（要件 §8 の「設計書…を必ず渡し」と字面が違う。目的のページ間の一貫性は手引きと見本で保つ）（T21）
