工程3（設計）の成果物。要件（[requirements.md](requirements.md)）と決定事項（[decisions.md](decisions.md)）を前提に、調査（[research/](research/)）の結果から、目次・分類・編集方針・技術構成・制作の進め方を決める。全ページの一覧（目次）は [catalog/](catalog/) に置き、この設計書の規則（§4・§5）に従って作る。

- 版：2026-10-21 初版（工程4の見直しの前）
- 設計を変えるときは、この文書を直し、変更の理由を末尾の「変更履歴」に書く。ユーザーの判断が要る変更は decisions.md にも記録する

## 1. 前提の整理

### 1.1 学習者と目標

- レート961、パフォーマンス1100〜1450。ABC は D まで安定、E は時々。目標は黄色（パフォーマンス2000前後を安定して出す）
- 直近81回の ABC（abc400〜abc480）の difficulty（research/00 §2.3）から、教材のレベルと問題位置はおおむね次のように対応する。**水 ≒ E（と易しい F）、青 ≒ F（と難しい E）、黄 ≒ 難しい F と易しい G**
- F の75%は difficulty 2000 未満。したがって黄色への主な条件は「青までの知識を速く確実に使うこと」で、黄の知識は難しい F と G で効く。教材は「水・青を厚く、正確に」を最優先にする
- 最近の傾向：E は数え上げ（二項係数・包除・寄与）と累積和・差分、F は「言い換えてからセグ木（特に遅延セグ木）に載せる」、G は専用の手法（FPS・フロー・行列累乗・Mo など）が多い（research/00 §2.3.8）

### 1.2 教材の使われ方と、そこから来る設計の条件

| 使われ方 | 設計の条件 |
| --- | --- |
| ABC で解けなかった問題から引く（辞書） | どのページも冒頭だけで「何ができて、いつ使うか」が分かる。名前・別名・問題のサインのどれからでも引ける（検索・逆引き・索引）。行き止まりを作らない（基礎と発展もページを持つ） |
| 色ごとに順に学ぶ | レベルと前提関係から、ロードマップと知識マップを自動で作る。「次に読む」がたどれる |
| 解説コードの1行が読めない | C++ 章を「書き方から引ける」形にする（C++ の逆引き） |
| claude.ai で解説してもらう | 索引ファイルから関連ページを探せる。1ページが単独で読める（断片だけ読まれても意味が通る）。用語と記法が教材全体でそろっている |
| 自作ライブラリを作る | 実装の全体は載せないが、自分で実装できる粒度の処理の流れ（保つ性質・各操作の手順・境界）を書く。ACL の対応と、Library Checker での確かめ方を示す |
| スマホで読む | 表を横に広げすぎない。動く図は指で操作できる。長い証明は折りたたむ |

### 1.3 成功の条件

1. 学習者が解けなかった ABC の E・F を持ってきたとき、関連するページに3クリック以内（または索引の1回の検索）でたどり着ける
2. 各ページが「なぜそうなるか」を説明しており、手順の羅列で終わっていない
3. 事実（計算量・定理・問題番号・difficulty・ACL の API）に誤りがない。問題番号はすべて機械的に実在を確かめている
4. 用語・記法・文体が全ページでそろっている
5. 制作が途中で止まっても、どこまでできていて次に何をするかがファイルから分かる

## 2. 全体構成

### 2.1 分野（ナビゲーションの章）

ページは1つの分野（`field`）に属し、ナビゲーションの章になる。分野をまたぐ引き方は、手法の種類（`kind`）・レベル・題材・逆引き辞典が受け持つ。

| field | 表示名 | 中身 | おもな出典 |
| --- | --- | --- | --- |
| `start` | はじめに | この教材の使い方、記法と用語の約束、AtCoder の仕組み | 00 |
| `guide` | 横断ページ | 逆引き辞典、使い分け、知識マップ、ロードマップ、早見表、戦い方など（§7） | 00 |
| `basics` | 基本テクニック | 計算量の見積もり、全探索、二分探索、累積和・いもす、尺取り、ソート・座標圧縮、貪欲、半分全列挙、ダブリング、分割統治、周期性、bit 演算 | 01 |
| `thinking` | 考察 | 言い換え・主客転倒・寄与・余事象・偶奇・不変量・構築などの型（少しだけ扱う） | 01 |
| `dp` | 動的計画法 | DP の考え方、列・区間・集合・桁・木の DP、DP の高速化 | 02 |
| `graph` | グラフ | 探索、最短路、有向グラフ、連結性と全域木、フロー | 03 |
| `tree` | 木 | 木の性質、直径・LCA・オイラーツアー・マージテク・重心など | 04 |
| `ds` | データ構造 | STL の応用、スタック・キュー、Union-Find、BIT・セグ木、クエリ処理の工夫 | 05 |
| `math` | 整数論・代数 | mod、素数・約数、GCD と合同式、floor、行列・線形代数、畳み込み | 06 |
| `comb` | 数え上げ・確率・ゲーム | 数え方の考え方、二項係数・包除、確率・期待値（期待値 DP を含む）、ゲーム（ゲーム DP を含む） | 07 |
| `string` | 文字列 | ハッシュ、Z・KMP・Manacher、Trie、Suffix Array、Aho-Corasick | 08 |
| `geometry` | 幾何 | ベクトルと外積、誤差、凸包、偏角ソート、45度回転など | 08 |
| `misc` | その他の技法 | インタラクティブ、乱択、bitset による高速化、構文解析 | 08 |
| `patterns` | 題材別 | 括弧列・mex・順列・XOR・区間・グリッドなど、問題に現れる「対象」から引く案内ページ | 00 |
| `cpp` | C++ | 解説コードに出る書き方、AtCoder と手元の環境、落とし穴、ACL の読み方 | 09 |

並び順は上の表のとおり。`guide` を `start` の次に置くのは、辞書として引く入口（逆引き・地図）を最初に見せるため。

### 2.2 ページの種類（`type`）

| type | 内容 | 長さの目安 |
| --- | --- | --- |
| `technique` | 手法・データ構造・定理。教材の本体 | 制限なし（基礎は短め） |
| `thinking` | 考察の型 | 短い |
| `pattern` | 題材別の案内（よく出る問われ方 → 手法の表） | 短い〜中 |

| `guide` | 横断ページ・はじめに（手書き） | ページによる |

### 2.3 規模の見込み

調査の項目は延べ598（重複30を含む）。§4 の規則でまとめた目次（catalog の初版）は **367ページ**になった（technique 257、overview 55、thinking 10、pattern 8、cpp 19、guide・start 18。ほかに生成ページ）。レベル別は基礎93・水90・青58・黄44・発展55・なし27。

規模を下げる案（分野ごとの大きなページにまとめて約150ページ）も比べたが、辞書として引くときに目的の節を探す手間が増え、レベルの違う内容が1ページに混ざるので採らない（§13 案の比較 A）。

## 3. レベルと分類

### 3.1 レベル（`level`）

| level | difficulty | 扱い |
| --- | --- | --- |
| 基礎 | 〜1199 | 短いページ。初歩の説明は省き、応用の型・落とし穴・上位の手法とのつながりに絞る |
| 水 | 1200〜1599 | 本格的に扱う |
| 青 | 1600〜1999 | 本格的に扱う |
| 黄 | 2000〜2399 | 本格的に扱う |
| 発展 | 2400〜 | `overview` ページだけ |

割り当ての規則：

1. **その手法を知らないと解けない問題が、まとまって現れ始める帯**にする。易しい例が1問だけ下の帯にあっても下げない。根拠の問題と difficulty を catalog の `level_evidence` に残す
2. difficulty は AtCoder Problems の推定値（`tools/ap.py`）。2019年以前の ABC は同じ手法でも高めに出るので、近年の問題を重く見る
3. 典型90問など difficulty のない問題は、作問者の★を目安にする（★4＝基礎、★5＝水、★6＝青、★7＝黄）。ABC の問題があればそちらを優先する
4. 1つの手法で易しい使い方と難しい使い方の帯が分かれるとき：中身が多ければページを分け（例：区間 DP と区間 DP の応用）、少なければ1ページの中で節に**レベルの印**（例：「応用（青）」）を付ける
5. ページの前提に、そのページより高いレベルのページを置かない（検証スクリプトで警告する）。避けられないときは `related` にする
6. `start`・`guide`・`cpp`・`patterns`・`generated` はレベルを持たない（`cpp` は「目に入り始める帯」を `level` に入れてよい）

### 3.2 分類の軸

| 軸 | キー | 値 | 使い道 |
| --- | --- | --- | --- |
| 分野 | `field` | §2.1 の15個のどれか1つ | ナビゲーション |
| レベル | `level` | §3.1 | バッジ、レベル別一覧、ロードマップ、知識マップの色 |
| 手法の種類 | `kind` | 固定の語彙（catalog/README.md）から複数 | 分野をまたぐ一覧（例：DP の種類に `comb` の期待値 DP も入る） |
| 出題頻度 | `frequency` | A（最近の ABC で頻出）／B（時々）／C（まれ） | ロードマップの「必修・準必修・余裕があれば」 |
| 問題のサイン | `signs` | 制約の形・言い回し | 逆引き辞典2種 |
| 前提 | `prerequisites`・`related` | ページ id | 知識マップ、次に読む、ロードマップの順序 |

Material の tags プラグイン（階層タグ）も比べたが、1ページ1値の軸（レベル・分野）を単一値のキーで持つほうが二重管理がなく、検証もしやすい。一覧ページはスクリプトで生成する（research/10 §3.1.2 の案 K。§13 案の比較 B）。

### 3.3 メタデータ（front matter）

全ページ共通で必須なのはメタデータだけ（要件 §4）。形式は `schema/page.schema.json` で検証する。

```yaml
---
id: lazy-segment-tree          # 一意。ファイル名と同じ。英小文字・数字・ハイフン
title: 遅延セグメント木
aliases: [遅延セグ木, Lazy Segment Tree]
type: technique
field: ds
level: 青
kind: [データ構造, 区間クエリ]
prerequisites: [segment-tree, segment-tree-monoid]   # 必須の前提（知識マップの辺）
related: [range-set-management, imos]                 # あると良い関連（地図には薄く）
summary: 区間への一括更新と区間の集約を、どちらも O(log N) で行う。
complexity: 構築 O(N)、更新・取得 O(log N)
signs:
  - {type: phrase, text: 区間に一括で加算・代入し、区間の和や最小値を答える}
  - {type: constraint, text: "N, Q ≤ 2×10^5 で区間の更新と取得が交互に来る"}
acl: [lazy_segtree]
frequency: A
verify: [range_affine_range_sum]   # Library Checker の問題（自作ライブラリ用。任意）
status: draft                      # stub / draft / reviewed / done
updated: 2026-10-21
---
```

- `cpp` のページは、`cpp_std`（17・20・23）、`gcc_min`（13・14・15）、`atcoder`（AtCoder で使えるか）を足す（research/09 §7.3）
- 例題・練習問題の ID は front matter に重ねて書かない。本文の決まった形のリスト（§6.6）からスクリプトが拾う（二重管理を避ける）
- `summary` は1〜2文。索引・一覧・知識マップのツールチップに使うので、単独で意味が通るように書く

## 4. ページの粒度と分野間の境界

### 4.1 粒度の規則

1. **1ページ＝名前で引かれ、独自の「なぜ」を持つ1つの単位**。その変種・応用は節にし、節には見出しのアンカーを付けて直接リンクできるようにする
2. **難度帯がはっきり分かれる型は、基本と応用を別ページにする**（研究の提案どおり）：セグ木は「基本（水）／モノイドの設計（青）／セグ木上の二分探索（青）／遅延セグ木（青）／載せ方の型（青）」の5ページ、区間 DP・桁 DP は基本と応用、bitDP は「bitDP（水）／3^N（青）／プロファイル DP（黄）」
3. **基礎の小さな項目は、引かれる名前が違えば別ページ、同じ考え方の変種なら節**（例：いもす法と2次元いもすは1ページ、bit 全探索と順列全探索は1ページ。ただし差分は、黄の「差分列への言い換え」を含むと中身が多くレベルも離れるので、いもす法とは別ページにした）
4. **発展は1手法1ページの短い概要**（ユーザーの回答どおり）。ただし同じ系統で単独では薄すぎるもの（Monge の系統、文字列の発展手法など）は1枚にまとめ、節ごとにアンカーを付ける
5. **C++ 章は約15〜20ページ**にし、書き方1つずつにアンカーを付け、「C++ の逆引き」（書き方 → ページ#節）を入口にする。研究の案 A（36ページ）は1ページが薄くなりすぎ、案 B（11ページ）は1ページが長くなりすぎるので中間を取る（§13 案の比較 F）
6. **幾何は ABC での出題が少ないので、統合を優先して8ページ前後**にする
7. **考察（`thinking`）は「入口1ページ＋短いページ8本＋節」**（research/01 §7.3）。要件の「少しだけ」に合わせ、各ページは「その型が使える合図・最小の例・ABC の例題2〜4問」に絞り、証明の技法は体系的に教えない
8. **題材別（`patterns`）は8ページ前後**：括弧列、mex、順列（置換）、XOR、区間、グリッド、K 番目と中央値、操作列（クエリ・逆順処理）を候補とし、catalog で決める。各ページは「その題材でよく出る問われ方 → 使う手法」の表を中心にした案内で、手法の説明は各ページに任せる

## 5. 目次（catalog）の作り方

### 5.1 形式

- `planning/catalog/<field>.yaml` に、その分野の全ページを並べる。並び順がナビゲーションの順になる
- 1ページの項目：`id`・`chapter`（分野の中の章。ナビゲーションの小見出し）・`title`・`aliases`・`type`・`level`・`level_evidence`・`kind`・`prerequisites`・`related`・`summary`・`signs`・`acl`・`frequency`・`sections`（主な節。レベルの印を含む）・`merged_keys`（統合した調査の key）・`visual`（図・動く図の案）・`problems`（例題・練習の候補。執筆時に確かめ直す）・`sources`（執筆時に読むべき調査レポートの節）
- id は原則として調査の key を使う。統合したページは主な key を id にし、ほかを `merged_keys` に入れる。前提に他分野のページを書くときは、相手の調査の key を書いてよい（統合後にスクリプトで解決する）
- 詳しい規則と `kind` の語彙は [catalog/README.md](catalog/README.md)

### 5.2 作り方

1. 分野のまとまりごとにサブエージェントが、調査レポートと topics.yaml、この設計書の §3〜§4 に従って下書きを作る
2. メインのセッションが検証スクリプトで全体を確かめる：id の重複、前提の解決、前提の循環、前提のレベルの逆転、`kind` の語彙、分野ごとの数とレベルの分布、調査の key の取りこぼし（どのページにも入らなかった key）
3. 工程4の見直しで、目次も含めて批判的に読んでもらう

### 5.3 例題・練習問題の選び方

| 役割 | 内容 | 数の目安 |
| --- | --- | --- |
| 例題 | 本文で方針まで説明する。最初の例題がそのページの代表問題 | 1〜3（基礎は1、発展は0〜2） |
| 練習 | 要約と難易度だけ。「解いた」チェック付き | 2〜6 |
| 力試し | そのページの手法を、言い換えや組み合わせで使う難しめの問題 | 0〜3 |

- ABC を優先し、近年（7問体制の 2023-09 以降を含む）の問題を重く見る。典型90問・EDPC は型の代表として使う。ARC は考察寄りなので少なめにする
- 例題の位置の目安：水は E、青は F（と難しい E）、黄は難しい F と易しい G
- 易しい順に並べ、そのページのレベルの帯をまたいで幅を持たせる
- 問題の内容（何を問い、どの手法で解けるか）は、第三者の解説で裏付けが取れたものだけ使う。調査で「未確認」とした問題は、執筆時に裏付けが取れなければ使わない

## 6. 編集方針

### 6.1 共通の原則

1. **意味の理解を最優先にする。** 「何ができるか」の次に「なぜそれで正しいか」を書き、手順の羅列で終わらせない
2. **冒頭だけで引ける。** 各ページの最初に「要点」の囲み（何ができるか・いつ使うか・計算量・前提）を置く。辞書として引いたときは冒頭だけ読めば足り、学ぶときは続きを読む
3. **図で伝わるものは図にする。** 静的な図（Mermaid・SVG・表）を基本にし、状態が時間とともに変わるものだけ動く図にする（§8.5）
4. **自分で実装できる粒度の処理の流れを書く。** コードの全体は載せない。保つべき性質（不変条件）、各操作の手順、境界（半開区間・空区間・単位元）を言葉と短い擬似コード・数行のコード片で示す
5. **1ページで完結させる。** 前提の説明は繰り返さずリンクするが、断片だけ読まれても何のページか分かるように、冒頭の段落にタイトル・別名・要点を書く（claude.ai の検索で断片が読まれる前提）
6. **用語と記法をそろえる。** 用語は用語集の正規形（[style-guide.md] と `prh.yml` で検査）、記法は「記法と用語の約束」のページに従う
7. **全体を不必要に縛らない。** 下の構成は目安で、分野と内容に合わせて変えてよい

### 6.2 文体

- だ・である調。です・ます との混在を textlint で検出する
- 「〜である」「〜する」を基本にし、読者への呼びかけは控えめにする
- 1文を短く。1段落1つの主張

### 6.3 ページの構成の目安（type ごと）

**technique（水・青・黄）**

1. 要点の囲み（一言・使いどころ・計算量・前提）
2. どんな問題で必要になるか（素朴な方法がなぜ間に合わないか）
3. アイデアと、なぜ正しいか（図）
4. 処理の流れ（保つ性質・各操作の手順・境界）
5. 計算量とその根拠
6. 応用の型（節ごとにレベルの印。問題のサインを添える）
7. 落とし穴（よくある誤解・バグ）
8. ACL では（囲み。対応する名前・宣言・主なメソッド・要件だけ）
9. 例題（要約・方針。解法の詳細は折りたたみ）
10. 練習問題・力試し（チェック付き）
11. 確認問題（折りたたみ）
12. 使い分け・次に読む（前提と関連はスクリプトが補う）
13. 参考（出典）

**technique（基礎）**：要点 → 応用の型 → 落とし穴 → 上位の手法とのつながり → 問題。初歩の説明は省く

**overview（発展）**：何ができるか → どんな問題で使うか（サイン）→ 計算量 → ライブラリでの使い方 → 学ぶための資料 → 例題0〜2

**thinking**：その型が使える合図 → 最小の例 → ABC の例題2〜4（方針は折りたたみ）→ 関連する手法

**pattern**：題材の性質 → 「よく出る問われ方 → 使う手法 → ページ」の表 → 例題

**cpp**：一言 → 素朴に書くとどうなるか（同じ意味のコード）→ 版（いつから・AtCoder と手元の g++-15 で使えるか）→ 落とし穴（確かめた実例）→ 確認問題 → 関連

### 6.4 記法の約束（要点）

- 計算量は $O(N \log N)$ のように KaTeX で書く。log の底は書かない
- 区間は**半開区間** $[l, r)$ を基本にする。閉区間を使うときは明記する
- 添字は、問題文の 1-indexed と実装の 0-indexed の変換を各ページで明示する
- 合同式は $a \equiv b \pmod{m}$、余りは $a \bmod m$、床関数は $\lfloor x \rfloor$
- 木の記法は research/04 §7.5（深さ `dep`、親 `par`、部分木サイズ `sz`、行きがけ番号 `in`・`out`）
- 詳細は工程6で `docs/start/notation.md`（記法と用語の約束）と `planning/style-guide.md` に書く

### 6.5 コード片

- 載せるのは要点の数行と処理の流れ。完全なプログラムは `snippets/<page-id>/` に置き、本文には `pymdownx.snippets` の範囲指定で必要な部分だけ取り込む。完全なプログラムは CI と手元でコンパイル・実行して確かめる（§8.6）
- 書き方は AtCoder の GCC 15.2（`-std=gnu++23`）で通る範囲で、読みやすさを優先する。`#include <bits/stdc++.h>` と `using namespace std;` を使ってよい。マクロ（`rep` など）と型の別名は使わない（`long long` と書く）
- 範囲 for・構造化束縛・ラムダ（比較関数と DFS）は使ってよい。views・`println`・deducing this などの新しい書き方は、使うときに C++ 章の該当ページへリンクする
- 入出力は最小限にし、手法の中心の関数を見せる

### 6.6 問題の載せ方

- 問題文は転載しない。リンクと、自分の言葉での1〜2文の要約だけを載せる
- リンクは `https://atcoder.jp/contests/<contest>/tasks/<id>` の形で、`tools/ap.py` の情報（元のコンテスト・記号・タイトル）と一致させる
- difficulty は「diff 1882」のように数値と色を添える。値は `tools/ap.py` から機械的に更新できるようにする
- 例題・練習問題・力試しの見出しの下に、決まった形のリストで並べる（正確な書式は工程6で style-guide に決め、スクリプトで検査する）。スクリプトは見出しとリンクから問題 ID と役割を拾い、ロードマップの集計・問題からページへの対応表・検証に使う
- 例題の解法は「方針」までを本文に書き、詳細は折りたたみ（ネタバレ防止）

### 6.7 出典

- 他者の記事は参考にしても文章を転載しない。各ページの末尾に「参考」として URL を残す
- atcoder.jp と codeforces.com は noai 指定のため開かない。USACO Guide は無断複製を禁じる規約なので構成の参考にとどめる。ikatakos 氏の記録（CC BY 4.0）は問題文を引用した節を使わない（research/00 §7.5）

## 8. 技術構成

### 8.3 生成スクリプト

### 8.4 表示

- 検索：`lang: ja` に加え、文字種の境目で区切る `separator` を設定する（research/10 §2.4：30問中29問で正解のページが出る）
- 数式：KaTeX 0.16.47 を同梱し、`pymdownx.arithmatex`（generic）で描画する
- 図：Mermaid（Material の標準の統合）。Mermaid は CDN から読まれるので、欠けると困る図は SVG にする
- レベルのバッジ：AtCoder の色に合わせ、ページ上部にテンプレートの上書きで表示する
- ライトとダークの切り替え、スマホ表示に対応する

### 8.5 動く図

- 素の JS ＋ SVG の小さな部品にする。「状態の列を先に全部作り、i 番目を描く」方式で、外部ライブラリを使わない（research/10 §3.3）
- 共通部品（ステップ送りの操作：最初・前・次・最後・自動再生・速度、キーボードとスワイプ）を1つ作り、図ごとに「状態の列を作る関数」と「状態を描く関数」だけを書く
- 埋め込みは `<div class="viz" data-viz="<名前>" data-config="…">` の形。instant navigation の下でも動くよう `document$` で初期化する
- JS が動かない環境（claude.ai での読み込みを含む）でも意味が通るように、図の前後に文章で要点を書く
- 優先度の高い図（研究の提案から）：BFS の層とキュー、ダイクストラのヒープ、01-BFS の deque、ワーシャルフロイド、Kruskal と Union-Find、セグ木の更新と取得、遅延伝播、二分探索の境界、尺取り、いもす法、ナップサックの表、オイラーツアーと列の対応、LCA のダブリング、直径の2回探索、最大流の残余グラフ。合わせて20〜30個を目安にし、catalog の `visual` で割り当てる

| Zensical | 試験ビルド（失敗してもデプロイは止めない） |

### 8.7 デプロイ

## 9. 使い続けるための仕組み

### 9.1 確認問題・進捗チェック（ユーザーの回答で3つとも入れる）

| 機能 | 形 | 保存 |
| --- | --- | --- |
| 確認問題 | 本文の要所に「なぜ？」「この場合は？」の小問を置き、答えを折りたたみ（`pymdownx.details`）で隠す | 保存しない |
| 練習問題の「解いた」チェック | JS が本文の問題リストの各問題にチェック欄を付ける。ロードマップにレベル・分野ごとの解いた数を出す | localStorage（キーは `kyopro-atlas:v1:solved:<問題ID>`） |
| ページの「理解した」チェック | ページ上部（テンプレートの上書き）にボタン。知識マップで理解したページを塗り、前提をすべて理解した未読のページを「次の候補」として強調する | localStorage（`kyopro-atlas:v1:understood:<page-id>`） |

- 端末間の同期はしない（要件）。Safari は7日間使わないとデータを消すことがあるので、「使い方」のページに書き出し・読み込み（JSON のコピーと貼り付け）を置く。これは同期ではなく手動の退避

### 9.2 解説（claude.ai ＋ GitHub 連携）

- **方式**：従来のプロジェクトに GitHub 連携で `docs/`（`docs/assets/` を除く）・`snippets/`・`claude/` を入れる（research/10 §3.6 の方式 A）。教材が大きくなると claude.ai が自動で検索方式（RAG）に切り替わる前提で手順を書く。加えて、利用者がメッセージに `llms.txt` の URL を書いたときは、公開サイトから最新のページを読む方式 B も手順に書いておく
- **手順ファイル**：`claude/explain.md`（git で追跡。プロジェクトの指示から参照）。プロジェクトの指示に貼る短い文は `claude/project-instructions.md` に置く
- **手順の骨子**：
  1. 開催中のコンテスト（ABC・ARC・AGC）の問題なら解説しない（AtCoder生成AI対策ルール）
  2. 問題はスクリーンショットか利用者の要約で受け取る。atcoder.jp のページを取得しない
  3. 利用者が考えたことを聞き、「ヒントだけ」か「解説まで」を選んでもらう
  4. 索引（`docs/llms.txt`）で関連ページを探す。検索方式のときは、手法名・別名・問題のサインで言い方を変えて複数回検索する。必要なページだけを読む
  5. 教材の用語と記法で解説し、該当ページ・節の URL を示す。教材にない知識はそうと明示する
  6. 解けなかった原因を一言で分類する（知識不足／気づけなかった／実装ミス／時間不足）
  7. 頼まれたときだけ、記録用スキルに貼り付ける「記録用まとめ」を決まった形で出す
- 実機で確かめること（工程9）：GitHub 連携でフォルダ選択後に追加したファイルが同期で含まれるか、`llms.txt` の URL を渡したときに各ページを続けて取得できるか、検索方式での索引の引かれ方

### 9.3 記録（Claude Code のスキル）

- `.claude/skills/record-problem/SKILL.md`（git で追跡）。`disable-model-invocation: true` で、利用者が `/record-problem` と打ったときだけ動く
- 入力：問題 ID と原因など、または claude.ai が出した「記録用まとめ」の貼り付け
- 処理：`tools/ap.py` で問題の実在・タイトル・difficulty を確かめ（atcoder.jp は開かない）、`notes/<日付>_<問題ID>.md` を作る。先頭の front matter に、日付・問題のリンク・原因の分類・学んだこと（一言）・関連ページ・教材の改善案（あれば）を書く
- 集計機能は持たない。`notes/` は git の追跡外

## 10. 制作の進め方

### 10.1 工程

| 工程 | 内容 | 終わりの条件 |
| --- | --- | --- |
| 3 設計 | この設計書と catalog | catalog の検証が通る |
| 4 見直し | 別のサブエージェントが設計書と catalog を批判的に読み、直す | 指摘への対応を記録 |
| 5 決定の提示 | 決定の一覧をユーザーに出し、確認を得る | ユーザーの承認 |
| 6 土台作り | mkdocs.yml・テンプレート・CSS/JS（進捗・動く図の部品・知識マップ）・schema・tools・CI・textlint・style-guide・用語集の種・各 type のひな形 | 空のサイトがビルド・デプロイされ、検証が通る |
| 7 試作 | 性質の違うページを8つ前後作り、設計と style-guide を直す。ユーザーに見てもらう | ユーザーの確認 |
| 8a 骨格 | catalog から全ページの枠（front matter・要点の囲み・要約）を作る。逆引き・知識マップ・ロードマップ・索引がこの時点で動く | 全ページが stub 以上 |
| 9 スキル作成 | 解説手順と記録用スキル。**骨格のすぐ後に前倒しする**（要件の順では本制作の後だが、骨格ができた時点で辞書として使い始められるため。ユーザーの確認を取る） | claude.ai での実機の確認 |
| 8b 本文 | 基礎・水 → 青 → 黄 → 発展の順。横断ページは並行して育てる | 全ページが done |
| 10 全体の検証 | リンク切れ、前提の矛盾、用語・記法の不統一、事実の誤り | 検証の記録 |

試作の候補（性質の違うもの）：答えの二分探索（基礎）、bitDP（水・DP）、遅延セグメント木（青・データ構造・動く図）、期待値の線形性（水・数学）、状態を頂点にする最短路（水〜青・グラフ）、ranges と views（C++）、HL 分解（発展の概要）、括弧列（題材別）、逆引き辞典と知識マップ（生成）。

### 10.2 サブエージェントの使い方

メインのセッションは設計と一貫性の管理に専念する。

| 役割 | 単位 | 渡すもの | 返すもの |
| --- | --- | --- | --- |
| 執筆 | 本格的なページは1〜2ページ、基礎・発展・C++ は同じ分野の3〜6ページ | 設計書、style-guide、用語集、記法のページ、catalog の該当項目、調査レポートの該当節、試作で確定した見本のページ | ページの Markdown、snippets、図、未解決の点の報告 |
| 事実の検証 | 執筆とは別のエージェント | 書かれたページ、検証のチェックリスト | 指摘の一覧（計算量・定理・ACL の API・問題の内容と difficulty・リンク） |
| コードの検証 | 同上 | snippets | コンパイル・実行の結果と指摘 |
| 分かりやすさの検証 | 同上。レート1000前後の読者の立場で読む | ページ、前提のページ | 分かりにくい箇所・飛躍・「なぜ」の欠け |
| 修正 | 執筆者か別のエージェント | 指摘の一覧 | 直したページ |

- 書いた本人に採点させない
- 並列の数は、1回に動かすのを10本程度までにする
- 1バッチ（例：ある分野の水のページ群）ごとに、執筆 → 検証 → 修正 → 機械的な検証 → commit・push

### 10.3 進捗の管理と再開

- 各ページの `status`（stub → draft → reviewed → done）を front matter に持ち、`tools/gen_site.py` が制作状況の表を生成する
- `planning/progress.md` に工程・バッチ・次にやることを書く。セッションが切れたら、これと制作状況の表から再開する
- 新しく決めたことは decisions.md に、設計の変更はこの文書の変更履歴に残す

| AtCoder の生成AIのルールへの抵触 | 解説の手順で開催中のコンテストの問題を断る |

## 12. 決定の一覧（工程5でユーザーに示す要約の元）

1. 構成：15の分野（はじめに・横断・基本テクニック・考察・DP・グラフ・木・データ構造・整数論・代数・数え上げ・確率・ゲーム・文字列・幾何・その他・題材別・C++）、目次の初版で367ページ
2. レベル：基礎〜1199／水／青／黄／発展2400〜。「まとまって現れ始める帯」で決め、根拠の問題を残す。応用は節にレベルの印
3. 分類：分野・レベル・手法の種類・出題頻度・問題のサイン・前提。一覧はスクリプトで生成
4. 境界の主な決定：期待値 DP とゲーム DP は「数え上げ・確率・ゲーム」に置く、Union-Find の構造は「データ構造」、使い方は「グラフ」、括弧列・mex・順列・XOR などは「題材別」の案内ページ
5. 粒度：セグ木5ページ、区間 DP・桁 DP・bitDP は基本と応用に分ける、C++ は約15〜20ページ＋C++ の逆引き、考察は入口＋短いページ8本、幾何は8ページ前後
6. ページの構成：冒頭に要点の囲み、なぜ正しいか、自分で実装できる粒度の処理の流れ、ACL の囲み、例題（解法は折りたたみ）、練習問題（チェック付き）、確認問題
7. コード片：要点だけ本文に、完全なプログラムは別ファイルで GCC 15.2・gnu++23 でコンパイル・実行して確かめる
8. 問題：ABC 優先、例題1〜3・練習2〜6・力試し0〜3、第三者の解説で裏付けたものだけ
9. 技術：Material 9.7.7 固定、生成は独立スクリプト、日本語検索の調整、KaTeX 同梱、知識マップは Cytoscape.js、動く図は自作の小さな部品、索引は `docs/llms.txt`
10. 進捗：確認問題（折りたたみ）、練習問題の解いたチェック、ページの理解したチェック（localStorage、書き出し・読み込みあり）
11. claude.ai：GitHub 連携で `docs/`・`snippets/`・`claude/` を入れる。手順は `claude/explain.md`。開催中のコンテストは断り、atcoder.jp は開かない
12. 記録：`/record-problem` スキルで `notes/` に1問1ファイル
13. 制作順：土台 → 試作（ユーザーの確認）→ 骨格 → 解説と記録の仕組み（前倒し）→ 本文（基礎・水 → 青 → 黄 → 発展）→ 全体の検証

## 13. 比べた案

| 論点 | 案 | 採否と理由 |
| --- | --- | --- |
| A ページの粒度 | 細かく（調査の key ごと、約450）／粗く（分野ごとの大ページ、約150）／中間（名前で引かれる単位、約330〜380） | 中間。細かすぎると薄いページが増え前提の網が密になりすぎる。粗いと辞書として引きにくく、レベルの違う内容が混ざる |
| B 分類の持ち方 | tags プラグインの階層タグ／単一値キー＋生成した一覧 | 単一値キー。二重管理がなく検証しやすい。Zensical でも同じに動く |
| C 問題の ID の持ち方 | front matter に列挙／本文のリストから拾う | 本文から拾う。要約と一緒に書く本文と二重にならない |
| D 期待値 DP・ゲーム DP の置き場所 | DP の章／数え上げ・確率・ゲームの章 | 後者。つまずきの原因が「なぜ後ろ向きか」「自己ループ」「必勝・必敗の定義」という数学の側にあるため（research/07 §7.6）。DP の状態・遷移の説明も同じページに書き、DP の一覧には kind で出す |
| E claude.ai の参照方式 | A 本文まで同期（大きくなると RAG）／B 索引だけ同期し本文は公開サイトから取得／C 新しい Projects | A を基本に B を手順に併記。A は公式の標準の使い方。B は同期が要らないが、利用者が URL を書く必要がある。C は提供が段階的 |
| F C++ 章の粒度 | 36ページ／11ページ／15〜20ページ＋逆引き | 15〜20ページ＋逆引き。書き方1つずつにアンカーを付ければ、逆引きから直接たどれる |
| G 解説の仕組みの時期 | 要件の順（本制作の後）／骨格の直後 | 骨格の直後（ユーザーの確認を取る）。骨格の時点で索引と要約がそろい、辞書として使い始められる |
| H 数式 | KaTeX／MathJax 4 | KaTeX。約3.7倍軽く、競プロで使う記法はすべて描ける |
| I 知識マップ | Cytoscape.js（ブラウザで配置）／ビルド時の Graphviz SVG | Cytoscape.js。クリック・絞り込み・理解度の色分けが要る |
| J 題材の扱い | タグだけ／案内ページ（題材別の分野） | 案内ページ。解けなかった問題の「対象」（括弧列など）から引く入口になる |
