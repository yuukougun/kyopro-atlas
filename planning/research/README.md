# 調査の手引き

分野別の調査を担当するサブエージェントへの共通の指示。各担当はこの手引きに従って自分の分野を調べ、指定のファイルを書く。調査結果は工程3（設計）で、目次・レベル割り当て・前提関係・例題選び・横断ページの材料として使う。

## 1. プロジェクトの概要

- **目的**：AtCoder で緑上位〜水色手前（レート961、パフォーマンス1100〜1450。ABC は D まで安定、E は時々）の学習者が、黄色（2000）に到達するための網羅的な「読んで学ぶ教材」を作る。ABC が中心で、ARC 的な考察は少しだけ
- **使われ方**：読み通す本ではなく、ABC で解けなかった問題をきっかけに引く「辞書」。claude.ai のプロジェクトから教材を参照して、解けなかった問題を解説させる使い方もする
- **形式**：Material for MkDocs の静的サイト。1ページ＝1つの手法・概念が基本。各ページのメタデータ（レベル・分野・前提ページ・問題のサインなど）から、逆引き辞典・知識マップ・ロードマップ・Claude 用の索引を自動生成する
- **内容の方針**：コード全体（実装）は載せない。意味と「なぜそうなるか」を最優先にし、自分で実装できる粒度の処理の流れ（保つべき性質、各操作の手順、境界の扱い）を書く。ACL にある機能は、対応する名前と最低限の使い方を囲みで添える。学習者は将来、自作ライブラリを作る予定
- 詳しくは [requirements.md](../requirements.md) と [decisions.md](../decisions.md) を読むこと

## 2. レベルの定義（重要）

レベルは「その知識が主に必要になる問題の difficulty 帯」で決める。difficulty は AtCoder Problems の推定値。

| レベル | difficulty | 扱い |
| --- | --- | --- |
| 基礎 | 〜1199（灰・茶・緑） | 短いページ。初歩の説明は省き、応用の型・落とし穴・上位の手法とのつながりに絞る |
| 水 | 1200〜1599 | 本格的に扱う |
| 青 | 1600〜1999 | 本格的に扱う |
| 黄 | 2000〜2399 | 本格的に扱う |
| 発展 | 2400〜 | 概要だけの短いページ（何ができるか・どんな問題で使うか・ライブラリでの使い方） |

同じ手法でも、易しい使い方から難しい使い方まで幅がある。「その手法を知らないと解けない問題が、まとまって現れ始める帯」を目安にし、根拠にした問題と difficulty を必ず添える。1つの手法で「基本は水、応用は青」のように分かれる場合は、ページを分けるべきか節で足りるかの意見も書く。

## 3. 守ること

1. **atcoder.jp とそのサブドメインのページ（問題・解説・ブログ・提出など）は開かない。** 問題ページと解説ページには noai 指定がある。検索結果に出てくるのは構わないが、開かない
2. 問題の実在・タイトル・difficulty は `tools/ap.py` で確認する（§4）。**記憶だけで問題IDを書かない。** ap.py で見つからない ID は書かない
3. 問題の内容（何を問い、どの手法で解けるか）は、第三者の解説記事などで裏付けが取れたものだけを候補にする。裏付けに使った URL を残す。裏付けが取れないものは「未確認」と明記するか、載せない
4. 他者の文章を転載しない。要点を自分の言葉でまとめ、参考にした資料の URL を残す
5. 事実（計算量・定理・API の仕様など）は一次資料か信頼できる資料で確かめる。ACL のドキュメントは手元の `~/lib/ac-library-master/document_ja/` にある（CC0）
6. ほかの担当の範囲（§6）には深入りしない。境界にある項目は、どちらに置くべきかの意見として書く
7. 書いてよいのは自分の担当の成果物ファイルだけ。git の commit はしない。リポジトリのほかのファイルは変更しない
8. Web の資料を読むときは、そのサイトが AI による利用を明示的に断っていないかに注意する（noai などの指定や利用条件に AI の利用を禁じる記述があれば使わない）。**codeforces.com にも noai 指定がある**（調査中に判明）ので開かない

## 4. 問題の確認ツール `tools/ap.py`

AtCoder Problems の公開データ（2026-10-21 取得のキャッシュ）を引く。リポジトリのルートで実行する。

```bash
python3 tools/ap.py show abc300_a abc244_f   # 実在確認。タイトル・difficulty・色/レベル・日付・URL
python3 tools/ap.py search "shortest" --prefix abc --min 1200 --max 1999   # 英語タイトルの部分一致
python3 tools/ap.py contest abc479           # コンテストの問題一覧
python3 tools/ap.py show --json typical90_a  # JSON で出力
```

- 出力の `diff=` は AtCoder Problems の表示と同じ補正後の値。`（参考値）` は推定が不安定なもの。`diff=なし` は推定値がない（典型90問・EDPC などのレーティング対象外のコンテスト）
- 典型90問の問題IDは `typical90_a`〜`typical90_cl`、EDPC は `dp_a`〜`dp_z`、TDPC は `tdpc_*`、アルゴリズムと数学 演習問題集は `math_and_algorithm_*`。タイトルの（★n）は作問者による難易度
- データは手元のキャッシュだけを読む。`fetch` は実行しない（取得済み）

## 5. 成果物

### 5.1 調査レポート `planning/research/NN-<分野>.md`

次の節を持つ。長さに制限はない。設計と執筆の材料になるので、具体的に書く。

1. **調べた資料**：資料名・URL・何の参考にしたか
2. **分野の全体像**：サブ分野の構造と、項目どうしの関係（何が何の前提か、どれとどれが混同されやすいか）
3. **項目一覧**：表（項目名／レベル／根拠の問題と difficulty／前提／ACL での対応／ページ分割の案）。詳細は topics.yaml に書く
4. **項目ごとのメモ**：項目ごとに、次の観点で分かる範囲を書く
   - 何ができるか、なぜそれで正しく動くか（直感的な説明の筋道）
   - 学習者がつまずきやすい点、よくある誤解やバグ
   - 図にすると伝わるもの、動く図（ステップ送り）が効くものと、その見せ方の案
   - 確認問題（「なぜ？」「この場合は？」を問う小問）の案
   - 問題のサイン（制約・言い回し）。逆引き辞典に使う
   - 似た手法との使い分け
5. **例題・練習問題の候補**：表（問題ID／タイトル／difficulty／使う手法／何を問う問題か（自分の言葉で一言）／裏付けの URL）。1項目あたり2〜6問。易しいものから難しいものまで幅を持たせる。ABC を優先し、典型90問・EDPC・ARC なども使ってよい
6. **横断ページへの材料**：逆引き辞典（制約・言い回し → 手法）、似た手法の使い分け、早見表、用語集に入れるべき項目
7. **設計への提言**：ページの分け方、レベル割り当てで迷う点、見落としやすい項目、ほかの分野との境界

### 5.2 項目一覧 `planning/research/NN-<分野>.topics.yaml`

レポートの項目一覧を機械で扱える形にしたもの。設計で全分野を統合するのに使う。`python3 -c "import yaml,sys; yaml.safe_load(open(sys.argv[1]))" ファイル名` で読めることを確かめる。

```yaml
area: dp                      # 分野の略号（§6 の表の略号）
topics:
  - key: bit-dp               # 仮の識別子（英小文字・数字・ハイフン）。他分野の項目を指すときも key を推測して書いてよい
    title: bitDP
    aliases: [集合DP, bit DP]
    level: 水                 # 基礎 / 水 / 青 / 黄 / 発展
    level_evidence: "abc???_? (diff 1400) で必須"   # 根拠
    prerequisites: [dp-basics, bit-operations]
    acl: null                 # 対応する ACL の機能（例: atcoder::segtree）。なければ null
    signs: ["N ≤ 20", "部分集合を状態に持つ", "順番を決める（巡回セールスマン）"]
    compare_with: [bit-full-search]
    page: own                 # own（単独ページ）/ section-of:<key>（他ページの節）/ overview（発展の概要）
    visual: "部分集合を2進表記で並べ、遷移を矢印で示すステップ送り"   # 図・動く図の案。なければ null
    problems:
      - id: abc???_?
        difficulty: 1400
        role: example         # example（例題）/ practice（練習）
        summary: "何を問う問題かを自分の言葉で一言"
        evidence: "https://..."   # 内容の裏付けに使った URL
```

## 8. メインのセッションへの最終報告

作業を終えたら、最終メッセージは10行以内にする。書いたファイルのパス、項目数、例題候補の数、設計で判断が必要な点（3つまで）だけを書く。詳細はファイルに書く。
