# 執筆の手引き

執筆のサブエージェントに毎回渡す規則。設計書（design.md）・見直し（design-review.md）・部品の約束（interfaces.md）から、ページを書くのに要るものを集めた。用語の正規形は付録 A、資料に使えると確かめたドメインは付録 B。

- 版：2026-10-21 初版（工程 6）。2026-10-22 に §15（b2・b3 の決定）と §16（b4・b5 の決定）を追加。上位の決定との食い違いに気づいたら、自分で判断せず報告に書く
- 一緒に渡す見本のページは書き方の水準を示すもので、構成はまねない

## 1. 目的と読者

- 教材は AtCoder で黄色（2000）を目指す学習者が引く辞書である。読者はレート 1000 前後（ABC の D まで安定、E は時々）で、C++ の基本文法は分かるが現代的な書き方には不慣れ
- 解けなかった問題から名前・別名・問題のサインで引かれ、冒頭だけで「使えるか」を判断される。学ぶときは続きを読む
- claude.ai は索引から関連ページを探し、節の断片だけを読んで解説に使う。どの節も単独で意味が通るように書く
- 目標：このページだけで、なぜ正しいかが分かり、自分で実装できる粒度の処理の流れがつかめる

## 2. 必ず守ること

### 2.1 書いてよいもの

- 書くのは担当ページ `docs/<field>/<id>.md`、`snippets/<id>/`、そのページの図 `docs/img/<id>/` だけ。動く図の JS と試験は指示で頼まれたときだけ書く（§8）
- 共有のファイル（用語集・prh.yml・早見表・使い分け・catalog・問題の台帳）は直さず、報告に「提案」として書く。`tools/gen_site.py` の実行と commit はしない。生成部分（`<!-- gen:begin … -->` の間）は書かない（その節の見出しの置き方は §16-11）。例外として、本文の数字を計算したスクリプトは `tools/numbers/` に置く（§16-13）
- front matter で直すのは `complexity`（プレーンな文字。例：`構築 O(N)、更新・取得 O(log N)`。計算量のない guide・hub・pattern のページは null のまま。§16-12）・`stage`（書き終えたら `draft`）・`updated` だけ。節を足すなら `sections` にも足してよい（level はページと同じ。既存の anchor は変えない）。ほかの項目を変えたいときは提案にする
- 検索の重み（工程11、#52）：`tags` には題名か aliases にある検索語だけを書き、ありふれた語や漢字で始まる語は避ける。`search.boost` は手法の系統の主なページだけに 2 以下で付ける。変えたら `node tools/check_search.mjs` で上位を確かめる。Zensical では tags がページの下にラベルとして出るので、移るときは `hide: [tags]` で隠す
- `updated` は、読者に見える中身（本文・問題の行・図・取り込むコード片・誤字）を変えたときに直す。front matter だけ・生成部分だけの変更では直さない。道具 `fix_code_links.py` が作る所（コードの下の行と地の文の `snippets/…` のリンク。§9）の変更でも直さない。ページの末尾に段階と一緒に表示される（工程11、#9）
- `related` は近いものから順に書く。書いた順にページ下部の「関連」に出る（20 件まで。工程11、#56）
- `order`（章の中の並び）は、前提を先に置き、同じ話題は続けて置いて中はレベルの低い順にし、話題どうしは最初のページのレベルが低い順に並べる。分野の入口とナビはこの順に並ぶ（工程11、#58）

### 2.2 冒頭

```markdown
!!! abstract "要点"
    - **何ができるか**：区間への一括の加算・代入と、区間の和・最小値の取得を、どちらも $O(\log N)$ で行う。
    - **いつ使うか**：区間に一律に加算・代入し、区間の和や最小値を何度も答える。
    - **計算量**：構築 $O(N)$、更新・取得 $O(\log N)$
    - **前提**：[セグメント木](../ds/segment-tree.md)

<!-- textlint-disable -->
別名：遅延セグ木・Lazy Segment Tree・lazy segtree・…
<!-- textlint-enable -->

遅延セグメント木は、…（題名を主語にした 1〜3 文の導入）
```

- 要点の囲みは全ページの本文の最初に置く。骨格の要点を書き直してよいが、summary・signs・prerequisites と食い違わせない。計算量には条件（ならし・期待・前計算）も書く。guide・start・patterns・hub は項目を内容に合わせて変えてよい
- 「何ができるか」は 1 文目で何ができるかを言い、「このページ」「扱う」「紹介する」などの語と帯の名前（水・青など）を使わない。「いつ使うか」は問題文の言い回し・制約の形・立てた式の形で書き、手法名を入れない（summary・signs の規則と同じ）
- 囲みの後に、aliases をすべて並べた別名の行（揺れた表記も含むので textlint から外す）と、題名を主語にした導入を置く。どちらも最初の `##` より前に置く（検査される）
- 本文に `#`（H1）を書かない。題名はテンプレートが出す

### 2.3 見出しと節

- 見出しは `##` から。front matter の `sections` の各節を `## 見出し {#anchor}` の形で必ず置く。見出しにレベルの印を手で書かない（上の帯の節には、テンプレートが見出しと目次に印を付ける。工程11、#54）
- 節の level はページの level 以上。ページより低い内容は下位のページへのリンクで済ませ、基礎のページの節は青までにする。上位の帯の節は、最初に追加の前提をリンクで示す（「この節は [X](…) を前提にする。」の形。レベルは書き直さない）
- 見出しと sections の title に波かっこ `{` `}` を書かない。`集合 {a, b} の和 {#x}` のように組があると attr_list が末尾の `{#anchor}` を拾わず、anchor が変わる（python-markdown で確認）

### 2.4 文体

- だ・である調（です・ます を混ぜない）。1 文を短く、1 段落 1 つの主張。呼びかけは控えめにする。用語と表記は §7、記法は §6 にそろえる
- textlint で検査する。囲み・折りたたみの中で空行の後に続く段落は検査されないので、自分で確かめる

### 2.5 問題

- 載せるのは台帳 `data/problems.yaml` で「確認済み」の問題だけで、役割（例題・練習・力試し）は台帳と catalog のとおり。足す・外す・役割を変えるときは提案にする
- 問題文と入出力例を転載しない。要約は台帳の summary（問いだけ。手法名を書かない）を使う。summary が「（執筆時に確かめる）」なら、台帳の evidence の解説で問いを確かめて自分の言葉で書き、台帳の修正を提案する
- atcoder.jp の問題へのリンクは問題の囲み（§10）の中だけに置く。本文で触れるときは例題の見出しかページへリンクする

### 2.6 Web と出典

- atcoder.jp（サブドメインを含む）と codeforces.com は開かない（noai 指定）。問題の題名・difficulty は台帳と `python3 tools/ap.py show <ID>` で確かめ、記憶で問題番号を書かない
- 新しいドメインは読む前に `python3 tools/check_noai.py <URL>` で確かめ、noai・noimageai の指定や AI の利用を断る規約があれば使わない
- 他者の文章を転載しない。参考にした資料はページ末尾の「参考」に残す（§11）

### 2.7 コード

- 本文に ```` ```cpp ```` で C++ を直接書かない。C++ は snippets からの取り込みだけ、擬似コードは ```` ```text ````（§9）

## 3. 書き方の原則

- 「何ができるか」の次に「なぜ正しいか」「なぜ速いか」を書く。手順の羅列で終わらせない
- 自分で実装できる粒度の処理の流れを書く：保つ性質（不変条件）、各操作の手順、境界（半開区間・空区間・単位元・番兵）。コードの全体は載せない
- 必要になる場面（素朴な方法がなぜ間に合わないか）から入り、小さな具体例で一度動かしてから一般化する。図で伝わるものは図にする
- 1 ページで完結させ、前提の説明は繰り返さずリンクする。節の最初の文で何の話かを書き、「上の図」「前述の」に頼らない
- 目安を埋めるためだけの薄い節を作らない。§4・§5 は目安で、内容に合わせて並べ替え・省略する
- 基礎のページは初歩を省き、応用の型・落とし穴・上位の手法へのつながりに絞る。落とし穴は実際に起きる誤解・バグとその避け方を具体的に書く
- 確認問題（「なぜ？」「この場合は？」）を要所に置き、答えを折りたたむ（`??? question "確認問題：…"`）。長い証明も折りたたむ（`??? note "証明"`）
- 似た手法との使い分けは短く書く。「次に読む」は書かない（前提と次に読むはテンプレートが出す）

## 4. type ごとの構成の目安

- **technique（水・青・黄）**：要点 → 必要になる場面 → アイデアとなぜ正しいか（図）→ 処理の流れ → 計算量とその根拠 → 応用の型（サインを添える）→ 落とし穴 → ACL では → 例題 → 練習・力試し → 確認問題 → 使い分け → 参考
- **technique（基礎）**：要点 → 応用の型 → 落とし穴 → 上位の手法へのつながり → 問題
- **overview（発展）**：何ができるか → サイン → 計算量 → ライブラリでの使い方（`{#library}`）→ 学ぶための資料（定型の `{#resources}`）→ 例題 0〜2。短く書き、証明や実装の流れは資料に任せる。ACL・Library Checker に対応がないときと、問題が 0 問のときの書き方は §16-1〜5
  - 似た手法と比べるなら、定型の `## 使い分け {#comparison}` を 2〜4 行で、例題・練習の後、参考の直前に置き、似た手法とハブの節へリンクする（工程11、#67）
- **hub**：「何から引くか → 使う手法 → ページ」の表とリンクが本体。中身の説明は各ページに任せる。表の例題の列は相手のページの例題の小見出しか `#practice` へリンクしてよい（§16-8）
- **guide**：構成は自由。目安の例は debugging-checklist の「要点 → 導入 → 症状ごとの節 → 確認問題 → 参考」（§16-10）
- **thinking**：その型が使える合図 → 最小の例 → ABC の例題 2〜4（方針も折りたたむ）→ 関連する手法。証明の技法は体系的に教えない
  - 導入の後に「使える合図は N つある。…である。」の段落を置き、問題文の言い回しで合図を 2〜3 個書く。詰まったときの発想リストの対応する表へのリンクは、使い分け（なければ合図の段落の末尾）に置く（工程11、#65）
- **pattern**：題材の性質 → 「問われ方と手法の一覧」の節（anchor `overview`。中身の節として sections に置く）→ 「よく出る問われ方 → 使う手法 → ページ」の表。問題は行の代表だけで、表の「代表の問題」の列には行き先のページの問題の label を文字だけで書き、リンクは行き先のページに任せる（見本 bracket-sequence の形。§16-7・§16-9）
  - 表の後に行ごとの節を置く（見出しは「問われ方 → 手法（行き先の id）」）。表の「よく出る問われ方」の列は、その行の節へのリンクにする（§16-7。工程11、#66）
- **cpp**：一言 → 素朴に書くとどうなるか（同じ意味のコード）→ 版（いつから・AtCoder と手元の g++-15 で使えるか）→ 落とし穴（確かめた実例）→ 確認問題 → 関連。書き方 1 つずつに anchor を付ける

ACL に対応がある手法は「ACL では」の囲みに、名前・宣言・主なメソッド 2〜3 個と計算量・要件だけを書く。ACL v1.6 のドキュメント（`~/lib/ac-library-master/document_ja/`）で確かめ、使い方の例は snippets から取り込む。

```markdown
!!! info "ACL では"
    `dsu d(n);`。`d.merge(a, b)`・`d.same(a, b)`・`d.size(a)` はどれもならし $O(\alpha(N))$。
```

ページの題の部品を自作した実装（ライブラリに入れる形の struct）は、「自作するとき」として次のように置く（工程11、#64）。節の中の変種（双対セグメント木・偶奇の Union-Find など）と使い方の例には当てない。

- **置き場所**：処理の流れの節の中で、手順の擬似コード（なければ手順の説明）の後に置く。境界の小見出しの前でも後でもよい。上の帯の自作の節（lazy-segment-tree#invariants など）があればその節の終わり、発展の概要は `#library` に置く
- **折りたたむか**：ACL に同じ部品があり「ACL では」の囲みを置くなら、`` ??? note "自作するとき：`型名`（ACL の `名前` に当たる）" `` に入れる。ACL にない部品と、ACL の部品では書けない操作（BIT 上の二分探索など）は折りたたまずに置く
- **ACL との対応**：折りたたむときは最初の段落に、ACL にそろえた名前と、そろえていない名前・返り値・引数を書く（「根を求める関数は `find`（ACL では `leader`）」）。開いて置くときは、同じ節のコードより前の段落に、ACL にないので自作すること（書けない操作なら理由）と、そろえた ACL の名前（Sparse Table の `prod`）・そろえていない名前と返り値を書く。違いは library-design#acl-names の表にもまとめる（行を足すのは提案）
- **名前**：メンバ関数の名前・引数の順・0-indexed・半開区間は ACL にそろえる。コンストラクタは ACL のドキュメントの「コンストラクタ」の項の形（`dsu(n)`・`fenwick_tree(n)`・`segtree(v)` など）を持たせ、足したもの（配列から作る `BIT(a)` など）は違いに書く。そろえないのは本文の手順や図と名前を合わせたいとき（Union-Find の `find`）だけにする。同じ部品を別のページでも自作するなら、名前をそろえるか違いを書く（`lower_bound(w)` と `kth(k)`）
- **試験とリンク**：折りたたむときは、コードの後の段落に試験で確かめたこと（素朴な方法との照合・乱数）を 1〜2 文で書き、library-design の #interface・#verify へのリンクの文（下の例の最後の文）で結ぶ。開いて置くときは、リンクの文をコードの前か後の段落の末尾に置き、試験の文は任意。確認用の問題（verify）はテンプレートがページ下部に出すので、並べ直さない（触れるなら judge.yosupo.jp へのリンクにする。§15-5）

## 5. 分野ごとの書き方

- **basics**：判定の単調性と保つ性質を主役にする（二分探索は ok 側と ng 側の不変条件、尺取り法は左端を進めても右端が戻らない理由。単調なのは各 $l$ に対する右端 $r(l)$）。累積和・いもす法は半開区間と添字の対応を式で示す。貪欲法は正しさの理由（交換しても悪くならない）を必ず書く
  - 計算量の目安の数値（1 秒に $10^8$ 回・log の値・メモリに置ける個数）は complexity-estimation の値にそろえる（reverse-index-constraints#magnitudes の表も同じ値）
  - 区間を座標圧縮するときは、閉区間を半開区間 $[l, r+1)$ に直してから両端点を入れる書き方にそろえる
  - 三分探索は凸性の確かめ方を書き、整数の関数では隣との差の符号で二分探索する方法を主役にする
  - 交換論法で導いた比較は比の割り算にせず、$t_i w_j < t_j w_i$ の掛け算の形のまま使う。$(0, 0)$ の要素はどれとも比べられず、比べられない関係が推移的でなくなる（$(1, 2)$・$(0, 0)$・$(2, 1)$）ので先に除く。符号が混じるなら符号でグループに分けてから比べる（持ち主は exchange-argument#ratios）
  - 区間に 1 を足す操作の最小回数・可否は、両端の外も含めて差分を $N + 1$ 個取ると端の場合分けがなくなる（0-indexed で $A_{-1} = A_N = 0$ とし、$d_i = A_i - A_{i-1}$。$d_0 = A_0$、$d_N = -A_{N-1}$）。最小回数は正の差分の和で、負の差分の和の絶対値と等しい（difference-sequence と定義をそろえる）
  - mex を印の配列で求めるときは、配列の大きさを $N + 1$ にし（$N$ 個の値の mex は $N$ になりうる）、$N$ より大きい値は読み飛ばす（持ち主は patterns/mex#pitfalls）
- **thinking**：主客転倒は和の順序の入れ替えまで、余事象は補集合と 2〜3 条件の包除まで、偶奇・不変量は必要条件の見つけ方まで（一般の包除原理・期待値・ゲームは comb）
  - basics・ds と同じ考え方を扱うときは、thinking には気づき方（合図）と最小の例を、basics・ds の持ち主の節には手順・証明・実装・落とし穴を書き、持ち主でない側は要点 1〜2 文と持ち主の節へのリンクにする（例：区間加算の最小回数は basics/difference-sequence#min-operations、隣接 swap の最小回数は ds/inversion-number#adjacent-swaps が持ち主。工程11、#70）
- **dp**：状態の意味（「$\mathrm{dp}[i][j]$ ＝ …」を言葉で 1 文）、遷移（場合分けと式、小さな表の図）、計算順序（依存の向きと、その順でよい理由）、初期値と答え（最適化は ±∞、数え上げは $\mathrm{dp}[0] = 1$、可否は true。答えの取り出し方）を必ず書く。その状態で足りる理由（先の選び方が状態だけで決まる）と計算量（状態数 × 遷移数）も書く。高速化は遷移の式の形から選ぶ（dp-speedup-overview）
  - 積の条件を数える DP の初期値は空の積の 1 にする（余りを状態にするなら $\mathrm{dp}[0][1 \bmod M] = 1$）
  - メモ化再帰は「未計算」の印を答えと別に持つ（-1 などの印が答えになりうるなら、計算済みかを表す配列を別に置く）
  - 1 本の配列で書き換えてよいかは「同じ段で書き換えた値を同じ段で読むか」で決める。0-1 ナップサックは容量の大きい方から回す。グループから 1 つ選ぶ遷移も、重さが正なら容量を外側（大きい方から）・グループの品物を内側に回せば 1 本で書ける
  - 1 本の配列で書き換える DP で、その行で読む値が同じ行の書き込みで変わるなら、読む値を先にすべて集めてから書き込む（インライン DP）
  - 品物を取り除く更新（戻す DP）は追加と逆向きに回す。0-1 は追加が容量の大きい方から・削除が小さい方から、個数制限なしは追加が小さい方から・削除が大きい方から
  - 数え上げの区間 DP は、1 つの対象がただ 1 つの分け方に対応する位置（左端の相手など）で分ける。任意の位置で 2 つに分けると重複して数える（長さ 6 の括弧列が 5 でなく 6 になる）。最小化では重複は害にならない
  - 下の桁から決める桁 DP の上限のフラグは「ここまでの下の桁だけを比べて上限より大きいか」を持ち、上限と異なる数字を置いた桁で上書きする（同じ数字なら引き継ぐ）
  - 異なる部分列を数える DP では $\mathrm{dp}[0] = 1$ が空文字列を表す。答えに空文字列を含めるかを長さ 1 の入力（含めると 2、含めないと 1）で確かめる
  - 二乗の木 DP が $O(N^2)$ になるのは、マージのループの範囲がそれぞれの部分木のサイズまでのときだけである。配列を長さ $N$ で回すと $O(N^3)$ になる。サイズの更新はマージのループの後に行う
  - Alien DP（最大化、$g(\lambda) = \max_k (f(k) - \lambda k)$）で同点の個数があるときは、罰金つきの問題で個数の少ない方を選ぶと決め、$\mathrm{cnt}(\lambda) \le K$ となる最小の整数 $\lambda$ で $g(\lambda) + \lambda K$ を答える（返った個数ではなく $K$ を掛ける）。値しか返せないなら $h(\lambda) = g(\lambda) + \lambda K$ を整数の三分探索で最小にする（持ち主は alien-dp#binary-search-lambda）
- **graph**：何を頂点・辺にしたかを小さな例の図で示す。BFS・01-BFS・ダイクストラ法は「距離の小さい順に確定させる」の特殊化として、何が確定を保証するかと壊れる例（負の辺など）を書く。計算量は頂点数 $N$・辺数 $M$ で書く。フローは中身より、どんなグラフを作るか（容量・コストの付け方と、なぜそれが答えか）を主役にする
  - 01-BFS の壊れる例は負の辺ではなく、実装の誤り（初めて見つけたときに距離を確定させる・重み 0 の辺の先を末尾に入れる・重み 2 以上の辺の先を末尾に入れる）で示す
  - 負の辺のある最短路は、負閉路の有無ではなく、答えを聞かれた頂点が負閉路から到達できるかで判定する。$\mathrm{dist}$ が $\infty$ の頂点からは緩和しない（$\infty$ に負の辺を足した値で誤って更新される）
  - 差分制約 $x_v - x_u \le w$ を辺 $u \to v$（重み $w$）にしたとき、$x_t - x_s$ の最大は $\mathrm{dist}(s \to t)$、最小は $-\mathrm{dist}(t \to s)$ である
  - 補グラフの探索の $O(N + M)$ は、未訪問の集合を走査して「残す」回数を元の辺に、「取り出す」回数を頂点に割り当てて示す
  - フローに帰着するときは「解 → 流れ」と「整数の流れ → 解」の両向きの対応を書く（片方だけでは最大値が答えと一致する根拠にならない）
  - 最大値の最小化を二分探索するときは、答えが候補の値（組のコストなど）のどれかに等しいので、候補をソートして添字で二分探索する（実数の二分探索を避ける）
  - 最小費用流で「定数 − 利得」と置いて非負にするときは、どの 1 単位の流れも定数を足した辺をちょうど 1 回通るように層を作る（通る回数が違うと定数の分がずれる）
  - カットの容量は S 側から T 側へ向かう辺だけを数える。カットの復元は残余グラフで s から届く頂点の集合で行い、飽和した辺をそのままカットとしない（容量 1 の辺が 3 本直列なら、3 本とも飽和するがカットは 1 本）
  - 個数を mod で数えた値の 0 を、存在の判定に使わない。正の個数でも余りが 0 になりうる（彩色数の包除で $k$ 色で塗れないと誤る。LGV・行列式でも同じ）。法を 2 つ使うか、法を乱択する（持ち主は chromatic-number#chromatic-number）
  - 頂点を共有してよい鎖での被覆は、推移閉包を取ってから頂点を共有しないパス被覆にする。覆わなくてよい頂点を通ってよい場合も同じ（$0 \to 1 \to 2$ で 0 と 2 だけを覆うなら、閉包なしでは 2 本と誤る。持ち主は dilworth-path-cover#antichain）
  - 下限付きの流れの最大化で、可能な流れを作るときの $t \to s$ の容量 $\infty$ の辺を残したまま `flow(s, t)` を呼ぶと、その辺の逆辺を通ってすでに流れた量も返る。返り値がそのまま合計の流量になる（持ち主は flow-lower-bounds#super-vertex）
  - BEST 定理の数 $\mathrm{ec}$ は、辺を区別し 1 本目の辺を固定した数（巡回シフトを同一視した数）である。始点 $s$ だけを決めた閉路は $\mathrm{ec} \times \deg^+(s)$、$s \ne t$ のオイラー路は辺 $t \to s$ を足してそれを 1 本目に固定して数える。$(\deg^+(v) - 1)!$ の出次数には自己ループを数え、行列木定理の行列には入れない。同じ種類の辺を区別しないなら個数の階乗で割るが、割れるのは始点を決めた列の数だけである（同じ自己ループ 2 本の $\mathrm{ec} = 1$ は $2!$ で割れない。持ち主は matrix-tree-theorem#best-theorem）
  - 最小シュタイナー木の DP は辺の重みが 0 以上のときだけ使える（木にできることとダイクストラ法の両方に要る）。重み 0 の辺は 2 つの部分の両方に入っても値が増えないので、復元で 2 回出ることがあり、印で除く（持ち主は steiner-tree#library）
  - 2-SAT の復元は「トポロジカル順で後ろの成分にある方を真」にする。Tarjan 法は成分を逆トポロジカル順に見つける（ACL の `scc_ids` は番号を付け直してトポロジカル順にし、頂点 $2i + 1$ を真として `id[2i] < id[2i+1]` なら真とする）ので、自作では番号の向きを確かめる（持ち主は two-sat#acl）
- **tree**：§6 の木の記法を使う。「なぜ」の要所（直径の 2 回探索・重心の性質・マージテクの log・HL 分解の軽い辺の数・重心分解の深さ・DFS 順と部分木の対応・Prüfer 列の全単射）は証明の筋を図で示す。小技（辺の値を子に寄せる・親を引数で渡すなど）は tree-basics へリンクする。ACL の囲みには「どの列にどのデータ構造を載せるか」を書く。パス状の木で再帰が深くなることに触れる
  - 頂点 $x$ が $u$-$v$ パス上にあるかを $d(u, x) + d(x, v) = d(u, v)$ で判定するときは、重みのない距離（辺の本数）で行う。重み 0 の辺があると、パスの外の頂点でも等号が成り立つ（持ち主は tree-path#pitfalls）
  - 木の同型・木のハッシュでは、子の名前を整列した列（多重集合）として扱い、名前の表は比べる木すべてで共有する。根のない木は中心（または重心）を根にし、2 個あるなら両方を試すか、間の辺に仮の頂点を足す（持ち主は tree-isomorphism#unrooted。tree-centroid#one-or-two とそろえる）
  - 木の制約つきの交換論法（01 on Tree など）では、$(0, 0)$ の頂点は並びのどこに置いても値が変わらず、比較が推移しないので、最初に親へまとめる（exchange-argument#ratios の「$(0, 0)$ は除く」の木の版。持ち主は tree-ratio-greedy#why-ratio）
- **ds**：BIT・セグメント木・遅延セグメント木・Union-Find などは「保つ性質」「各操作の手順」「境界（半開区間・空区間・単位元）」の 3 つの小見出しをそろえる（自作ライブラリ用）。ならし計算量かどうかを明記する。演算は「結合法則を満たす演算と単位元」と性質で言う（モノイドは用語集へ）
  - 取り消し付き Union-Find で成分の合計を持ち、取り消しの間に値を加える問題では、根の合計を「併合前の値を書き戻す」形で戻すと、その間に加えた値が消える。各頂点に「自分の下の合計」を持たせ、加算は $v$ から根までの経路すべてに足し、取り消しは子の合計の引き算にする。同じ成分どうしの併合（根が同じ）の記録を取り消すときは引かない（持ち主は rollback-union-find#offline-dynamic-connectivity）
- **math**：定理 → なぜ（短い証明か直感。長い証明は折りたたむ）→ 計算の手順 → 典型の型 → 落とし穴。群・環・体の語は使わない。基礎のページは落とし穴（負の数の割り算・オーバーフロー・逆元がない場合）を厚くする
  - 題材が閉区間で定まる手法（区間篩の $[L, R]$ など）は閉区間のまま書いてよい。そのときは冒頭で閉区間と明記する
  - 同じ落とし穴が複数のページにまたがるとき（指数の mod・逆元がない場合など）は、持ち主のページを 1 つにして、ほかはリンクで済ませる（持ち主はメインが決める）
  - 離散対数（BSGS）で $x = in - j$ の形の正の最小の解を返すときは、表の同じ値に大きい $j$ を残す。$x = 0$（$b = 1$）と正の最小を区別する
  - 行列式の掃き出しでは、ピボットの行をピボットで割らない（割ると行列式もその値で割られる。割るなら値を掛け戻す）。素数でない法では逆元がないので、互除法の形で掃き出す（持ち主は determinant#modulus）
  - XOR の畳み込みの逆変換（アダマール変換）は最後に $2^n$ で割るので、偶数の法（$2^{64}$ など）では使えない。AND・OR の畳み込み（ゼータ変換・メビウス変換）は足し算と引き算だけなので使える（持ち主は hadamard-transform#index-operations。zeta-mobius-subset#vs-xor も同じ趣旨）
  - 64 bit の法の掛け算は `__int128` の mulmod を mod-pow に置き、Montgomery・Barrett の掛け算と Miller-Rabin の底の選び方は miller-rabin#mulmod・miller-rabin#deterministic-bases に置く（§15-12 の持ち主の書き分け）
- **comb**：数える対象をまず明示し、小さい例の全列挙で式を確かめ、重複も漏れもない理由を書く。期待値 DP は「なぜ後ろから」・自己ループの移項・計算順序を、ゲームは必勝・必敗の定義と終局から決まる理由を書く（DP の部分は dp に従う）。mod の値は大小比較できないことに触れる
  - 期待値 DP で選択がある状態（どちらを選ぶかで期待値が変わる）の比較は、自己ループを移項した後の式で行い、mod の値ではなく実数か分数で比べる
  - 二項係数の範囲外を 0 とする約束だけでは空の組を落とすことがある。$x_1 + \dots + x_n = k$ の非負整数解の個数 $\binom{k+n-1}{n-1}$ は $n = k = 0$ で $\binom{-1}{-1}$ になるが、答えは 1 である。境界の値は別に確かめる
  - 約数包除で「ちょうど $d$」を倍数の値から引いて求めるときは $d$ の大きい順に、約数の値から引いて求めるときは小さい順に計算する
  - 連結なラベル付きグラフの数を全体から引いて求めるときは、頂点 1 を含む連結成分（大きさ $k$）の外を全体の数 $2^{\binom{N-k}{2}}$ で掛ける。連結なものの数で掛けると成分がちょうど 2 つのものしか引かれない（$N = 3$ で 4 でなく 5 になる）
  - 包除の和を DP にするときは、符号 $(-1)^{\lvert S \rvert}$ を値に掛けて運び、偶奇を状態に持たない（$\lvert S \rvert$ ごとに違う係数が掛かるときだけ個数を状態に持つ）
  - メビウス関数の篩は、素数 $p$ の倍数すべて（$p$ 自身を含む）で符号を反転し、$p^2$ の倍数だけを 0 にする
  - 高速ゼータ変換は和で累積したものなら戻せるが、max・min（上位 $k$ 個）で累積したものは戻せない（1 要素の集合で $(1, 0)$ と $(1, 1)$ が同じ $(1, 1)$ になる）。約数・部分集合の両方の落とし穴で、持ち主は zeta-mobius-subset
  - 鏡像法は「触れたら違反」の線（0 未満を禁じるなら $y = -1$）で折り返す。始点か終点が条件を破るときは式が 0 にならない（負の値も出る）ので、先に 0 を返す
  - 分割数 $p(n, k)$ は資料によって定義が違う（部分がすべて $k$ 以下・ちょうど $k$ 個・$k$ 個以下）。$n = 6$、$k = 3$ でそれぞれ 7・3・7 になる。ページの中で 1 つに決め、小さい値で確かめる
  - 閉路のある期待値を $a + bX$ の組で解くとき、$b = 1$（終わらない）かどうかは mod の値ではなく到達可能性で判定する（$1/(p+1)$ は mod $p$ で 1 になる）
  - 期待値 DP で状態ごとに「その状態に至る確率を掛けた値」を運ぶと、合流では足すだけで済む（条件付きの期待値で運ぶと、合流で確率の重みを付け直す必要がある）
  - 閉路のあるゲームの後退解析では、更新が止まった後に未確定で残る局面は、行き先に負けの局面がなく、未確定の局面が必ずある。これが引き分けの根拠になる
  - 連続値の確率を double で区分ごとに多項式の積分で求めるときは、$t = x + u$ と原点を区分の左端へ移してから $[0, 1]$ で積分する（$x^{d+1}$ の値の差を取ると、$x$ が大きいほど桁落ちする。持ち主は continuous-probability#library）
  - LGV 補題の行列式は、頂点を共有しない経路の組を、始点と終点の対応の置換の符号を付けて足したものである。交わらない組が恒等置換でしか作れないように始点・終点の番号を付けてから行列式を取る。番号を逆順に付けると逆順の置換の符号 $(-1)^{n(n-1)/2}$ が掛かる（$n = 2, 3$ で負、$n = 4$ で正。持ち主は lgv-lemma）
  - 非不偏ゲームの値（数）は double で持たず、分母を 2 の冪に固定した整数で持つ。左の選択肢の最大が右の選択肢の最小以上の局面は数にならないので、assert で確かめる（持ち主は partizan-games）
  - 第 1 種スターリング数は、符号なし $c(n, k)$ と符号付き $s(n, k) = (-1)^{n-k} c(n, k)$ を書き分ける。Library Checker の Stirling Number of the First Kind は符号付きを求める（持ち主は stirling-first。fps-basics・generating-function-counting でも同じ取り違えが起きうる）
  - partition-number・twelvefold-way は $p(n, k)$ を「部分がどれも $k$ 以下（部分が $k$ 個以下と同じ数）」で定めている。部分がちょうど $k$ 個の分割の数は $p(n - k, k)$ である
- **string**：配列の定義を 1 文で書く（例：$z_i$ は $S$ と $S[i, N)$ の最長共通接頭辞の長さ）。各位置で何を使い回すから線形かを書く。ハッシュは衝突の確率と mod・基数の選び方（乱択）に必ず触れる
  - 集合や多重集合のハッシュで等しい組を数えるときは、比べる組の数（およそ $N^2/2$）で衝突の確率を見積もる（$N = 2 \times 10^5$ なら組は $2 \times 10^{10}$ ほどで、32 bit のハッシュでは足りない）
  - Aho-Corasick 法・KMP 法のオートマトンを DP に使うときは、ならしの $O(1)$ が効かないので遷移表を埋める。終端の印は失敗リンク先から受け継ぐ（パターン abc と b なら、状態 ab は失敗リンク先の b の印を受け継ぐ。受け継がないと ab で b を見落とす）。持ち主は aho-corasick#inherit-terminal
  - 値そのもの（巨大な整数）を mod で比べるときは基数がないので、法の素数を乱択する（持ち主は hash-safety#what-to-randomize）
- **geometry**：整数のまま外積・内積で判定するのを基本にし、浮動小数点を避ける理由と使うときの誤差の根拠を書く。外積の符号の向き（反時計回りが正）を明記する
  - 偏角や角度の比較は、180 度未満の範囲（上半平面と下半平面など）に分けてから外積の符号で比べる（外積の符号は、2 つの向きの差が 180 度未満のときだけ大小を表す）
  - 外積の値どうしを掛けない（線分の交差判定などは、外積を符号 −1・0・1 にしてから掛ける）。座標が $10^9$ なら外積は $10^{18}$ ほどで、その積は `long long` を超える
  - 90 度の倍数の回転は三角関数を使わず整数の式で書く。盤面を（列, 行）＝ $(x, y)$ とみると $y$ が下向きなので、反時計回りの式 $(x, y) \to (-y, x)$ は見た目では時計回りになる
  - 2 乗の比較で大小が保たれるのは 0 以上の量どうしのときだけである（$(-3)^2 > 2^2$）
  - 凸多角形の辺のベクトルを外積の符号で比べてマージするとき（ミンコフスキー和）は、どちらの列も最も下（同じ高さなら最も左）の頂点から反時計回りに始める。始点がずれると向きの差が 180 度を超え、比較が壊れる（持ち主は advanced-geometry）
  - 回転キャリパーは一直線上の点を除いた凸包で行う。一直線上の点を残すと、対になる頂点を進める判定が止まり、直径を取り落とす（convex-hull#degenerate）
  - AtCoder は `-march=native` でコンパイルするので、CPU が FMA を持てば `a * b - c * d` が 1 回の丸めで計算され、小数の結果が手元と変わりうる（平行な $(0.1, 0.3)$ どうしの外積が 0 でなくなる）。小数の外積の符号や `== 0` に頼らない（持ち主は cpp-environment#march-native）
- **misc**：インタラクティブは質問回数の上限の根拠と flush、乱択は失敗確率の見積もり、bitset は 1/64 になる根拠を書く
  - bitset で速くなるのは定数倍（1/64）だけで、計算量の次数が 1 つ違う解法は救えない。$N \times N$ の bitset はメモリが $N^2/8$ バイト（$N = 10^5$ で $1.25 \times 10^9$ バイト）になることも見積もる
- **cpp**：版（`cpp_std`・`gcc_min`・`atcoder`）は g++-13 と g++-15 で確かめる。落とし穴は snippets の期待（`compile-error`・`warning`・`run`）で確かめた実例にする
  - `1 << 31` は「C++20 から規格で値（$-2^{31}$）が決まった。C++14・C++17 では処理系定義で、GCC では同じ値になる。シフト幅が型の bit 数以上なら、どの版でも未定義動作」と書く
  - AtCoder は `-ftrivial-auto-var-init=zero` でコンパイルするので、関数の中の大きな配列は呼ぶたびに 0 で埋められて遅い（手元で $10^5$ 要素の局所配列を持つ関数を $2 \times 10^5$ 回呼ぶと 0.05 秒が 1.03 秒になった）。作業用の配列はグローバルに置くか使い回す（持ち主は cpp-environment#auto-var-init）

## 6. 記法

- 数式は KaTeX。インラインは `$…$`、別行は前後を空行にした `$$…$$`。front matter には KaTeX を使わない（`O(N log N)`、`2×10^5`）
- 計算量：`$O(N \log N)$`（log の底は書かない）、`$O((N + M) \log N)$`、「ならし $O(\alpha(N))$」「期待 $O(N)$」
- 区間は半開区間 $[l, r)$ を基本にし、閉区間は「閉区間 $[l, r]$」と明記する。数式の外（図の代替テキスト・リンクの文字）に区間を書くときは §8 のとおり括弧をエスケープする
- インラインの数式の `\text{…}` の中に `$…$` を書かない（`$X_i = [i \text{ が条件を満たす}]$` のように数式を外に出す。中に書くと KaTeX が壊れ、赤字のエラーになる）。日本語の長い説明もインラインの数式に入れず、地の文にする（スマホで折り返せず、ページ全体が横にずれる）。どちらも check_pages が見つける（工程11、#31・#33・#61）
- 添字：問題文は 1-indexed、実装は 0-indexed。どちらで書くかを最初に示し、変換を明示する。例：$a_i = A_{i+1}$、$S_0 = 0$、$S_{i+1} = S_i + a_i$ とすると $[l, r)$ の和は $S_r - S_l$
- 文字：列の長さ・頂点数 $N$、辺数 $M$、クエリ数 $Q$、列 $A = (A_1, \dots, A_N)$、法 $m$（素数なら $p$）
- 整数：`$a \equiv b \pmod{m}$`、`$a \bmod m$`、`$\lfloor x \rfloor$`・`$\lceil x \rceil$`、`$a \mid b$`、`$\gcd(a, b)$`・`$\operatorname{lcm}(a, b)$`、`$\binom{n}{k}$`
- ビット：XOR は `$\oplus$`、AND・OR は `$a \text{ AND } b$`。確率 `$P(A)$`、期待値 `$E[X]$`
- DP の表は `$\mathrm{dp}[i][j]$`（斜体の積に見えないよう `\mathrm`）
- 木：$\mathrm{dep}[v]$（深さ）・$\mathrm{par}[v]$（親）・$\mathrm{sz}[v]$（部分木サイズ）・$\mathrm{in}[v]$・$\mathrm{out}[v]$（行きがけ番号・出る番号）・$S[v]$（根からの累積）・$\mathrm{lca}(u, v)$・$d(u, v)$（距離）。最短路は $\mathrm{dist}[v]$
- 文字列：長さ $\lvert S \rvert$、$S[i]$（0-indexed）、部分文字列 $S[l, r)$
- 表の中では `|` の代わりに `\lvert … \rvert`・`\mid` を使う。数式の中の日本語は `\text{…}` で囲む
- 表のセルのバッククォートの中の `|` は、そのまま書く（`` `v | views::reverse` ``）。このサイトの python-markdown の表では区切りとみなされず、`\|` と書くと逆斜線がそのまま出る（3.11 で確認）
- 数学のページは最初に「このページで使う記法」を 1〜2 行置き、[記法と用語の約束](../start/notation.md)へリンクする

## 7. 用語とリンク

- 付録 A の正規形（ページの題名の書き方）にそろえる。かっこ内は本文で使ってよい別の書き方で、ほかの別名は別名の行でだけ使う。揺れは prh.yml で検出する
- 人名の連結は ASCII のハイフン（Aho-Corasick・Sprague-Grundy）。題名がカタカナの手法は題名に従う（ワーシャルフロイド法）
- 半角英数字と全角文字の間に空白を入れる（「2 次元」「K 番目」「$O(N)$ で」「`lower_bound` で」）。全角の句読点・括弧の前後には入れない。和文の括弧は全角、句読点は「、」「。」
- 数を数えるときは算用数字（「2 回」「1 つ」）、用語の中の漢数字はそのまま（二分探索・二部グラフ・二乗）。K 番目の K は大文字
- ひらがなで書く語：すべて・できる・あらかじめ・ほとんど・または・および・かつ・ただし・すなわち・ごとに
- 数学の「組合せ」と一般語の「組み合わせる」を書き分ける。グラフは「閉路」、置換は「巡回」と言う
- リンクはファイルへの相対パス `../<field>/<id>.md` で書き、節は `#anchor` を足す。ほかのページの節へは、そのページが draft 以降（見出しがある）のときだけリンクする
- 用語へのリンクはページの中で最初に出たときの 1 回だけ（見出しの中ではしない）。ページのある手法名はそのページか節へ、ページのない語（状態・単位元・半開区間など）は用語集へ：`[単位元](../guide/glossary.md#identity-element)`
- 用語集の anchor は英小文字・数字・ハイフン（英語名が基本）。用語集にない語は本文で短く定義し、語・anchor・1〜2 文の定義を提案する（リンクは張らない。§15-1）

## 8. 図

- 静的な図を基本にし、状態が時間とともに変わるものだけ動く図にする。図の前後に文章で要点を書く（JS が動かない環境や claude.ai でも通じるように）
- **Mermaid**：小さなフローチャート・状態遷移・小さなグラフ。CDN から読まれるので、欠けると困る図は SVG にする
- **SVG**：`docs/img/<page-id>/<name>.svg` に置き、`![要点を言う代替テキスト](../img/<page-id>/<name>.svg)` で参照する。背景を白で塗る（透明にするとダークモードで読めない）。文字はテキストのまま（`font-family="sans-serif"`）、`viewBox` と、それと同じ比の `width`・`height` を付ける。1 枚の幅は 400 程度までにし、横に並べたいものは 2 枚に分ける（§15-8）。色だけで区別せず、線の種類やラベルも使う
- **動く図**：`<div class="kp-viz" data-viz="<名前>" data-config='{…}'></div>` で埋め込む。catalog の visual が priority 1 なら必ず作り、2 は余力があれば、3 は静的な図で代えてよい。JS は `overrides/assets/js/viz/<名前>.js` に `states(config)`（各ステップの `caption` を持つ状態の列。DOM を使わない）と `render` を登録し、`tests/viz/<名前>.test.mjs` に試験を書く（見本は binary-search）。色は kp.css の `.kp-v-*` の class で付ける。JS を頼まれていなければ、div と図の仕様を報告に書く
- 表は横に広げすぎない（スマホで読む。列は 4〜5 まで）
- **代替テキストとリンクの文字の括弧**（工程11、#50）：区間を書いて対にならない括弧ができるときは逆斜線でエスケープする（`![区間 \[1, 5) に +1](../img/imos/imos-1d.svg)`）。対にならない `[` があると画像として読まれず、図の代わりに文字とリンクが出る。check_pages がエラーにする
- **SVG の背景**（工程11、#32）：白い背景の rect は viewBox 全体を覆う（viewBox の左上が 0 でないときは x・y も合わせる。`width="100%"` は viewBox の左上からではなく 0 から塗る）。覆わない部分はダークモードで暗い帯になり、文字が読めない。check_svg が警告する
- **動く図の JS**（工程11、#51）：`data-viz` に書いた名前の JS（`overrides/assets/js/viz/<名前>.js`）がないと、公開中のページに赤字のエラーが出る。置き場だけを先に書かない。check_pages がエラーにする

## 9. コード片

- 載せるのは要点の数行と処理の流れ。完全なプログラムを `snippets/<page-id>/<name>.cpp` に置き、取り込む範囲を `// --8<-- [start:core]`〜`// --8<-- [end:core]` で囲んで、本文では次のように取り込む

````markdown
```cpp
--8<-- "lazy-segment-tree/usage.cpp:core"
```
````

- コードの下の行（「完全なプログラム：<ファイル名>（GitHub）」と、範囲に `mint` が出れば同じ行の型と modint へのリンク）は `tools/fix_code_links.py` が作るので、手で書かない。取り込みを足したら `python3 tools/fix_code_links.py --page <id>` を流す。CI が `--check` で確かめる（工程11、#8・#62）
- 本文から snippets のファイルを指すときは `` `snippets/<id>/<名前>` `` と書けば、同じ道具が GitHub へのリンクにする（工程11、#72）
- 取り込む範囲の外で定義した補助関数や表（`binom`・`comb`・`fact` など）を範囲の中で使うときは、どの前計算か（階乗と逆階乗の表・パスカルの三角形・範囲外の値など）を本文に 1 文で書く。binomial-precompute の該当の節（`#fact-ifact`・`#composite-mod` など）へリンクする（工程11、#62）
- 設定 `snippets/<page-id>/<name>.yaml`：

```yaml
compilers: [g++-15]          # C++ の章で版を確かめるなら [g++-13, g++-15]
flags: "-std=gnu++23 -O2 -Wall -Wextra"
expect: run                  # run（実行して出力が一致）／ compile-error ／ warning
cases:
  - {input: "3\n1 2 3\n", output: "6\n"}
```

- プログラムは `main` と `assert` を持つ完全なものにし、cases には空・1 要素・境界を入れる。問題の入出力例は使わない。完全なプログラムは提出用ではないので、入出力は手元で確かめるための自前の形でよい（問題の入力の形に合わせなくてよい。読者向けの説明は how-to-use#page-anatomy）。ACL は v1.6（`third_party/ac-library/`）で、`modint::val()` は `int` を返す
- 書き方：AtCoder の GCC 15.2（`-std=gnu++23`）で通る範囲で読みやすさを優先する。`#include <bits/stdc++.h>` と `using namespace std;` を使い、マクロ（`rep` など）と型の別名は使わない（`long long` と書く）。ただし、数論のコード片の `using u64 = unsigned long long;`・`using u128 = unsigned __int128;`（§15-9）と ACL の modint は例外で、modint は `using mint = atcoder::modint998244353;`（法が 10^9+7 なら `atcoder::modint1000000007`）を使ってよい。ループは素朴な for を基本にし、範囲 for・構造化束縛・ラムダ（比較関数・DFS・二分探索などの判定の関数、短い補助の関数など）は使ってよく、DFS は `auto dfs = [&](auto&& self, int v, int p) -> void { … };` の形にする。views・`println`・deducing this などを使うときは C++ の章の該当ページへリンクする。C++26 は使わない
- 変数名は §6 にそろえる（`n`・`a`・`dp`・`par`・`dep`）。添字は 0-indexed、区間は半開、改行は `'\n'`。入出力は最小限にして中心の関数を見せる
- 法が入力で決まるときは `using mint = atcoder::modint;` と `mint::set_mod(m);` を使ってよい（値を作る前に `set_mod` を呼ぶ）
- ACL のヘッダ名は下線のない `<atcoder/fenwicktree>`・`<atcoder/segtree>`・`<atcoder/lazysegtree>`・`<atcoder/modint>` などで、クラス名（`fenwick_tree`・`lazy_segtree`）とは違う
- 再帰ラムダの `-> void` は省かない。再帰の呼び出しより前に戻り値の型を決める `return` がないと、g++ は「use of … before deduction of 'auto'」のエラーにする
- 非再帰の DFS は、入るときに `v` を、出るときの処理のために `~v`（負の数）を積む形にそろえる（見本は `snippets/dfs/order.cpp` の `iterative` の範囲）
  - 例外：DFS 木の親が要るときは（頂点, 親）の組を積み、取り出したときに印と親を決める。積むときに印を付ける形は DFS 木を作らない（三角形 0-1-2 を 0 から回ると、親が 1→0・2→0 になり、DFS 木の 0-2-1 にならない）
- `using namespace std;` の下で std の名前と同じ関数名を作らない。`relation` は C++20 の概念 `std::relation` とぶつかり「reference to 'relation' is ambiguous」のエラーになる（g++-15 で確認）。`circle_relation` のように具体的な名前にする
  - グローバルの変数・ラムダに std の関数と同じ名前（`merge`・`print` など）を付けても「reference to … is ambiguous」になる（`auto merge = [](int a, int b) { … };` で g++-15 で確認）。同じ名前の関数（`int merge(int, int)`）ならオーバーロードで通るが、Union-Find・treap・マージテクの自作では `unite`・`join` などにする
- 法が $10^{12}$ 程度なら積は $10^{24}$ ほどで、`long long`（$2^{63} \approx 9.2 \times 10^{18}$）を超える。`__int128` を使う mulmod は持ち主の mod-pow に置き、ほかのページはリンクする
- `ios::sync_with_stdio(false);` を書いたコード片では、`printf`・`scanf`・`println` のように C の stdout・stdin を直接使う入出力を混ぜない（出力の順が入れ替わる）
- ranges のアルゴリズムの射影にメンバ関数のポインタ（`ranges::sort(v, {}, &mint::val)`）を渡すと、g++-13・g++-15 の `-O2 -Wall` で `-Warray-bounds` の誤警告が出る。射影はラムダ（`[](mint x) { return x.val(); }`）にする
- 1 つの snippet に名前の違う範囲（`[start:core]` と `[start:fold]` など）をいくつも置き、`"crt/crt-merge.cpp:fold"` のように範囲ごとに取り込める
- 折りたたみ（`??? note`）の中では、コードの囲みと `--8<--` の行を 4 字下げにすれば取り込める
- `#pragma once` は main のファイルに書くと g++ が警告（「#pragma once in main file」。g++-13・g++-15 で確認）を出すので、ヘッダの形のコードはそのまま snippets に置けない。`// #pragma once` のコメントにして本文で説明する（library-design）
- `mt19937_64` の出力の列は規格で決まるが、`uniform_int_distribution` などの分布を通した値は標準ライブラリの実装で変わりうる。乱数の値を期待の出力にしたコード片は「標準ライブラリが同じときに限る」と添える（cpp-math-functions#random と同じ注意）

## 10. 問題の載せ方

練習・力試しは目印の囲みに 1 問 1 行で書く（`data-role` は example・practice・challenge）。

```markdown
<div class="kp-problems" data-role="practice" markdown>

- [ABC340 E. Mancala 2](https://atcoder.jp/contests/abc340/tasks/abc340_e)（diff 1157）：円環に並ぶ箱の玉を取り出して順に配る操作を繰り返した後の、各箱の玉の数を求める。

</div>
```

- label は「コンテストの表示名 記号. 題名」（ABC340 E. Mancala 2、典型90 001. Yokan Party（★4）、EDPC A. Frog 1）。label・URL・diff は台帳の値にする（difficulty のない問題は `diff なし`）。行を `- abc340_e：要約` と書いて `python3 tools/fix_problems.py --page <id>` で埋めてもよい
- difficulty は、ない問題を「（diff なし）」、AtCoder Problems が参考値として出す問題（台帳の `experimental: true`）を「（diff 1856・参考値）」と書く。表の diff の列では、ない値を「—」と書く（工程11、#5・#76）。行は fix_problems.py が台帳から作るので手で書かない
- 例題は 1 問ずつ `### 例題：ABC382 F. Falling Bars {#abc382_f}`（anchor は問題 ID）を立て、その下に 1 行だけの囲み（`data-role="example"`）、続けて方針を書き、解法の詳細は `??? note "解法の詳細"` に入れる。thinking のページは方針も折りたたむ。練習の方針は一覧の後の折りたたみに書く（一覧で解き方が見えないように）
- 数の目安：例題 1〜3（基礎は 1、発展は 0〜2、thinking は 2〜4、patterns は 0〜1）、練習 2〜6（patterns は 0〜3）、力試し 0〜3、hub は合わせて 0〜3
- 例題は 1 問につき 1 ページ（その手法の持ち主）で、ほかのページでは練習か本文の参照にする。catalog で representative の例題は、手法をそのまま使う代表として扱う。並びは易しい順
- 問題を提案するとき：ABC を優先し、abc319 以降（7 問体制）を重く見る（水・青のページには 1 問以上）。例題の位置は水＝E、青＝F と難しい E、黄＝難しい F と易しい G が目安。典型90・EDPC は型の代表、ARC は少なめ。問いと解き方は第三者の解説で裏付け、URL を添える

## 11. 出典

- ページ末尾に `## 参考 {#references}` を置き、1 行 1 件で「- [著者「題名」](URL)：参考にした点」と書く。例題の方針のために読んだ解説も入れる。ACL は GitHub の document_ja を指す。atcoder.jp・codeforces.com の URL は入れない
- USACO Guide は規約で複製を禁じるので構成の参考だけ。ikatakos 氏の記録（CC BY 4.0）は問題文を引用した節を読まない・使わない。cp-algorithms・OI Wiki（CC BY-SA）の文章と図は使わない
- 付録 B にないドメインは `tools/check_noai.py` で確かめ、結果を報告に書く（メインが付録 B に足す）

## 12. 報告の形

検査（`python3 tools/check_pages.py --page <id>`、`python3 tools/check_snippets.py snippets/<id>`、`npx textlint docs/<field>/<id>.md`）を通してから、次の形で報告する。

```markdown
- 書いたファイル：docs/ds/lazy-segment-tree.md、snippets/lazy-segment-tree/usage.{cpp,yaml}、docs/img/lazy-segment-tree/…
- front matter で変えたもの：complexity・stage・updated（足した節）
- 検査の結果：check_pages・check_snippets・textlint（残った警告とその理由）
- 使った出典：URL と使った箇所。新しく noai を確かめたドメイン
- 提案：用語集（語｜anchor｜定義）、台帳（問題 ID｜項目｜新しい値｜根拠の URL）、
  front matter・catalog（変更と理由）、prh.yml・早見表・使い分け
- 未解決の点：確かめきれなかった事実、迷った点、上位の決定との食い違い
- 使用量の目安：道具の呼び出し回数、Web 取得の回数、所要時間（分かれば入出力のトークン）
```

## 13. 試作で決めたこと（2026-10-21）

試作の執筆者が迷った点の決まり。上の各節と食い違うときはこちらを優先する。

1. **sections に載せる節**：中身の節（理解度のチェックやほかのページからのリンクの単位になるもの）だけを載せる。定型の節は sections に載せず、次の見出しと anchor を使う：`## 例題 {#examples}`・`## 練習問題 {#practice}`・`## 力試し {#challenge}`・`## 確認問題 {#quiz}`・`## 使い分け {#comparison}`・`## 落とし穴 {#pitfalls}`・`## 参考 {#references}`、発展の概要の `## 学ぶための資料 {#resources}`（§16-1）。練習と力試しは別の見出しにする
2. **見出しの文字**：sections に載せた節は、見出しの文字と front matter の `title` を同じにする（見出しを短くしたら title も直す。front matter の sections の title と level と anchor の変更は、執筆者が行ってよい）
3. **例題の小見出し**：`### ABC382 F. 題名 {#abc382_f}` のように anchor は問題 ID にする。difficulty のない問題は、難しさの見当（★や内容）で易しい順の位置に置く
4. **まだないページへのリンク**：catalog にある id のページへは、まだなくても相対リンク（`../ds/segment-tree.md`）を書いてよい。骨格を作れば解決する
5. **用語集へのリンク**：用語集にある語は `../guide/glossary.md#<英語の anchor>` で書く。まだない語はリンクせず本文で短く定義し、報告に「用語集の提案」として語・anchor・定義を書く。メインが用語集に足した後でリンクを張る（§15-1）
6. **台帳にない問題**：本文で触れるときは問題 ID を出さず型だけを書き、報告で台帳への追加を提案する
7. **台帳の summary が表記の規則に合わないとき**：本文の行は fix_problems が台帳から作り直すので、本文だけ直さず、報告で台帳の直しを提案する（メインが台帳を直して fix_problems を流す）
8. **textlint**：エラーは0にする。警告は、数式（`$…$`）の中の括弧や読点、数式を含む文の長さなど、規則の誤検出なら残してよい
9. **取り込まないコード片**：版の注記や失敗例を確かめるためだけの snippets（`*-ng` など）は、本文に取り込まなくても置いてよい
