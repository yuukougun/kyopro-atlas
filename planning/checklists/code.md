# コード片の検証のチェックリスト

コードと図の検証役（書いた本人とは別のエージェント）が使う。渡されるもの：ページ、`snippets/<page-id>/` のコード片と設定、このチェックリスト、執筆の手引き（`planning/style-guide.md` §9）。図は `figure.md`。設計書 §6.5・§8.6・§10.2、design-review T11。

- 指摘は 1 件 1 行で「ファイルと行｜項目（C1 など）｜内容｜確かめた結果（コマンドと出力の要点）｜直し方の案｜重さ（必須／推奨）」の形で一覧にする
- 実行したコマンドと、コンパイラの版（`g++-15 --version` の 1 行目）を記録に残す
- 試しに書いたコードはリポジトリに置かない（作業用の場所を使う）

## C1 コンパイルと実行

- **確かめ方**：`python3 tools/check_snippets.py`（変わったものだけなら `--changed`。使い方は tools/README.md）。手でも `g++-15 -std=gnu++23 -O2 -Wall -Wextra -I third_party/ac-library` でコンパイルし、cases の入力で実行して出力を比べる。未定義動作を疑うときは `-fsanitize=address,undefined` を足して動かす
- **よくある失敗**：警告（未使用の変数、符号付きと符号なしの比較）が残る（`run` は警告があると通らない）。手元の g++-13 だけで試している。ACL のヘッダの名前が違う。小数の出力の桁数が期待と違う

## C2 期待（expect）と cases

- **確かめ方**：設定の `expect` がコード片の目的と合うか。`run` なら、cases が本文の述べる境界（空・1 要素・同じ値・負の値・最大値の近く）を含み、期待出力が手計算か素朴な方法で確かめられているか。`compile-error`・`warning` なら、出たエラー・警告の文面が本文の説明する理由と一致するか
- **よくある失敗**：cases が 1 つだけ。問題の入出力例を写している（問題文の一部なので使わない）。`compile-error` の原因が別の打ち間違い（セミコロン抜けなど）。期待出力をプログラムの出力から写しただけ。`assert` で中身を確かめていない

## C3 本文との一致

- **確かめ方**：取り込んだ行と本文の説明（保つ性質・各操作の手順・境界）を 1 行ずつ対応させる。変数名と記号（`n`・`dp`・`par`・`dep`）、添字（0-indexed）、区間（半開）がそろっているか
- **よくある失敗**：本文は閉区間でコードは半開区間。本文の記号とコードの変数名が違う。説明にない処理が取り込みの範囲に入っている。本文の計算量とコードの計算量が違う

## C4 取り込みの範囲

- **確かめ方**：本文の `--8<-- "<page-id>/<name>.cpp:core"` の名前と、ファイルの `// --8<-- [start:core]`・`// --8<-- [end:core]` が合うか（`mkdocs build --strict` と `tools/check_pages.py` が見る）。取り込みが要点の数行で、実装の全体になっていないか。本文の ```` ```cpp ```` に取り込み以外が書かれていないか、擬似コードが ```` ```text ```` か
- **よくある失敗**：印の名前の打ち間違い。`#include` や `main` まで見せる。完全な実装を載せる（要件は「要点となる数行や処理の流れ」）。本文に C++ を直接書く

## C5 書き方の決まり

- **確かめ方**：手引き §9 と照らす（`bits/stdc++.h` と `using namespace std;`、マクロと型の別名なし、ラムダは比較関数と DFS、DFS は `auto dfs = [&](auto&& self, int v, int p) -> void {…}` の形、改行は `'\n'`、入出力は最小限）。views・`println`・deducing this など新しい書き方には C++ の章へのリンクがあるか
- **よくある失敗**：`#define rep`・`using ll = long long`・`#define int long long`。views を説明もリンクもなしに使う。`endl`。DFS の書き方がページごとにばらばら。C++26 の機能を使う

## C6 版の注記

- **確かめ方**：C++20・23 の機能を使うコード片は、本文に版を書くか C++ の章へリンクしているか。C++ の章のページは設定を `compilers: [g++-13, g++-15]` にして両方を通し、front matter の `gcc_min`・`cpp_std`・`atcoder` と一致するか。`-std=gnu++23` と厳密モード `-std=c++23` の差が話題なら両方で試す
- **よくある失敗**：GCC 14 からの機能に `gcc_min: 13` と書く。`__int128` の扱いの差（`-std=c++23` では `abs(__int128)` がコンパイルエラーになる）を見落とす。AtCoder で使えるかを手元の結果だけで決める

## C7 ACL の使い方

- **確かめ方**：v1.6 の意味で書かれているか（`third_party/ac-library/` を `-I` で使う）。テンプレート引数・メソッドの使い方を v1.6 のドキュメントと照らす（`fact.md` F4）
- **よくある失敗**：`modint::val()` を `unsigned int` として扱う（v1.6 は `int`。`a.val() - b.val()` は負になりうる）。キャプチャのあるラムダを segtree の `op`・`e` に渡す（テンプレート引数にできない）。`lazy_segtree` の `mapping`・`composition` の引数の順を取り違える

## C8 未定義動作とあふれ

- **確かめ方**：サニタイザ付きで cases を動かす。最大の制約の値で中間値の大きさを見積もり、型が足りるかを見る。再帰の深さ（パス状の木で $N$ 段）を見積もる
- **よくある失敗**：`int` どうしの掛け算のあふれ。`v.size() - 1` の符号なしの引き算。未初期化の変数（AtCoder は `-ftrivial-auto-var-init=zero` で 0 になり、手元と結果が違う）。深い再帰でスタックがあふれる
