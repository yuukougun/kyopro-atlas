# 事実の検証のチェックリスト

事実の検証役（書いた本人とは別のエージェント）が使う。渡されるもの：書かれたページ、このチェックリスト、問題の台帳（`data/problems.yaml`）、執筆の手引き（`planning/style-guide.md`）。設計書 §10.2・design-review T12。

- 指摘は 1 件 1 行で「場所（節の anchor か行）｜項目（F1 など）｜内容｜根拠（資料の URL・計算）｜直し方の案｜重さ」の形で一覧にする。重さは「必須」（誤り・規則違反）か「推奨」（直すとよくなる）
- 書いた本人の説明を根拠にしない。一次資料・計算・コードで確かめる
- atcoder.jp・codeforces.com は開かない。手引きの付録 B にないドメインは `python3 tools/check_noai.py <URL>` で確かめてから読む
- 問題の内容を確かめたら、台帳の `checked` に日付を入れる提案を添える（確認済みの記録はほかのページで使い回す）

## F1 計算量

- **見るもの**：要点の「計算量」、front matter の `complexity`、本文の計算量の主張とその根拠
- **確かめ方**：3 か所が一致しているか。根拠（1 回の操作の手間 × 回数、状態数 × 遷移数）を本文の手順から数え直す。ACL の機能は v1.6 のドキュメント（`~/lib/ac-library-master/document_ja/`）の計算量の項と照らす。ならし・期待・前計算の条件と、変数（$N$・$M$・$Q$・値の上限）の定義が書かれているか
- **よくある失敗**：ならしの計算量を最悪の計算量として書く（Union-Find の $\alpha(N)$、vector の push_back）。log の数の取り違え（$O(\log^2 N)$ と $O(\log N)$）。ダイクストラ法を $O(N \log N)$ と書いて辺数を落とす。前計算を数えない。ACL の計算量が「渡す関数が定数時間」の仮定であることを落とす

## F2 定理・性質の主張

- **見るもの**：「〜が成り立つ」「〜なので正しい」と述べる箇所と、その証明・説明
- **確かめ方**：成り立つ条件（法が素数・互いに素・負の辺がない・判定が単調・DAG・凸）がそろっているか。条件を外した小さな反例を作ってみる。証明が主張を本当に支えているか（逆向きの議論・循環になっていないか）。教科書・ACL のドキュメント・信頼できる記事で確かめる
- **よくある失敗**：条件の書き落とし（フェルマーの小定理で $a$ が $p$ の倍数のとき、中国剰余定理で法が互いに素でないとき、二分探索で判定が単調でないとき）。「必ず」「常に」の言い過ぎ。逆が成り立たないのに同値として書く。条件が折りたたみの証明の中にだけある

## F3 具体例と表の数値

- **見るもの**：本文の小さな例、表、図の中の値
- **確かめ方**：手で計算し直すか、短いプログラムで確かめる（試しのコードはリポジトリに置かない）。図・表・本文で同じ例の値がそろっているか。データから計算した数字は `tools/numbers/` のスクリプトがあり、「データから計算した値（日付）」と添えてあるか（手引き §16-13）。早見表（cheatsheet）・逆引き（reverse-index-signs など）に同じ値や見分け方を持つページなら、そちらの行と食い違わないか
- **よくある失敗**：途中の値の計算違い。DP の表の 1 マスの誤り。図と本文で例の値が違う。0-indexed と 1-indexed がずれた例

## F4 ACL の API（v1.6）

- **見るもの**：「ACL では」の囲み、本文とコード片の ACL の使い方
- **確かめ方**：名前・テンプレート引数の順・メソッド名と引数・戻り値の型・要件（制約）・計算量を v1.6 のドキュメントと照らす。怪しいときはコード片で動かす
- **よくある失敗**：`modint::val()` の型（v1.6 は `int`、v1.5 までは `unsigned int`）。`composition(f, g)` の向き（$f \circ g$。g を先に作用させる）。`max_right`・`min_left` の要件 `f(e()) = true`。`mcf_graph` のコストは非負。`z_algorithm` の `z[0]` は $N$。`lcp_array` の長さは $N - 1$。`prod(l, r)` は半開区間。`dsu::merge` の戻り値は代表元。`scc_graph::scc()` の順はトポロジカル順

## F5 問題の内容と台帳

- **見るもの**：問題の囲みの各行、例題の見出し・方針・解法の詳細、本文の問題への言及
- **確かめ方**：`python3 tools/check_pages.py --page <id>` で、書式・台帳にあり確認済みか・label と URL と diff の一致・囲みの外の問題リンクを見る。要約が問いだけで、手法名・解き方を含まないか。例題の方針と解法の詳細を台帳の evidence の解説で確かめ、方針の計算量が制約（$N$ の上限など）に合うか見る。役割と数が台帳・catalog と合い、例題が持ち主のページだけにあるか
- **よくある失敗**：要約に手法名が入る。台帳の summary が「（執筆時に確かめる）」のまま載る。解説が別の解き方をしていて本文の方針と食い違う。方針の計算量が制約に合わない。例題を 2 ページで重ねる。本文に問題の URL を直接書く

## F6 前提とレベル

- **見るもの**：本文で使う手法・用語と front matter の prerequisites、sections の level と節の中身
- **確かめ方**：使う手法・用語が、前提のページか本文のリンクで手当てされているか。節の中身の帯が sections の level と合うか（ページより低い内容の節がないか、基礎のページに黄・発展の中身がないか）。上位の帯の内容が level のない節に紛れていないか
- **よくある失敗**：前提にない手法を説明なしに使う。下位のページの説明を繰り返して節にする。青の内容を水の節に書く

## F7 記法と用語

- **見るもの**：数式・添字・区間・用語・リンク
- **確かめ方**：手引きの §6（記法）・§7 と付録 A（正規形）と照らし、textlint（prh を含む）の結果を見る。添字の 0/1-indexed の変換、半開区間、KaTeX の書き方（`\mathrm{dp}`、表の中の `\lvert`）を見る。用語へのリンクがページの中で最初の 1 回だけか
- **よくある失敗**：閉区間を断りなく使う。1-indexed と 0-indexed が混ざる。「セグメントツリー」「ダイクストラ」などの揺れ。数式の中の日本語を `\text` で囲まない。同じ語に何度もリンクする

## F8 出典の文章に近すぎないか

- **見るもの**：参考に挙げた資料・台帳の evidence と、同じ話題を扱う本文の段落
- **確かめ方**：資料と本文を並べて読み、文の並び・言い回し・例（数値・図の形）がそのままでないかを見る
- **よくある失敗**：記事の例をそのまま使う（同じ数値・同じ図）。語だけ入れ替えて文の順序と言い回しが同じ。問題の要約が問題文の言い回しのまま

## F9 参考の URL

- **見るもの**：ページ末尾の「参考」
- **確かめ方**：各 URL を開き（atcoder.jp・codeforces.com は開かない）、題名・著者・内容が書かれたとおりかを見る。題名は記事の h1 のままか（手引き §14-24。空白の補いなどで書き換えていないか）。ドメインが付録 B にあるか、なければ `tools/check_noai.py` で確かめる。atcoder.jp・codeforces.com の URL が入っていないか
- **よくある失敗**：記憶で書いた URL（存在しない・別の記事）。atcoder.jp にある公式解説を参考に入れる（典型90 の作者の GitHub の解説は手引き §11 のとおり挙げてよい）。USACO Guide の文章を使う。ikatakos 氏の記録の問題文を引用した節を使う

## F10 front matter と冒頭

- **見るもの**：front matter、要点の囲み、別名の行、導入
- **確かめ方**：`tools/check_pages.py` の結果を見る。執筆者が変えたのが `complexity`・`stage`・`updated`（と足した節）だけか。要点が summary・signs・prerequisites と食い違わないか（特に「何ができるか」と summary を並べて読む）、計算量が埋まっているか。別名の行に aliases がすべてあるか
- **よくある失敗**：`complexity` と要点の計算量が違う。要点に「（執筆時に書く）」が残る。題名・別名・前提を提案にせず直接書き換える。別名の行が最初の `##` より後にある
